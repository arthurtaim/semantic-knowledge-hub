# GitLab как хранилище базы знаний: структура, изменения, синхронизация

Статус: реализовано в приложении и проверено **только на GitLab-mock** (`backend/tests/support/gitlab_mock.py`;
pytest, Playwright и Docker-профиль `integration_mock`). Поведение настоящего GitLab банка подтверждается
отдельно по `docs/STAGING_TEST_RUNBOOK.md`. Обновлено для M4.6 (операция `create`, редактируемые черновики)
и M5 (передача смёрженной ревизии в публикацию).

GitLab — источник истины для документации команды. Приложение читает его, индексирует и создаёт
предложения изменений через ветку и Merge Request. Само приложение ничего не утверждает и не делает merge:
это делают ревьюеры в GitLab по правилам защищённой ветки.

## 1. Структура репозитория знаний

```text
<группа>/<проект-базы-знаний>         # отдельный GitLab-проект, не репозиторий приложения на GitHub
├── README.md                         # вне каталога знаний — не индексируется
├── CODEOWNERS                        # владельцы разделов = обязательные ревьюеры MR
└── docs/                             # GITLAB_KNOWLEDGE_PATH=docs (пусто = корень репозитория)
    ├── SEM-ARCH-001.md
    ├── SEM-PROC-001.md
    └── integrations/SEM-INT-ARIS-001.md   # подкаталоги допустимы
```

- Индексируются только файлы `*.md` внутри `GITLAB_KNOWLEDGE_PATH` ветки `GITLAB_DEFAULT_BRANCH`.
- Не более `GITLAB_MAX_FILES` файлов (по умолчанию 2000) и `MAX_DOCUMENT_BYTES` на файл (512 КБ).
- Бинарные файлы, схемы и вложения сейчас не индексируются: ссылайтесь на них из Markdown.

## 2. Документ

Markdown с YAML front matter по `docs/DOCUMENT_SCHEMA.md`. Обязательные поля: `id`, `title`, `type`,
`status`, `owner`, `tags`. Необязательные: `related_ids`, `source_refs`, `reviewed_at`, `summary`.

| Правило | Почему |
|---|---|
| `id` уникален во всём репозитории (без учёта регистра) и **никогда не меняется** | на него ссылаются цитаты, связи и предложения; дубликаты не показываются вообще, а попадают в «Проблемы загрузки» |
| Имя файла = `<id>.md` (рекомендация) | путь файла может меняться, `id` — нет |
| Формат `id`: `<ОБЛАСТЬ>-<ТИП>-<NNN>` (пример `SEM-ARCH-001`) | читаемо, сортируется, однозначно |
| Статусы: `draft` → `in_review` → `approved` → `deprecated` | ассистент по умолчанию опирается только на `approved` и `in_review` |
| Перевод в `approved` — только через MR и ревью | ИИ-предложение не может ставить `approved` (ошибка валидации) |

## 3. Версионирование

- **Ревизия документа** = `last_commit_id`, который GitLab сообщает для файла. Локальные метки времени не используются.
- **Дата обновления** = `committed_date` этого коммита. Если GitLab её не отдал, дата не выдумывается: показывается «—».
- **Ссылка на оригинал** ведёт на файл именно этой ревизии: `<web_url проекта>/-/blob/<sha>/<путь>`.
  Ссылка формируется, только если хост и схема совпадают с `GITLAB_URL`.
- **Конкретная ревизия** читается из истории GitLab (`get_document_at_revision`) по текущему пути документа.
  Принимаются только SHA коммитов (`[0-9a-f]{7,64}`), имена веток и тегов не принимаются.

## 4. Изменения через Merge Request

Предложение имеет операцию (`operation`): `update` — изменение существующего документа, `create` — новый
документ (M4.6, раздел 4a и `docs/DOCUMENT_CREATION_WORKFLOW.md`). Путь через ветку и MR у них общий.

```text
Документ ─▶ Предложение (draft, редактируемый черновик) ─▶ Валидация ─▶ Diff-ревью ─▶ «Готово к ревью»
          ─▶ «Отправить в GitLab»: ветка kb/update/<ID>-<8 символов id предложения> ─▶ коммит update|create ─▶ MR (Draft:)
          ─▶ ревью и merge в GitLab (люди) ─▶ «Проверить статус» ─▶ merged ─▶ синхронизация и переиндексация
          ─▶ merged_revision зафиксирована ─▶ задание публикации в Confluence (если настроено; раздел 10)
```

1. **Создание предложения** не меняет документ. Сохраняются ID документа, базовая ревизия, исходный и новый
   текст, причина, автор, время и результат валидации. Пока предложение в статусе `draft`, это
   **редактируемый черновик**: `PUT /api/drafts/{id}` с `expected_version` (оптимистическая блокировка,
   устаревшая версия → `409 draft_modified`), удаление — `DELETE /api/drafts/{id}` (только до отправки в
   GitLab). Базовая ревизия при правке черновика не меняется.
2. **Валидация** (при создании и повторно перед отправкой):
   - корректность Markdown и YAML front matter;
   - обязательные поля; `id` не изменён, а значит остаётся уникальным;
   - путь — относительный POSIX-путь `.md` внутри `GITLAB_KNOWLEDGE_PATH`, без `..`, `\`, абсолютных путей и пустых сегментов;
   - размер не больше `MAX_DOCUMENT_BYTES`;
   - текст действительно изменён;
   - ИИ-предложение не переводит документ в `approved`.
3. **«Готово к ревью»** — локальный статус. Перед переходом ревизия документа сверяется с GitLab напрямую, в обход кэша.
4. **Отправка** (только при `GITLAB_PROPOSALS_ENABLED=true`):
   - Сначала ищется существующий MR ветки предложения (любого состояния). Если он есть, он переиспользуется, новый не создаётся.
   - Существующая ветка переиспользуется, только если в ней нет коммитов или есть только коммит этого
     предложения (трейлер `Proposal-Id`). Ветка с чужими коммитами не трогается: результат — ошибка `gitlab_branch_conflict`.
   - Коммит содержит ровно одно действие над файлом документа: `update` с предусловием `last_commit_id` =
     базовая ревизия или — для нового документа — `create` (раздел 4a). Удаление и перенос файлов, смена прав
     и действия над другими путями запрещены.
   - Сообщение коммита: `docs(<ID>): <причина>` (для `create` — `docs(<ID>): create — <причина>`) и трейлеры
     `Proposal-Id: <id>`, `Operation: update|create`; для `update` также `Base-Revision: <SHA>`.
   - Прямой коммит в основную ветку невозможен: имя ветки всегда начинается с `kb/update/`. Защищённая ветка
     в GitLab — второй рубеж.
   - MR создаётся с префиксом `Draft:`. В описании: документ, файл, базовая ревизия, причина, объём изменений,
     автор, `Proposal-Id` и ссылка на предложение (если задан `APP_PUBLIC_URL`).
5. **Merge** выполняют только ревьюеры GitLab. Статус `merged` ставится только после того, как GitLab сообщил
   `state=merged` (кнопка «Проверить статус в GitLab»). После этого запускается синхронизация, и база знаний
   показывает новую ревизию; приложение записывает её в предложение (`merged_revision`, `synced_at`, событие
   `knowledge_synced`). Если синхронизация сразу после merge не удалась, предложение остаётся `merged` с
   `source_document_state=merged_pending_sync` и `can_refresh_status=true`: повторная «Проверить статус в
   GitLab» повторяет синхронизацию. Merge при этом не отменяется.
6. **MR закрыт без merge** → предложение `rejected` с комментарием. Повторно MR не создаётся: закрытие — решение ревьюеров.

## 4a. Новый документ (`operation=create`)

1. Черновик создаётся по шаблону (`POST /api/authoring/drafts`); frontmatter генерирует приложение
   (`docs/DOCUMENT_TEMPLATES.md`). Базовой ревизии нет (`base_revision=""`), базовое содержимое пустое.
2. ID и путь проверяются на уникальность (без учёта регистра) против базы знаний и незавершённых предложений
   создания; перед «Готово к ревью» и перед отправкой — по свежему состоянию ветки знаний (синхронизация и
   прямое чтение файла).
3. При отправке, непосредственно перед коммитом, файл ещё раз проверяется в GitLab: **файл не должен
   существовать**. Если он появился — конфликт `document_exists`, предложение → `conflict`, ничего не
   записано, чужой файл не тронут.
4. Коммит — одно действие `create` **без** `last_commit_id`; трейлеры `Proposal-Id`, `Operation: create`.
   GitLab сам отклоняет `create` существующего файла (400); приложение решает по фактическому состоянию
   файла, а не по тексту ошибки.
5. MR: `Draft: [новый] <ID> — <причина>`; описание — «Операция: создание нового документа», «Базовая
   ревизия: — (новый файл)».
6. Документ появляется в каталоге и поиске только после подтверждённого merge и синхронизации.
   `source_document_state` до merge — `new_document` (или `id_taken`, если ID занял другой документ).
7. Потерянные ответы обрабатываются так же, как для `update` (раздел 6): коммит с трейлером `Proposal-Id`
   и MR ветки находятся и переиспользуются, дубликатов нет.

## 5. Состояния предложения

Локальный статус и состояние MR хранятся **раздельно** (`status` и `merge_request.state`).

| Статус | Значение | Что можно сделать |
|---|---|---|
| `draft` | создано, документ не изменён; черновик можно редактировать и удалить | «Сохранить», «Удалить черновик», «Готово к ревью», «Отклонить» |
| `ready_for_review` | проверено на актуальной ревизии; **MR ещё нет** | «Отправить в GitLab», «Отклонить» |
| `submitting` | идёт запись в GitLab (защита от двойной отправки) | ждать; через 5 минут считается прерванным и может быть повторено |
| `submitted_to_gitlab` | MR существует; **это не утверждение** | «Проверить статус в GitLab» |
| `merged` | GitLab подтвердил merge | при `merged_pending_sync` — «Проверить статус в GitLab» (повтор синхронизации) |
| `rejected` | отклонено локально или MR закрыт без merge | — |
| `conflict` | документ изменился после базовой ревизии (`update`) или ID/путь уже заняты (`create`); ничего не перезаписано | создать новое предложение на актуальной версии / новый черновик с этим текстом и другим ID; удалить, если отправок не было |
| `submission_failed` | запись в GitLab не завершилась; предложение сохранено | «Повторить отправку»; при `uncertain` сначала «Проверить статус» |

## 6. Ошибки записи и повторы

| Ситуация | Поведение |
|---|---|
| 401/403 при записи | `submission_failed`, результат определён, ничего не записано; повтор после исправления прав |
| SHA-конфликт (наша проверка или 400 от GitLab на `last_commit_id`) | `conflict`; ничего не перезаписано |
| Коммит отклонён по другой причине (400) | `submission_failed` (`gitlab_commit_rejected`) |
| Таймаут или 5xx на POST коммита | POST **не повторяется**. Ветка проверяется: если коммит есть — продолжаем, если нет — `submission_failed` с пометкой, что повтор безопасен. Если проверить не удалось — `uncertain` |
| Таймаут или 5xx на POST MR | MR ищется по ветке. Нашёлся — переиспользуется, иначе `uncertain` |
| `uncertain` | отклонить нельзя, пока не выяснено, создан ли MR. «Проверить статус» либо находит MR (→ `submitted_to_gitlab`), либо снимает пометку |
| GET-запросы | до 2 повторов для 429/502/503/504 и таймаутов, с учётом `Retry-After` (не более 5 с) |

## 7. Конфликты

- Предложение хранит базовую ревизию. Перед «Готово к ревью» и перед отправкой ревизия сверяется с GitLab
  в обход кэша.
- Последний рубеж — предусловие `last_commit_id` в самом коммите: даже гонка между проверкой и записью
  не перезапишет чужую правку. Для `create` последний рубеж — отказ GitLab создавать существующий файл.
- В конфликте ни документ, ни предложение не теряются. Пользователь может открыть редактор с текстом
  старого предложения поверх **актуальной** версии и обязательно посмотреть diff: иначе можно отменить
  чужие изменения.

## 8. Синхронизация и индекс

- **Быстрая проверка:** head-коммит ветки знаний. Если он не изменился и прошлых сбоев не было, дерево не перечитывается.
- **Инкрементальное обновление:**
  - дерево обходится с keyset-пагинацией (с откатом на offset);
  - перечитываются только файлы с изменившимся `blob id`;
  - файлы, исчезнувшие из дерева, удаляются из каталога и из поискового индекса.
- **Индекс** (SQLite FTS5) хранит для каждого документа источник и ревизию (`doc_versions`). Документ
  переиндексируется при смене ревизии или метаданных; запись на документ ровно одна.
- **Частичный сбой:** файл, который не удалось перечитать, остаётся в последней успешно прочитанной версии
  с пометкой «Версия может быть устаревшей» (`index_state=stale`). Сбой виден в `/api/index/status`
  и в «Проблемах загрузки». Новый документ, который не удалось прочитать, не показывается.
- **GitLab недоступен** (сеть, 5xx, таймаут): показывается последний синхронизированный снимок, и **все**
  документы помечены как возможно устаревшие.
- **401/403/404:** кэш сбрасывается, документы не показываются (fail closed: права могли быть отозваны).
- **Ручной запуск:** `POST /api/index/sync` или кнопка «Синхронизировать сейчас» на странице «Интеграции».
  Это полное перечитывание с очисткой инкрементального кэша.
- **Периодичность:** не чаще `GITLAB_REFRESH_SECONDS` (60 с) при обращении к данным. Фонового планировщика нет.

Известное ограничение: если файл вернули к прежнему содержимому (`A→B→A`) между двумя синхронизациями,
`blob id` совпадает и показанная `last_commit_id` остаётся прежней. Текст при этом верный, а проверка
перед записью обращается к GitLab напрямую. Поэтому возможен только ложный конфликт, а не перезапись.
Полная синхронизация (`/api/index/sync`) это исправляет.

## 9. Передача в публикацию (M5)

После подтверждённого merge и успешной синхронизации приложение вызывает публикацию с ID документа,
`merged_revision` и ID предложения. Если настроен `CONFLUENCE_REST_URL`, создаётся задание публикации для
этой ревизии и выполняется dry-run (только чтение); публикация — отдельное явное действие оператора.
Перед публикацией GitLab ещё раз спрашивается, попала ли ревизия в ветку знаний через смёрженный MR
(`GET /projects/:id/repository/commits/:sha/merge_requests`). Публикация никогда не меняет GitLab и
предложение; её ошибка не отменяет merge. Подробно — `docs/CONFLUENCE_PUBLISHING_ARCHITECTURE.md`.

## 10. Права и изоляция

До появления SSO/RBAC приложение читает GitLab одной сервисной учётной записью и показывает всё
прочитанное единственному локальному оператору (`AUTH_MODE=local_demo`, только loopback). Поэтому
GitLab с реальными данными допустим только в однопользовательском тестовом контуре
(см. `docs/PRODUCTION_BLOCKERS.md`, `docs/SSO_RBAC_REQUIREMENTS.md`).
