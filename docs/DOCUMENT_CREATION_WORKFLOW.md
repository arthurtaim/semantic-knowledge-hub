# Создание нового документа: от черновика до базы знаний и публикации (M4.6)

Статус: реализовано. Проверено локально (pytest, Vitest, Playwright `frontend/e2e/authoring.spec.ts`) и на
тестовых дублях GitLab и Confluence (`backend/tests/support/*_mock.py`, профиль `integration_mock`). С реальным
GitLab **не проверялось** (`docs/M4_M5_INTEGRATION_READINESS.md`). Соответствие сценариев E2E-13…22 тестам —
`docs/DEVELOPMENT.md` («Тесты и проверки»).

Связанные документы: шаблоны — `docs/DOCUMENT_TEMPLATES.md`; AI-помощник — `docs/AI_AUTHORING_CONTRACT.md`;
GitLab — `docs/GITLAB_KNOWLEDGE_WORKFLOW.md`; публикация — `docs/CONFLUENCE_PUBLISHING_ARCHITECTURE.md`;
API — `docs/API_CONTRACTS.md` (v0.3). Много файлов сразу (ZIP, папка) — «Массовый импорт»,
`docs/KNOWLEDGE_ONBOARDING.md` (M8): он создаёт такие же черновики и дальше идёт по этому же пути.

## 1. Сквозной путь

```text
«Создать документ» (главная, каталог, «Предложения»)
  → режим: «Вручную» | «С помощью AI» (демо)
  → тип документа = шаблон (раздел каталога)
  → редактор Markdown + предпросмотр; метаданные — в форме, frontmatter генерирует приложение
  → «Сохранить черновик»      POST /api/authoring/drafts (201), далее PUT /api/drafts/{id} c expected_version
  → «Проверить»               POST /api/authoring/check (ничего не сохраняет)
  → «Отправить на ревью»      сохранить + POST /api/drafts/{id}/mark-ready (свежая проверка ID/пути в GitLab)
  → «Отправить в GitLab»      POST /api/drafts/{id}/submit: ветка kb/update/<ID>-<8 hex> → коммит `create` → Draft MR
  → ревью и merge в GitLab    (только люди, по правилам защищённой ветки)
  → «Проверить статус в GitLab» POST /api/drafts/{id}/refresh-status: `merged` только по ответу GitLab
  → синхронизация базы знаний и поискового индекса FTS; фиксируется merged_revision
  → задание публикации + dry-run в Confluence (если публикация настроена); публикация — отдельным явным действием
```

Документ появляется в каталоге, поиске и доказательной базе ассистента **только** после подтверждённого
GitLab merge и успешной синхронизации. Черновик, предложение «Готово к ревью» и открытый MR — это ещё не знание.

## 2. Три независимых жизненных цикла

| Сущность | Где хранится | Статусы | Кто меняет |
|---|---|---|---|
| Документ | GitLab (`docs/DOCUMENT_SCHEMA.md`), локальный индекс — производный | `draft`, `in_review`, `approved`, `deprecated` (поле `status` во frontmatter) | только merge в GitLab |
| Предложение (`operation=create`) | `app_state.sqlite3` (том `workspace`) | `draft`, `ready_for_review`, `submitting`, `submitted_to_gitlab`, `merged`, `rejected`, `conflict`, `submission_failed` | приложение по действиям пользователя и ответам GitLab |
| Публикация | `publications.sqlite3` | см. `docs/CONFLUENCE_PUBLISHING_ARCHITECTURE.md` | оператор публикации |

Статусы не смешиваются: `ready_for_review` ≠ MR; MR ≠ merge; merge ≠ опубликовано в Confluence.
Статус документа `approved` в форме вступает в силу только после ревью и merge (предупреждение
`status_to_approved`).

## 3. Раздел каталога = тип документа (шаблон)

Пользователь выбирает не каталог в репозитории, а **тип документа**. Тип задаётся шаблоном и определяет раздел
каталога (`type` во frontmatter), префикс ID и обязательную структуру.

| Шаблон (`template_id`) | Название | `type` → раздел каталога | Префикс ID |
|---|---|---|---|
| `architecture` | Архитектура | `architecture` → «Архитектура» | `SEM-ARCH` |
| `integration` | Интеграция | `integration` → «Интеграции» | `SEM-INT` |
| `business_entity` | Бизнес-сущность | `domain` → «Домен» | `SEM-DOM` |
| `adr` | Архитектурное решение (ADR) | `decision` → «Решения» | `SEM-DEC` |
| `team_process` | Процесс команды | `process` → «Процессы» | `SEM-PROC` |

- Предлагаемый ID — следующий свободный `<ПРЕФИКС>-NNN` (без учёта регистра) с учётом документов базы знаний
  **и** незавершённых предложений создания.
- Предлагаемый путь — `<GITLAB_KNOWLEDGE_PATH>/<ID>.md` (в локальном режиме — `<ID>.md`). Подкаталоги по типу
  не создаются. Путь можно изменить, но он должен оставаться внутри каталога знаний, а имя файла — совпадать
  с ID (`<ID>.md`).
- Раздел в каталоге определяется полем `type`, а не каталогом файла.
- Тип документа нельзя изменить вручную: поле `type` всегда берётся из шаблона (`template_type_mismatch`).

## 4. Ручное создание

Форма: ID (предложен), название, владелец, статус (`draft` по умолчанию; можно `in_review` или `approved`;
`deprecated` для нового документа запрещён), теги, связанные документы (`related_ids`), источники
(`source_refs`), краткое описание (`summary`), **причина** (обязательна, от 3 символов; попадает в описание MR)
и тело Markdown, заранее заполненное структурой шаблона.

Редактор: панель Markdown (заголовки, списки, таблицы, ссылки, код), предпросмотр (рядом на десктопе,
переключатель на телефоне), индикатор «Есть несохранённые изменения», подтверждение при уходе со страницы.
Подтверждение одно для всех путей ухода внутри приложения — ссылки, боковая панель, «Отмена», кнопки браузера
«Назад»/«Вперёд»: диалог «Остаться» (фокус по умолчанию, Esc) / «Выйти без сохранения»; закрытие или перезагрузку
вкладки подтверждает сам браузер (`beforeunload`). После сохранения, отправки на ревью или удаления черновика
вопроса нет (`frontend/src/components/UnsavedChangesGuard.tsx`, дефект SYS-007).
Предпросмотр рендерится сервером через ту же санитизацию, что и документы (`preview_html`, без скриптов
и `javascript:`-ссылок). YAML пользователь не пишет — frontmatter генерируется (`docs/DOCUMENT_TEMPLATES.md`).

## 5. Создание с помощью AI (и без языковой модели)

«С помощью AI» → шаблон → название и запрос → `POST /api/authoring/ai-draft`. Ответ — **только текст-предложение**:
он не сохраняется и не становится предложением сам по себе. Текст подставляется в тот же редактор, дальше
путь одинаковый: сохранить → проверить → ревью → GitLab. Без языковой модели (`mock`) это структура шаблона, ссылки на
утверждённые документы и их дословные выдержки; остальные места помечены «Требует уточнения». Черновик
с `origin=ai_suggestion` не может иметь статус `approved` (ошибка `ai_cannot_approve`). Если AI выключен
(`AI_PROVIDER=disabled`), кнопка недоступна, `features.ai_authoring=false`, запрос — `503 ai_authoring_unavailable`.
Контракт — `docs/AI_AUTHORING_CONTRACT.md`.

## 6. Постоянный черновик

- Черновик — это предложение `operation=create` в статусе `draft`, сохранённое на backend в
  `app_state.sqlite3` (в Docker — том `workspace`). Он переживает перезагрузку страницы и перезапуск
  контейнеров. Только в `localStorage` черновики не хранятся.
- **Первое сохранение** — `POST /api/authoring/drafts` → `201` и `edit_version=1`; адрес страницы меняется на
  `/documents/new?draft=<id>`. **Следующие** — `PUT /api/drafts/{id}` с `expected_version` = текущий
  `edit_version`; каждое сохранение увеличивает версию на 1.
- **Параллельная правка** (две вкладки, два человека): устаревший `expected_version` → `409 draft_modified`
  (`details.current_version`). Ничего не перезаписано; локальный текст остаётся в редакторе для копирования,
  UI предлагает загрузить сохранённую версию.
- **Редактировать** можно только в статусе `draft` (`can_edit`). После «Готово к ревью» — `409 draft_not_editable`.
- **Удалить** — `DELETE /api/drafts/{id}` (`204`) после подтверждения в UI. Разрешено для `draft`, а также для
  `conflict`, если предложение ни разу не отправлялось в GitLab и MR нет (`can_delete`). Иначе —
  `409 draft_not_deletable`. Бессодержательный журнал аудита сохраняется; ID освобождается.
- **Продолжить** — список «Предложения» или `/documents/new?draft=<id>`; форма восстанавливается из
  сохранённого Markdown (`new_document.metadata`, `new_document.body`).
- Черновики предложений **изменения** существующих документов тоже редактируются: `PUT /api/drafts/{id}` с
  `proposed_content` (базовая ревизия не меняется).

## 7. Проверки

| Проверка | Код | Уровень |
|---|---|---|
| YAML-frontmatter разбирается, обязательные поля, корректный `title`, списки, даты | `missing_field`, `invalid_title`, `invalid_list`, `invalid_date`, … | ошибка |
| Тело не пустое | `empty_body` | ошибка |
| Нет ни одного заголовка | `no_heading` | предупреждение |
| Размер не больше `MAX_DOCUMENT_BYTES` (512 КБ) | `document_too_large` | ошибка |
| Путь — относительный POSIX `.md` внутри каталога знаний, без `..`, `\`, пустых сегментов | `unsafe_path` | ошибка |
| Имя файла = `<ID>.md` | `path_id_mismatch` | ошибка |
| Новый документ не `deprecated` | `new_document_deprecated` | ошибка |
| AI-черновик не `approved` / ручной `approved` | `ai_cannot_approve` / `status_to_approved` | ошибка / предупреждение |
| `type` совпадает с шаблоном | `template_type_mismatch` | ошибка |
| Есть все разделы шаблона | `template_section_missing` | предупреждение |
| Не осталось «Требует уточнения» | `unresolved_placeholders` | предупреждение |
| `related_ids` существуют в базе знаний | `unresolved_related` | предупреждение |
| Секреты и персональные данные | `secret_detected`, `personal_data_detected` | ошибка |
| `approved` без `reviewed_at` | `approved_without_review` | предупреждение |
| ID не занят | `document_id_taken` | ошибка |
| Путь не занят | `document_path_taken` | ошибка |

**Уникальность ID и пути** (без учёта регистра) проверяется:

1. против текущего снимка базы знаний — ID документов (включая дубликаты) и пути файлов, в том числе файлов,
   не прошедших валидацию;
2. против **незавершённых** предложений создания (`draft`, `ready_for_review`, `submitting`,
   `submitted_to_gitlab`, `submission_failed`) — сообщение называет причину конфликтующего предложения;
3. перед «Готово к ревью» и перед отправкой — по **свежему** источнику: синхронизация, затем прямое чтение файла
   в ветке знаний (`file_exists`), в обход кэша;
4. последний рубеж — непосредственно перед коммитом (`current_file_revision`) и сам GitLab, который отклоняет
   `create` существующего файла. Гонка разрешается конфликтом, а не перезаписью.

Когда выполняются проверки:

| Действие | Результат |
|---|---|
| «Проверить» (`POST /api/authoring/check`) | полный список замечаний, `id_available`, `path_available`, сгенерированный файл и предпросмотр; ничего не сохраняется |
| Сохранение (`POST`/`PUT`) | занятый ID/путь → `409`, черновик **не** сохранён/не изменён; прочие ошибки сохраняются вместе с черновиком |
| «Готово к ревью» | ошибки → `422 validation_failed`; занятый ID/путь по свежему источнику → `409 document_exists`, предложение → `conflict` |
| «Отправить в GitLab» | повторная проверка содержимого и свежая проверка ID/пути; занятый → `409 document_exists` |

## 8. Ревью и GitLab

- «Отправить на ревью» в редакторе сохраняет черновик (если есть несохранённые изменения) и отмечает его «Готово к ревью». Это локальный
  статус: **MR ещё нет**, это не утверждение.
- «Отправить в GitLab» доступна при `GITLAB_PROPOSALS_ENABLED=true` (иначе предложение остаётся локальным,
  `503 gitlab_proposals_disabled`):
  - ветка `kb/update/<ID>-<первые 8 символов id предложения>`; прямой коммит в основную ветку невозможен;
  - ровно один коммит с одним действием `create` файла документа, **без** `last_commit_id`; трейлеры
    `Proposal-Id: <id>` и `Operation: create`;
  - Draft MR `Draft: [новый] <ID> — <причина>`; в описании «Операция: создание нового документа», файл,
    «Базовая ревизия: — (новый файл)», объём изменений, автор, `Proposal-Id` и ссылка на предложение
    (при `APP_PUBLIC_URL`).
- Повторная отправка не создаёт второй MR: из `submitted_to_gitlab` отправка запрещена (`409 invalid_transition`),
  а после потерянного ответа существующие ветка, коммит с трейлером и MR находятся и переиспользуются.
- Merge выполняют только ревьюеры GitLab. «Проверить статус в GitLab» ставит `merged` только по ответу GitLab
  `state=merged`; MR закрыт без merge → `rejected`.

## 9. После merge: синхронизация и передача в публикацию

1. GitLab подтвердил merge → статус `merged`.
2. Синхронизация базы знаний и инкрементальная переиндексация FTS.
3. Приложение читает ревизию документа в ветке знаний (`current_revision`) и сохраняет её как
   `merged_revision` вместе с `synced_at`; событие `knowledge_synced`.
4. Если настроен `CONFLUENCE_REST_URL`, создаётся задание публикации для этой ревизии и выполняется dry-run
   (только чтение). Публикация автоматически **не** выполняется.

Если синхронизация не удалась (GitLab недоступен сразу после merge), статус остаётся `merged`, но
`merged_revision` пуст, `source_document_state=merged_pending_sync`, `can_refresh_status=true`: повторное
«Проверить статус в GitLab» повторяет синхронизацию. Ошибка синхронизации или публикации merge не отменяет.

## 10. Статусы и что видит пользователь

| Статус предложения | Подпись в UI | Что видно и что можно сделать |
|---|---|---|
| `draft` | «Новое» | редактирование, «Сохранить черновик», «Проверить», «Отправить на ревью», «Удалить черновик» |
| `ready_for_review` | «Готово к ревью» | «Отправить в GitLab» (если включено), «Отклонить»; редактирование закрыто |
| `submitting` | «Отправляется в GitLab» | ожидание; через 5 минут считается прерванным и может быть повторено |
| `submitted_to_gitlab` | «MR в GitLab» | ссылка на MR, «Проверить статус в GitLab» |
| `merged` | «Принято (merge)» | ревизия в базе знаний (`merged_revision`), время синхронизации; при `merged_pending_sync` — повторная проверка |
| `rejected` | «Отклонено» | комментарий; MR повторно не создаётся |
| `conflict` | «Конфликт версий» | ID или путь занят; текст сохранён; «Создать новый черновик с этим текстом» (`/documents/new?from=<id>`) с новым ID; удаление, если отправок не было |
| `submission_failed` | «Ошибка отправки» | «Повторить отправку»; при `uncertain` сначала «Проверить статус в GitLab» |

`source_document_state` для `create`: `new_document` (документа ещё нет — ожидаемо до merge), `id_taken`
(документ с этим ID появился раньше merge предложения), `merged_pending_sync`, `updated_by_this_proposal`.

## 11. Ответы 409 и как с ними работать

| Код | Когда | Что произошло | Что делать |
|---|---|---|---|
| `document_id_taken`, `document_path_taken` | сохранение черновика | черновик не сохранён/не изменён; `details.field` (`id`/`path`), `details.validation` | UI подсвечивает поле, текст остаётся; выбрать другой ID/путь |
| `draft_modified` | `PUT` с устаревшей версией | ничего не перезаписано; `details.current_version` | скопировать свой текст, загрузить сохранённую версию, перенести правки |
| `draft_not_editable` | `PUT` после «Готово к ревью» | — | создать новое предложение |
| `draft_not_deletable` | `DELETE` после отправки в GitLab | — | закрыть MR в GitLab |
| `document_exists` | «Готово к ревью» или отправка | ID/путь занят в GitLab; предложение → `conflict`, ничего не записано | новый черновик с этим текстом и другим ID |
| `invalid_transition` | действие не подходит к статусу | — | обновить страницу |
| `submission_in_progress` | двойная отправка | — | дождаться окончания |
| `gitlab_branch_conflict` | ветка предложения содержит чужие коммиты | ветка не тронута | разобраться в GitLab |

При ошибках API редактор не сбрасывает введённый текст (для 409 это закреплено тестами Vitest).

## 12. Diff нового файла

Для `create` базовое содержимое пустое: diff — один блок `@@ -0,0 +1,N @@`, все строки сгенерированного файла
(frontmatter и тело) отмечены как добавленные, `deletions=0`. В UI предложение помечено «Новый документ».
