# Work Management (M6): проекты, задачи, зависимости, планирование

Собственный лёгкий трекер внутри SKH (модульный монолит, без Plane/Jira): проекты, задачи и подзадачи, статусы,
приоритеты, исполнители, даты, вехи, зависимости Finish-to-Start, серверный предпросмотр расписания и
атомарное применение, аудит; связи задач с документами базы знаний и AI-предложения плана задач. Этот документ —
контракт для backend (шаги 1–2), UI (шаг 3, §9), связей с документами (шаг 4, §10) и AI (шаг 5, §11); проверка и
производительность — §12, обзор безопасности — §13. Все шаги 1–6 реализованы локально; развёртывание (шаг 7) не
выполнялось. Маршруты и схемы: `docs/API_CONTRACTS.md` «v0.8». Аудит исходного состояния: `reports/m6/BASELINE_AUDIT.md`,
итог: `reports/m6/FINAL_REPORT.md`, руководство пользователя: `docs/WORK_USER_GUIDE.md`.

## 1. Модель данных

**Статусы.** Workflow — четыре колонки Kanban; переходы между ними свободны (перетаскивание в любую колонку).
«Заблокирована» не статус: `blocked_by` = незавершённые FS-предшественники, вычисляется при чтении. Архив —
отдельное состояние (`archived_at`), а не статус. `Project.status` — статус проекта, не задачи.

**Иерархия.** Не более 4 уровней; подзадачи только в своём проекте; смена родителя проверяет циклы, глубину всего
переносимого поддерева и отсутствие FS-зависимости между поддеревом и новыми предками. У вехи детей нет
(`milestone_parent`, `milestone_has_children`). Даты родителя не сворачиваются из дочерних (P0).

**Удаление = архив.** `DELETE /api/tasks/{id}` архивирует; при активных подзадачах нужен `cascade=true`. Зависимости
архивируемых задач удаляются (с аудитом); аудит и ссылки на документы остаются. `restore` возвращает задачу и
поддерево, заархивированное той же операцией (старые зависимости не восстанавливаются). Пока задача лежала в архиве,
родитель мог измениться, поэтому `restore` заново проверяет инварианты переноса **до любой записи**: родитель активен
и в этом проекте, он не веха, а глубина родителя плюс высота всего возвращаемого поддерева ≤ 4. Иначе — `409
conflict` (`parent_archived` / `milestone_parent` / `too_deep` / `parent_not_in_project`), ничего не меняется (ни
задачи, ни ревизия плана, ни аудит); человек исправляет родителя и повторяет восстановление. Архивный проект — задачи
только для чтения (`409 conflict` `project_archived`).

**Диапазон дат — один на модуль** (`app/work/calendar.py` `MIN_YEAR..MAX_YEAR` = 2000–2100). Ему подчиняется каждая
хранимая дата: введённая человеком (задача, проект, начало «AI плана») — иначе `422 invalid_date_range`
`{reason: out_of_range, field}`; и вычисленная сервером: конец по длительности (как явный `end_exclusive`), сдвиг
зависимых в предпросмотре (конфликт `out_of_range`, применить нельзя), даты «AI плана» (замечание
`dates_out_of_range`, `can_apply=false`, apply → `422 plan_out_of_range`). Поэтому календарная арифметика не
доходит до `date.max` и не падает в 500. Веха хранится на указанной дате, в том числе в выходной (точка, а не
интервал); последователь по FS начинается не раньше следующего рабочего дня.

## 2. Время и календарь

- Даты задач — `YYYY-MM-DD` в часовом поясе проекта; события и аудит — UTC с offset.
- Обычная задача занимает **полуоткрытый** интервал `[start_date, end_exclusive)`. `duration_workdays` = число
  рабочих дней внутри (Пн–Пт, праздников нет — их не выдумываем). В ответе есть `last_day` — последний занятый
  рабочий день (включительно); **UI показывает его**, а не `end_exclusive`.
- Даты хранятся канонически: начало — рабочий день, конец — следующий день после последнего рабочего
  (`[Сб, Вт)` → `[Пн, Вт)`, `[Пт, Пн)` → `[Пт, Сб)`). Набор рабочих дней не меняется. Интервал без рабочих дней
  отклоняется (`no_workdays`).
- Веха — точка: `start_date == end_exclusive`, длительность 0, рисуется ромбом на границе дня.
- `due_date` — отдельный **включительный** дедлайн; планировщик его не меняет, только предупреждает.
- Незапланированная задача: `start_date = end_exclusive = null`; частично заданная пара отклоняется (`partial`).
  Ни одно действие не придумывает даты.
- FS, лаг 0: `start_B ≥ next_workday(end_exclusive_A)`. Пример (тест): A = пт 2026-11-27, 1 день →
  `[2026-11-27, 2026-11-28)`, B после A — не раньше пн 2026-11-30. Пн 2026-11-30 + 2 рабочих дня → конец ср 2026-12-02.
- `today` (просрочка) — дата в часовом поясе проекта. `overdue`: не `done` и `due_date < today`. `late`: не `done` и
  последний день плана (у вехи — её дата) раньше `today`.

## 3. Планирование

**Инварианты на запись.** Граф FS — DAG (цикл → `422 dependency_cycle` с путём `cycle_keys`); зависимость в одном
проекте, не на себя, не дубль, не между задачей и её предком/потомком, не на архивную задачу. Прямое изменение дат
(`PATCH`) не может создать новое нарушение FS (`422 schedule_conflict`, `fs_violation`) и не меняет закреплённые
даты (`task_locked`; снять закрепление можно в том же запросе). Зависимость, которую текущие даты уже нарушают,
`POST …/dependencies` не создаёт (`dependency_violated`) — её добавляют через предпросмотр (`add_dependencies`),
который заодно сдвигает зависимые. Так каждый путь записи сохраняет «FS выполнены для запланированных задач»;
Гант всё равно вычисляет `violations` (защита для старых данных) и умеет их устранить (`resolve_violations`).

**Алгоритм** (`app/work/scheduler.py`, чистые функции): топологический порядок Кана с ключом (номер, id) —
детерминированный; затем один проход вперёд по затронутым задачам:

- `shift_successors` — запрошенные задачи получают новые даты, все достижимые по FS последователи сдвигаются
  **только вперёд** ровно на ближайший допустимый старт с сохранением длительности; независимые ветки не трогаются;
  в ромбе A→B, A→C, B→D, C→D задача D двигается один раз на максимум ограничений;
- `only_this_task` — меняются только запрошенные задачи; нарушение у последователя — конфликт `successor_violation`;
- `resolve_violations` — без запроса: сдвинуть вперёд всё, что сейчас нарушает FS.

Конфликты (apply запрещён): `task_locked` (запрошена закреплённая), `locked_successor` (закреплённой пришлось бы
сдвинуться), `requested_violates_predecessor`, `successor_violation`. Предупреждения (нужно `accept_warnings`):
`due_date_exceeded`. `blocked_tasks`: `unscheduled` (нет дат — расчёт для неё остановлен) и
`predecessor_unscheduled` (ограничение от предшественника без дат не учтено; известные ограничения применяются).
Сложность O((V+E) log V). CPM/критический путь — P1: `critical_path` всегда `null`, флаг `features.critical_path =
false` — ложный критический путь не показывается.

**Preview → apply.** `POST /api/projects/{id}/schedule/preview` ничего не меняет в задачах, проекте и аудите (пишет
только запись предпросмотра) и возвращает `operations` (before/after, `shift_workdays`, причина, `because_of`,
версия задачи), `conflicts`, `warnings`, `blocked_tasks`, `unchanged`, `can_apply`, `base_plan_revision`,
`expires_at`. `POST …/schedule/apply` с `{preview_id, expected_plan_revision, client_request_id, accept_warnings}`
в одной транзакции `BEGIN IMMEDIATE`: идемпотентный повтор (тот же ключ → прежний ответ, `replayed: true`, без
второго аудита) → предпросмотр свой, не истёк, не применён → `plan_revision` проекта совпадает → расчёт заново по
текущему состоянию, хэши входа и результата совпадают → нет конфликтов, предупреждения приняты → запись дат с CAS
по версии каждой задачи, аудит `schedule_applied` (correlation = preview id), `plan_revision + 1` (только если
что-то меняется: пустой предпросмотр применяется без новой ревизии — чужие предпросмотры не устаревают «молча»),
отметка применения, запись idempotency. Родителя задачи можно указать ключом (`PKY-1`) или id; хранится id. Любая ошибка откатывает всё (тест M6-18 с отказом после второй записи). Ответы:
`409 stale_schedule` (`plan_revision`, `snapshot_changed`, `expired`, `already_applied`, `task_changed`) — UI просит
повторить предпросмотр; `422 schedule_conflict` (`conflicts`, `warnings_not_accepted`).

**plan_revision** растёт при каждом изменении задач, зависимостей, расписания и часового пояса проекта; списки,
Гант и карточка проекта возвращают её — все представления видят одно состояние (M6-36), а предпросмотр применяется
только к тому состоянию, по которому посчитан.

## 4. Идентичность и права

Два уровня, оба на сервере; ни один не читает роль, actor или user id из тела, query или заголовков запроса
(тела строгие, `extra="forbid"`: `created_by`, `role`, `version`, `is_demo` → 422).

1. **Глобальный** `AuthorizationPolicy` (`app/authz.py`): новые действия `view_projects`, `view_tasks`,
   `manage_project`, `create_task`, `edit_task`, `schedule_task`, `view_work_audit`, `propose_work`,
   `apply_work_proposal`; каждый маршрут объявляет ровно одно (тест).
2. **Проектный** `WorkAccessGate` (`app/work/permissions.py`):

| Режим | Когда | Права |
|---|---|---|
| `local_operator` | `AUTH_MODE=local_demo` (loopback, проверки старта), нет публичной экспозиции | один оператор, заданный сервером (`local-demo-user`), читает и пишет. Ролей команды **нет** (`members: []`, подпись «Локальная демонстрация — один оператор»); исполнители — сам оператор и вымышленная демо-команда «(демо)» (3 аналитика, руководитель проекта, 2 разработчика), не учётные записи |
| `read_only` | `WORK_PUBLIC_EXPOSURE=true` (ставит `docker-compose.claude-public.yml`), запрос с заголовком шлюза `X-SKH-Exposure` (ставят `deploy/claude-test/Caddyfile*`) или `WORK_WRITES_ENABLED=false` | только `view_projects`/`view_tasks`: синтетический снимок для показа. Нет записей задач, нет приватного аудита, нет AI-предложений; `403 forbidden` с `details.mode = read_only` и причиной. Единственное исключение — `shared_login` ниже (решение владельца) |
| `shared_login` | `WORK_PUBLIC_EXPOSURE=true` **и** `WORK_SHARED_LOGIN_WRITES=true` (по умолчанию `false`), запрос через шлюз с логином (`X-SKH-Exposure: public-login`, `Caddyfile.login`) или с loopback без маркера (SSH-туннель); `WORK_WRITES_ENABLED=false` по-прежнему отключает запись | тот же единственный оператор `local-demo-user`, что и в `local_operator`: читает и пишет, видит аудит, запускает «AI план». Подпись «Демо-стенд — общий вход, один пользователь». Запрос по открытой ссылке (`public`) или с любым другим маркером — `read_only` |
| `membership` | идентичность от настоящего провайдера (`Container.identity`, шов для SSO), `AUTH_MODE≠local_demo` | `ProjectMember`: viewer — чтение; member — + задачи, расписание, аудит, предложения; admin — + настройки проекта. Не участник — проект и его задачи **невидимы** (`404`, без названий и счётчиков). Демо-оператор в этом режиме ничего не может |
| `disabled` | `TASK_SYSTEM=disabled` | `503 feature_unavailable` |

Почему так: публичный шлюз тестового стенда переписывает `Host` на `127.0.0.1`, и backend не отличает внешний
запрос от локального; общий пароль Basic Auth не идентифицирует человека. Поэтому экспозиция объявляется явно
(переменная окружения в overlay + маркер шлюза, который может только **ограничить** доступ).

**Общий вход демо-стенда — отклонение от спецификации M6 (решение владельца, 2026-11-25).** Спецификация требует,
чтобы по общей ссылке задачи были только для просмотра: общий пароль не определяет человека. На личном демо-стенде
владелец разрешил запись одному общему суперпользователю, под которым команда заходит смотреть и тестировать
функционал. Последствия, принятые осознанно: все, кто входит по этому логину, — **один** пользователь
(`local-demo-user`); история изменений и аудит не различают людей; любой, кто знает пароль, может менять и
архивировать задачи и запускать «AI план» (расходует подписку Claude стенда). Границы: только за логином
(`Caddyfile.login` ставит `public-login`; открытый `Caddyfile` ставит `public` — там по-прежнему только просмотр),
только при явном `WORK_SHARED_LOGIN_WRITES=true` в env-файле стенда, только синтетические данные. Это не командный
режим (`team_ready` остаётся `false`) и не подходит для корпоративного контура — там нужен `membership` с настоящей
идентичностью.

**Team-ready gate** (не выполнен, `team_ready: false` в `GET /api/work/capabilities`): нужен реальный
`IdentityProvider` (SSO) в `Container.identity`, политика RBAC вместо `LocalDemoPolicy`, управление участниками
проекта (API не открыт, пока нет каталога пользователей) и E2E нескольких пользователей в разрешённом shared
runtime. Сегодня `AUTH_MODE=sso` не запускается, режим `membership` проверен только тестовой server-side
идентичностью (`tests/support/work_identity.py`, M6-19/M6-37).

## 5. Хранение, миграции, резервная копия и откат

- **Отдельный файл** `workspace/work.sqlite3` (`WORK_STATE_PATH`), а не таблицы в `app_state.sqlite3`: своя история
  миграций, свой backup/restore, неудачная миграция M6 не может задеть предложения, discovery и реестр шаблонов
  (прецедент — `publications.sqlite3`). Стек тот же: stdlib `sqlite3`, без ORM и новых зависимостей.
- **Миграции** (`app/work/migrations.py`): упорядоченные, только добавляются; каждая — одна транзакция с
  `PRAGMA user_version` и строкой в `work_schema_migrations` (имя + checksum). При старте: база новее приложения →
  отказ; изменённая выпущенная миграция (checksum) → отказ; после миграции проверяются таблицы и
  `foreign_key_check`. Несколько процессов: повторная проверка версии под write-lock.
- **Соединения**: одно на единицу работы; запись — `BEGIN IMMEDIATE` (один писатель, `busy_timeout` 10 с), чтение —
  снимок в WAL. `PRAGMA foreign_keys=ON` всегда. WAL — для параллельности, не вместо транзакций.
- **PostgreSQL**: доменная логика без SQLite-специфики (нет `INSERT OR REPLACE`, JSON1; даты ISO-текстом, id из
  приложения, рекурсивный CTE стандартный). Для порта меняются: `AUTOINCREMENT` → identity, триггеры append-only →
  функция-триггер или `REVOKE UPDATE, DELETE`, `user_version` → только таблица миграций. Отдельная реализация не
  делалась.
- **Версии схемы**: v1 `work_core` (шаги 1–2), v2 `task_document_links` (индексы связей, шаг 4), v3 `work_ai_proposals`
  (шаг 5). Проверка копии (`verify`) сверяет таблицы с ВЕРСИЕЙ копии, поэтому копия, снятая до обновления, остаётся
  пригодной для отката (тест `test_v1_database_upgrades_to_task_links_with_a_backup`).
- **Backup до миграции**: если база существует и есть новые миграции — `work.sqlite3.pre-v<N>-<UTC>.bak` через online
  backup API (включает содержимое WAL). Вручную: `python -m app.tools.work_db backup --out FILE`, проверка
  `verify`, состояние `status`.
- **Откат**: остановить backend → `python -m app.tools.work_db restore --from FILE --yes` (проверяет копию, сохраняет
  текущую базу рядом, удаляет `-wal/-shm`) → запустить предыдущую версию приложения (pin SHA). Миграции аддитивны,
  поэтому старая версия с восстановленной копией работает. Проверено тестом (`test_work_db.py`).
- **Docker**: база в томе `workspace` (`/data/workspace`), переживает перезапуск и пересборку (M6-21); корень
  контейнера read-only — в образ ничего не пишется.

### 9.1 Виды

- **Список** — дерево задач (до 4 уровней) таблицей без `<select>` в строках (Планировщик v2): Задача (ключ, веха,
  название, серые метки «ждёт ARIS-6» и число документов), Статус, Исполнитель, Приоритет, Сроки (начало – последний день,
  включительно), Срок сдачи (включительный дедлайн), «⋯». Ячейка — текст; клик или Enter открывает меню (статус — клавиши
  1–4, исполнитель, приоритет) или календарь (сроки, срок сдачи). «Группировка» (по статусу, исполнителю, приоритету) —
  плоский список под заголовками групп, подзадачи отмечены ↳; «Вид» скрывает колонки. Ниже — как было до v2. Свернуть / развернуть
  ветку — кнопка у задачи (`aria-expanded`). Отметки — словом и формой: «Веха» (ромб), «Ждёт ARIS-6», «Просрочена (срок …)»,
  «Отстаёт от плана», «Сроки закреплены» (замок). Правка на месте без перезагрузки: название (карандаш → поле, Enter
  сохраняет, Esc отменяет), статус / исполнитель / приоритет (списки), начало / последний день / срок (кнопка → поле
  даты). Каждая правка — `PATCH /api/tasks/{id}` с `expected_version`; простые поля показываются сразу и откатываются при
  ошибке (с текстом сервера); даты ждут ответа (их приводит к календарю сервер). `409 stale_task` — данные
  перечитываются и сказано «ARIS-4 уже изменили в другом месте… повторите правку». Если новые даты нарушают FS
  (`422 schedule_conflict`, `fs_violation`), открывается предпросмотр «сдвинуть зависимые» — тихого отказа нет. На
  телефоне строки — карточки (подписи полей над значениями). Рисуется по 200 строк, дальше «Показать ещё».
- **Доска** — колонки «К работе / В работе / На проверке / Готово» со счётчиками; карточка: ключ, приоритет (полоски +
  текст для экранного диктора), название, исполнитель, срок / «Просрочена», «Ждёт …», число подзадач и документов.
  Перетаскивание указателем (мышь, перо, сенсор на устройствах с точным указателем): порог 4 px, карточка едет
  CSS-трансформацией раз в кадр (`requestAnimationFrame`, без рендера React на каждый кадр), колонка под указателем
  подсвечена. Без перетаскивания (WCAG 2.5.7): меню «Сменить статус» на карточке и Alt + ← / → на карточке (фокус
  следует за ней). Статус сохраняется `PATCH` с версией; при отказе карточка возвращается и сказано почему.
- **Гант** — см. §9.2. На телефоне — та же шкала без перетаскивания (кнопка задачи открывает её карточку, сроки
  меняются формой — спецификация 03 §6 это допускает).
- **Карточка задачи** (панель / страница): название, статус, исполнитель, приоритет, срок; «Сроки» — план, длительность в
  рабочих днях, «Закрепить сроки», форма «Изменить сроки» / «Запланировать» (начало + последний день; у вехи — одна
  дата) → «Показать последствия» → предпросмотр прямо в карточке → «Применить»; «Снять даты» возвращает задачу в
  «Без дат». Описание — Markdown через общий безопасный рендерер (`AnswerMarkdown`, HTML — текстом). Подзадачи и
  «Добавить подзадачу». Зависимости FS: «Начнётся после» / «После неё начнутся», «Убрать» (`DELETE` с
  `expected_plan_revision`), добавление (роль + задача); цикл — `422 dependency_cycle`, показывается путь сервера
  `cycle_keys` («Цикл: ARIS-5 → ARIS-6 → ARIS-5»); зависимость, которую нарушают текущие даты, предлагается добавить
  через предпросмотр (`add_dependencies`, зависимые сдвигаются). «Документы» — шов шага 4 (ниже). История: кто, когда,
  что (поле: было → стало; описание — только «изменено»), «Показать раньше». Архив — с подтверждением (вместе с
  подзадачами, зависимости убираются, история остаётся).
- **Создание**: «Задача» (одна основная кнопка вида) и «Добавить подзадачу» открывают форму: название, родитель,
  статус, приоритет, исполнитель, сроки («Без дат» / «Начало и длительность» / «Веха»), срок. Ключ идемпотентности на
  форму. После создания открывается созданная задача. «Создать проект»: ключ (латиница, не меняется), название,
  описание, даты.

### 9.2 Гант: подход и взаимодействие

**Свой SVG, а не библиотека.** Проверено 24.11.2026 в реестре npm (`npm view … license version`): `frappe-gantt` 1.2.2
— MIT; `gantt-task-react` 0.3.9 — MIT, но peer `react ^18` (здесь React 19) и последняя публикация 2022 г.;
`@svar-ui/react-gantt` 2.8.3 — MIT. Лицензии совместимы, но решили не по лицензии: (1) контракт шага 2 —
предпросмотр до применения, полуоткрытый `[start, end_exclusive)`, календарь Пн–Пт, веха-точка, пул «без дат»,
закреплённые сроки — требует полного контроля над тем, когда и что меняется; библиотеки фиксируют изменение по
отпусканию и хранят своё состояние, которое пришлось бы откатывать; (2) нужна клавиатурная альтернатива сдвигу и
длительности (WCAG 2.5.7) — её всё равно писать самим; (3) один набор токенов и тёмная тема (03 §6: не вводить второй
дизайн-систему); (4) нет новой зависимости в банковском контуре; (5) прецедент — карта знаний (`GraphCanvas.tsx`).
Возможности библиотек (зум, виртуализация) по их документации в этой сессии не перепроверялись — решение от них не
зависит.

- Слева — дерево задач (липкая колонка, сворачивание как в списке), справа — шкала: месяцы и дни / недели / месяцы
  (Планировщик v2: масштабы «День / Неделя / Месяц / Квартал / Год» = 36 / 16 / 5 / 1,8 / 0,62 px на день и «Вписать»,
  Ctrl/⌘ + колесо — плавно 0,5–48 px на день вокруг указателя; шкала из двух рядов подбирает единицы по ширине ячейки;
  середина окна сохраняется; фиксированный масштаб открывается на сегодня на 30 % ширины, ещё не начатый проект — на
  его начале, законченный — с концом на 70 %), выходные затенены (от 10 px на день), сегодня —
  вертикальная линия (граница дня; при зуме «Дни» ещё и подсветка колонки), «Сегодня» прокручивает к ней. Ряд
  фильтров всегда одна строка: если элементы вида не помещаются (по ширине самого ряда), масштаб становится меню, а
  «Вписать» и «Сегодня» — иконками.
- Полоса = `[start_date, end_exclusive)`: кончается на границе после `last_day` (тест M6-26). Статус — формой:
  контур (к работе), заливка (в работе), фиолетовая заливка (на проверке), серая с галочкой (готово); «отстаёт /
  просрочена» — красный контур; закреплённая — замок и не перетаскивается; веха — ромб на границе дня; срок (`due_date`,
  включительно) — флажок в конце дня. Стрелки FS — от конца предшественника к началу последователя; нарушенная
  (`violations`) — красный пунктир; наведение выделяет стрелку и показывает «A → B». Задачи без дат на шкалу не
  попадают — секция «Без дат» под диаграммой (даты не придумываются, M6-27).
- **Перетаскивание** полосы — сдвиг, правого края — длительность (порог 4 px, шаг — день). Призрак рисуется по тому же
  календарю, что у сервера (начало в выходной → понедельник, длительность в рабочих днях сохраняется), прямо в DOM раз
  в кадр. На отпускании **ничего не пишется**: `POST …/schedule/preview` (`shift_successors`; сдвиг — `start_date` +
  `duration_workdays`, изменение длительности — `start_date` + `end_exclusive`, веха — `duration_workdays: 0`).
- **Клавиатура** (WCAG 2.5.7): полоса в фокусе — ← / → сдвиг на день, Shift + ← / → длительность, Enter —
  предпросмотр (или открыть задачу, если ничего не сдвинуто), Esc — отменить; новые даты объявляются в live-регионе.
  Альтернатива для всех — форма сроков в карточке задачи.
- **Предпросмотр** (лист справа; в карточке задачи — внутри неё): «Ничего не изменится, пока вы не нажмёте
  «Применить»», выбор «Сдвинуть зависимые / Только эта задача» (пересчёт на сервере), «Запрошено» и «Сдвинутся

## 10. Связи задач с документами (шаг 4)

**Модель.** Связь хранит стабильный id документа SKH и ревизию, которую сервер видел при связывании
(`revision_at_link`); заголовок, статус, версия и доступ читаются при КАЖДОМ запросе из снимка знаний читателя
(`KnowledgeService.snapshot(user)` — репозиторий является границей доступа, как для ссылок и графа документов).
`app/api/work.py` разрешает снимок один раз на запрос и кладёт его в `WorkPrincipal.documents` (`DocumentScope`,
`app/work/links.py`); сервис задач работает синхронно поверх него. Параллельного хранилища документов нет.

| Состояние | Когда | Что видно |
|---|---|---|
| `current` | документ виден, ревизия совпадает с записанной | id, название, статус, версия, ревизия |
| `revision_changed` | документ виден, ревизия другая | то же + «Документ изменён после связывания: ревизия a → b» |
| `revision_unknown` | ревизия при связывании не записана | то же + предложение отметить проверенным |
| `unavailable` | документа нет в снимке читателя: удалён, переименован или нет доступа — **неразличимо намеренно** | только «Документ недоступен — удалён или нет доступа»; ни id, ни названия, ни ревизии, ни цитаты |
| `unverified` | источник знаний сейчас не читается | ничего о документах; задача работает |

Флаги `deprecated` и `approved` — по текущему статусу документа (устаревший показывается, а не скрывается;
черновик — «не авторитетный»). `TaskOut.link_count` и `document_ids` считают **только видимые читателю документы**
(`null` — проверить сейчас нельзя), поэтому скрытый документ не проявляется ни в счётчике карточки Доски, ни в фильтре.
История (`activity`) называет документ связи только если читатель его видит («Документ: недоступен» иначе).

**Связь — не ребро графа знаний.** Задача — не документ: связь живёт в модуле «Работа», не пишет YAML, не создаёт
типизированных отношений между документами и не трогает текст документа (тест `test_links_add_no_graph_edge…`).
«Проекция рядом с графом» — это раздел «Задачи» на странице документа и `GET /api/documents/{id}/tasks`.

**Маршруты** (`docs/API_CONTRACTS.md` v0.8): `GET/POST /api/tasks/{id}/links`, `DELETE …/links/{link_id}` (удаление по
id — в том числе недоступной связи), `POST …/links/{link_id}/acknowledge` (человек проверил изменённый документ: связь
записывает текущую ревизию; сервер сам этого не делает), `GET /api/projects/{id}/documents` (документы проекта для
фильтра, с числом задач и изменённых связей), `GET /api/documents/{id}/tasks` (обратные ссылки; `404`, если документ
не виден), фильтр `document` в `GET /api/projects/{id}/tasks`. Связывание: документ должен быть виден СЕЙЧАС
(иначе `404 not_found` — тот же ответ, что для несуществующего), дубль активной связи — `409 conflict link_exists`,
архивная задача — `409 task_archived`, источник знаний недоступен — `503 knowledge_unavailable`. Связь не меняет
версию задачи и `plan_revision` (она не часть плана; видимость документа и так меняется без изменений в задачах).

**Права.** Чтение — `view_tasks`, изменение — `edit_task` (в режиме только для просмотра — `403`). В `membership`
обратные ссылки документа берутся только из проектов, где читатель — участник с правом чтения; чужие проекты не
показываются и не считаются. Внешние ссылки (Confluence/GitLab, `target_type = external`) в P0 не создаются — P1.

**UI.** Карточка задачи → «Документы»: связь (Реализует / Опирается на / Документирует / Проверяет / Блокирует),
ссылка на документ, статус, версия, отметки состояния, «Проверено» (подтвердить новую ревизию), «Убрать»,
«Связать с документом» (поиск по ID или названию среди доступных документов). Страница документа → вкладка «Связи» →
раздел «Задачи» со ссылками на `/tasks/KEY` и «Задачи проекта … по документу» (`/projects/KEY?doc=ID`). Фильтр
«Документ» (`?doc=ID`) одинаково сужает Список, Доску и Гант. Без модуля задач раздел на странице документа не
показывается.

## 11. AI (шаг 5): `work_inspect` и «AI план»

**`work_inspect`** — один узкий read-only инструмент в существующем цикле M5.7 (`SystemToolExecutor`, тот же
протокол, лимиты раундов/вызовов/времени/размера). Операции: `list_projects`, `list_project_tasks` (фильтры статуса,
просрочки, отставания, ожидания, вех, дат, текста), `get_task`, `get_dependencies`, `get_project_schedule` (сводка
плана: просрочка, отставание, ожидание предшественников, без дат, нарушенные зависимости, ближайшие вехи; критический
путь не считается). Аргументы — только ключи (`ARIS`, `ARIS-12`); полей пользователя, роли или области нет (лишнее
поле → отказ). Выполняется через `WorkService` с серверной идентичностью в самой строгой трактовке шлюза (только
чтение); чужой проект в `membership` — `not_found` и не считается. Результат — системный факт `skh_work` с ревизией
плана в фильтрах; текст задач — данные (инъекции скрываются, описание обрезается). Предлагается модели, только если
модуль включён и политика разрешает `view_tasks`. Записывающего инструмента в цикле нет. Политика ассистента
`TOOL_POLICY` v4: статус и риски — только из этих фактов, без выдуманных исполнителей, сроков и зависимостей.

**«AI план»** — типизированное предложение плана задач (`app/work/ai.py`):

1. `POST /api/work-ai/proposals {project_id, request, document_ids ≤ 5, start_date?, parent_task_id?}` → шлюз
   `propose_work` ДО любого вызова модели (только просмотр, viewer, не участник — модель не вызывается) → провайдер
   умеет планировать? (необязательная возможность `plan_work`: `internal_api` и `claude_cli`; у `mock`/`disabled`
   её нет — `503 feature_unavailable`, кнопки в UI нет) → документы видимы (или сервер берёт утверждённые по
   запросу; ничего не найдено — `422 no_sources`) → тексты документов с вырезанными инъекциями, ограничены по объёму.
2. Модель возвращает JSON (`app/adapters/ai/work_protocol.py`, без привязки к вендору): задачи с локальными id,
   оценками, подзадачами, зависимостями FS, источниками с цитатами, допущениями. Ответ не той формы — не JSON,
   контейнер не того типа (`tasks`/`dependencies`/`sources` не список, зависимость не объект из двух строк,
   `parent_local_id` не строка), `local_id` вне формы правок (`^[A-Za-z0-9_.-]{1,32}$`, например «т1» или «t 1») —
   это сбой ответа модели, а не запроса: `502 ai_invalid_response` с понятным сообщением «повторите запрос», с
   `request_id` и без трассировки; ничего не сохраняется. Неверное начало плана от человека отклоняется **до** вызова
   модели (`422 invalid_date_range`).
3. Сервер проверяет: повтор/неизвестный id, родитель, цикл иерархии, глубина ≤ 4, веха без подзадач, зависимость на
   неизвестную задачу, на себя, между предком и потомком, цикл FS — **весь план отклоняется** (`422 proposal_invalid`,
   ничего не сохраняется, M6-16). Содержательные ошибки нейтрализуются и видны человеку (M6-33): исполнитель, даты и
   id от модели отбрасываются; источник вне переданных документов отбрасывается; цитата, не найденная дословно,
   отбрасывается (ссылка на документ остаётся как неподтверждённая); нет оценки — задача без дат; похожая существующая
   задача отмечается. **Даты считает сервер** (Пн–Пт, FS) от выбранного начала; без начала задачи без дат.
4. Предложение сохраняется со статусом `suggested` и основанием: `base_plan_revision`, ревизии источников, провайдер,
   схема `work_plan.v1`, срок действия 24 ч; аудит `proposal_created`. В задачах ничего не меняется (M6-13).
5. Проверка человеком (`GET`, `POST …/preview` — пересчёт без записи): оставить/убрать задачу, название, описание,
   приоритет, оценка, исполнитель из справочника, убрать зависимость, начало. Добавить задачи или зависимости нельзя.
6. `POST …/apply {expected_plan_revision, client_request_id, правки}` — ОДНА транзакция (`WorkService.apply_task_plan`):
   идемпотентный повтор → предложение своё и `suggested` → ревизия плана, срок, ревизии и видимость источников
   совпадают (иначе `409 proposal_stale`: `plan_changed`, `source_changed`, `source_unavailable`, `expired`;
   устаревшее не применяется молча) → задачи (настоящие id и ключи вместо локальных), зависимости FS, связи с
   подтверждёнными источниками (`implements`, ревизия основания), аудит с `proposal_id`, один рост `plan_revision`,
   статус `applied`. Любая ошибка откатывает всё (M6-18). `POST …/reject` — только статус (M6-15).

Предложение личное (видит и применяет только автор, как предпросмотр расписания). Промпт и тексты документов не
сохраняются; хранится запрос пользователя, план и цитаты ≤ 300 символов. Модель не может назначить исполнителя,
поставить дату, выбрать id задачи, утвердить документ, вызвать инструменты или записать что-либо.

**UI.** Кнопка «AI план» рядом с «Задача» — только при `features.ai_proposals` и праве записи; лист запроса (что нужно,
документы, начало) → проверка предложения (`?proposal=WAP-…` в адресе): источники со статусами, допущения, «Проверка
сервера», задачи с правкой, зависимости, даты сервера → «Создать задачи (N)» / «Отклонить»; устаревшее —
«Подготовить заново». В чате (`/ask`) факты `work_inspect` показываются карточками «По данным модуля «Работа» SKH»
со ссылками на задачи.

**Без AI.** `AI_PROVIDER=mock|disabled`: проекты, Список, Доска, Гант, планирование, связи работают; «AI план» нет;
`POST /api/work-ai/proposals` → `503 feature_unavailable`; цикл инструментов с mock не запускается (mock не изображает
модель — решение владельца). Тесты модельных сценариев — скриптовый двойник `tests/support/scripted_model.py`.

  задач падает с 241 до 49 запросов/с при 10 клиентах; то же на коде шага 3 (29 запросов/с), то есть это не регрессия
  шагов 4–5 (они добавляют ≈ 0,3 мс на запрос — разрешение снимка знаний). P1: несколько процессов uvicorn (SQLite WAL
  это допускает) и/или кэш производных полей по `plan_revision`.

## 13. Обзор безопасности (шаги 4–5)

| Риск | Мера | Проверка |
|---|---|---|
| Утечка скрытого документа через связи, счётчики, фильтр, историю, обратные ссылки | всё — по снимку читателя на каждый запрос; недоступное без id/названия/ревизии; `link_count`/`document_ids` только по видимым; история редактируется | `test_m6_12_m6_37…`, `test_m6_34…`, work-eval `links-hidden` |
| Утечка чужого проекта через AI-инструмент | `work_inspect` идёт через шлюз проекта, ключи только, нет полей субъекта | `test_m6_37_m6_39…` |
| AI-запись без подтверждения | в цикле нет инструмента записи; план — предложение; apply — явный POST с ревизией плана и идемпотентностью | `test_m6_13…`, `test_m6_14…`, `test_m6_15…` |
| Вызов модели с публичной ссылки / без прав | шлюз `propose_work` до провайдера; в режиме только для просмотра — 403 | `test_m6_20…` (модель не вызвана), `test_m6_19_m6_37…` |
| «Галлюцинации» модели | исполнитель/даты/id/чужие источники отбрасываются; цитаты проверяются дословно; структура проверяется сервером | `test_m6_33…`, `test_m6_16…` |
| Устаревшее основание | `409 proposal_stale` по ревизии плана, ревизиям и видимости источников, сроку | `test_m6_34…`, `test_plan_change_and_expiry…` |
| Инъекции в тексте задач и документов | тексты — данные; инъекционные фрагменты скрываются в результатах инструмента и в источниках плана | `test_task_text_is_data…` |
| Частичная запись | одна транзакция, откат при ошибке в середине | `test_m6_18_failure_during_apply…` |
| Перегрузка | лимиты: ≤ 5 документов, запрос ≤ 2000, ≤ 30 задач и 60 зависимостей, таймауты провайдера и цикла | схемы, `test_documents_must_be_visible…` |

серверной идентичностью; ограничения частоты запросов на AI-маршрутах нет (в проекте нет стандартного middleware);
ответ модели в продуктиве (GigaChat) не проверялся — только скриптовый двойник.
