# Semantic Knowledge Hub — что реализовано

Сводный документ по состоянию приложения на **2026-11-23**: вехи M0–M5, включая M4.6 (создание документов),
M4 Integration Readiness и M5 (публикация в Confluence Data Center). Документ собирает в одном месте то, что
разнесено по `docs/`; подробности — по ссылкам в конце каждого раздела.

> **Статус.** Рабочее однопользовательское приложение на синтетических данных. Все внешние интеграции
> (GitLab, Confluence MCP, Confluence DC REST) реализованы и проверены **только на локальных тестовых дублях**.
> С реальными корпоративными системами соединений не было. Приложение **не готово к промышленному
> использованию** — см. раздел 11.

Код: ветка `feature/m4-m5-knowledge-workflow` (локальные коммиты, в удалённый репозиторий не отправлялись;
`main` не менялся).

## 2. Назначение и границы систем

Приложение — база знаний для команды семантического слоя: навигация по документам, поиск, ассистент,
управляемое создание и изменение документов через ревью и публикация утверждённых документов в Confluence.

| Система | Роль | Что приложение с ней делает |
|---|---|---|
| **GitHub** (этот репозиторий) | Только код приложения, тесты и синтетические примеры | — |
| **GitLab** (отдельный репозиторий) | Каноническая база знаний: Markdown + YAML, история, ревью | Читает документы; изменения — только через ветку и Merge Request |
| **Confluence Data Center** | Корпоративная документация и витрина опубликованных документов | Читает через утверждённый MCP (только чтение); публикует утверждённые документы через REST отдельным токеном |
| **Внутренняя модель / GigaCode** | Будущий AI-провайдер | Подключается через адаптер `AIProvider`; сейчас работает детерминированный демо-провайдер |
| **Система задач** | Внешняя, не определена | Показывается как «Не подключено»; задачи и сроки не выдумываются |

В офлайн-демо база знаний — 9 синтетических документов из `fixtures/knowledge`, которые при первом запуске
копируются в игнорируемый git каталог `workspace/`.

## 3. Возможности для пользователя

Интерфейс на русском языке, идентификаторы в API и коде — на английском. Экраны: главная, каталог, документ,
«Спросить», «Создать документ», предложения, страница задания публикации, «Интеграции», просмотр
корпоративной страницы.

### 3.1. Каталог, поиск и документ
- Полнотекстовый поиск (SQLite FTS5) по заголовку, тексту, тегам и связанным сущностям, с выдержками и
  подсветкой.
- Фильтры по статусу, владельцу, источнику и тегам, сортировка.
- Видно, если у документа нет владельца, просрочен пересмотр или устарел индекс.
- Страница документа: безопасно отрисованный Markdown и «Паспорт документа» — статус, владелец, ревизия,
  `source_uri`, источник (`local` / `gitlab` / `confluence`), теги, связанные документы.
- Отдельный список файлов, которые не прошли проверку схемы и поэтому не попали в каталог.
- Синтетические документы помечены «Демо-данные».

### 3.2. Ассистент
- Отвечает только по найденным источникам. Каждая цитата проверяется на сервере по набору извлечённых
  фрагментов и ведёт к разделу документа.
- Демо-провайдер (`AI_PROVIDER=mock`) строго извлекающий: собирает ответ из дословных выдержек. Если данных
  нет, честно отвечает «Недостаточно данных».
- Черновики и устаревшие документы по умолчанию исключены из доказательной базы и показаны отдельно; их можно
  включить переключателем «Учитывать черновики».
- Корпоративные страницы Confluence (демо-набор или MCP) показаны с пометкой источника.
- Текст источников передаётся модели как данные, а не как инструкции.
- Для внутренней модели есть адаптер OpenAI-совместимого API (`internal_api`); на реальном endpoint он не
  проверялся.

Подробнее: `docs/ARCHITECTURE.md` §5, `docs/SECURITY.md`.

### 3.3. Создание документа (M4.6)
Кнопка «Создать документ» есть на главной, в каталоге и на странице предложений. Порядок работы:
1. Выбрать способ: «Вручную» или «С помощью AI».
2. Выбрать тип документа (шаблон).
3. Заполнить форму метаданных.
4. Работать в Markdown-редакторе с панелью форматирования и предпросмотром.

Возможности:
- **Шаблоны.** Пять шаблонов: архитектура, интеграция, бизнес-сущность, архитектурное решение (ADR), процесс
  команды. Шаблон — это Markdown-файл с YAML-заголовком в `backend/app/document_templates/` или в каталоге
  `DOCUMENT_TEMPLATES_DIR`. Новый шаблон добавляется новым файлом, без изменения кода интерфейса.
- **Метаданные.** YAML-заголовок документа генерирует приложение из полей формы, вручную его никто не пишет.
  ID и путь к файлу предлагаются автоматически.
- **Черновик.** Хранится на сервере и переживает перезагрузку страницы и перезапуск контейнера. Есть
  «Сохранить», «Удалить» с подтверждением, «Проверить» и «Отправить на ревью».
- **Защита от потери правок.** Если черновик сохранили в другой вкладке, сохранение отклоняется с ответом 409,
  а текст остаётся в редакторе.
- **Уникальность ID и пути.** Проверяется по базе знаний, по незавершённым предложениям и ещё раз свежим
  запросом к источнику перед ревью и отправкой. При конфликте введённый текст не теряется.
- **Режим «С помощью AI».** Демо-провайдер собирает структуру шаблона и дословные выдержки только из
  утверждённых документов команды; всё остальное помечается «Требует уточнения». Каждая выдержка
  перепроверяется на сервере. Если подходящих источников нет, интерфейс пишет «Недостаточно данных».
  AI-черновик нельзя сразу сделать утверждённым: он проходит обычный путь ревью и MR.

Подробнее: `docs/DOCUMENT_CREATION_WORKFLOW.md`, `docs/DOCUMENT_TEMPLATES.md`, `docs/AI_AUTHORING_CONTRACT.md`.

### 3.4. Предложения изменений и цикл GitLab
- **Создание предложения.** «Предложить изменение» на документе — правка, построчный diff и вид «до/после»,
  проверка метаданных. Для нового документа diff показывает весь файл как добавленный.
- **Два вида операций.** `update` — изменение существующего документа; `create` — новый документ. Обе идут
  одним путём: черновик → «Готово к ревью» → «Отправить в GitLab» → ветка `kb/update/<ID>-<hash>` → один
  коммит (`update` или `create`) → Draft MR.
- **Ревью и merge.** Происходят в GitLab по его правилам. Приложение не пишет в защищённую ветку и не
  подменяет решение ревьюера.
- **После merge.** Статус «Принято (merge)» ставится только после того, как GitLab подтвердил merge. Затем
  приложение синхронизирует базу знаний и поисковый индекс и фиксирует вошедшую ревизию. Если синхронизация
  не удалась, это видно отдельно (`merged_pending_sync`), и её можно повторить.
- **Конфликты.** Если исходный документ изменился после базовой ревизии, предложение получает статус
  `conflict`; ничего не перезаписывается. Для `create` конфликтом считается появление файла или ID.
- **Без повторов вслепую.** Записи в GitLab не повторяются автоматически. Неизвестный результат (таймаут,
  потерянный ответ) разрешается чтением состояния ветки, коммита и MR. Повторная отправка не создаёт второй MR.

Статусы предложения: `draft`, `ready_for_review`, `submitting`, `submitted_to_gitlab`, `merged`, `rejected`,
`conflict`, `submission_failed`. Состояние MR в GitLab хранится отдельно.

Подробнее: `docs/GITLAB_KNOWLEDGE_WORKFLOW.md`.

### 3.5. Публикация в Confluence Data Center (M5)
На странице документа есть блок «Публикация в Confluence», у каждого задания — своя страница.

- **Что публикуется.** Только ревизия, которую GitLab подтверждает как вошедшую через merged MR (запрос
  `GET /projects/:id/repository/commits/:sha/merge_requests`). Публикуются только документы с разрешёнными
  статусами (по умолчанию `approved`).
- **Задание.** После подтверждённого merge и синхронизации задание публикации и предпросмотр создаются сами.
  Сама публикация никогда не запускается автоматически.
- **Предпросмотр (dry-run).** Выполняется только запросами чтения. Показывает действие (создать страницу,
  обновить с версии N до N+1, изменений нет, конфликт), итоговый storage-формат и построчные изменения.
- **Публикация.** Отдельное явное действие. Перед записью план строится заново; если он изменился,
  публикация отклоняется (`409 plan_changed`).
- **Привязка документа к странице.** Хранится в базе приложения и дублируется меткой владельца
  (content property `skh-managed-document`) на самой странице. Пространство и родительская страница берутся
  только из конфигурации; ни один маршрут API не принимает ID страницы; `confluence_page_id` во frontmatter
  игнорируется.
- **Конфликты без перезаписи:**
  - страница изменена вручную в Confluence;
  - страница с тем же заголовком создана не приложением;
  - заголовок занят;
  - привязанная страница удалена;
  - страница перенесена в другое пространство или под другого родителя.
- **Явные действия человека в конфликтах:**
  - «Принять ручную правку» — заново строит предпросмотр, который показывает, что будет заменено;
  - «Создать страницу заново» — если привязанную страницу удалили.
- **Устойчивость:**
  - повторная публикация без изменений не создаёт новую версию;
  - пересериализация storage на стороне Confluence не считается изменением;
  - после потерянного ответа состояние Confluence сначала проверяется (`result_unknown` → сверка), поэтому
    дублей не бывает;
  - у документа одновременно может быть только одно активное задание;
  - задания переживают перезапуск: прерванная публикация переходит в `result_unknown`;
  - ошибка публикации не откатывает merge.
- **Конвертация Markdown в storage-формат.** Заголовки, списки, таблицы, код (code macro с CDATA), ссылки,
  информационная панель с ID, статусом и владельцем. Небезопасные ссылки блокируют публикацию.
  Неподдерживаемое (изображения, диаграммы как код, сырой HTML) публикуется текстом с предупреждением.

Состояния задания: `pending`, `validating`, `dry_run_ready`, `publishing`, `published`, `conflict`, `failed`,
`result_unknown`, `superseded`.

Подробнее: `docs/CONFLUENCE_PUBLISHING_ARCHITECTURE.md`, `docs/CONFLUENCE_MAPPING.md`,
`docs/CONFLUENCE_SYNC_RUNBOOK.md`.

### 3.6. Интеграции и синхронизация
- **Страница «Интеграции».** Для каждой интеграции видны состояние, цель («Не настроено» / «Локально» /
  «Тестовый дубль» / «Реальный сервер»), доступ (чтение / запись) и время проверки.
- **Когда интеграция «Подключено».** Только после реальной проверки:
  - GitLab — проект и ветка;
  - MCP — обнаружение инструментов;
  - Confluence REST — пространство и родительская страница;
  - AI — `/models`.

  Метка «Реальный сервер» не означает, что интеграция прошла live validation.
- **Синхронизация и индекс.** Отдельный блок с кнопкой «Синхронизировать сейчас». Синхронизация с GitLab
  инкрементальная: перечитываются только изменённые файлы. При недоступности GitLab показывается последний
  снимок с пометкой «устарело»; при 401/403/404 кэш сбрасывается.
- **Инструменты MCP.** Сопоставляются по явной конфигурации и сверяются с тем, что сервер реально объявил в
  `tools/list`. Названия инструментов не угадываются.

### 3.7. Экспериментальный провайдер Claude Code CLI (личный тест)
- `AI_PROVIDER=claude_cli`: ответы с проверкой цитат, потоковый вывод (`POST /api/assistant/ask/stream`),
  диалог (история присылается клиентом и не хранится), отмена запроса, AI-черновики документов.
- Claude Code CLI запускается в отдельном контейнере-воркере без инструментов, MCP и доступа к данным
  приложения; backend не получает учётных данных Claude и по-прежнему не имеет выхода в интернет.
- Только для владельца подписки: один оператор, синтетические данные, доступ через SSH-туннель,
  явное подтверждение `CLAUDE_CLI_PERSONAL_USE_ACK=true`. Не корпоративный контур и не замена GigaCode.

Подробнее: `docs/CLAUDE_CODE_CLI_INTEGRATION.md`.

## 4. Как устроено

### 4.1. Компоненты

```text
UI (React + TypeScript + Vite, строгая CSP, без внешних ресурсов)
  │
FastAPI — на каждом маршруте require(Action) → AuthorizationPolicy (LocalDemoPolicy | DenyAllPolicy)
  │
  ├─ KnowledgeService ── KnowledgeRepository: Local | GitLab (REST v4, ревизии = SHA коммитов)
  ├─ SearchService ───── SQLite FTS5 (производный индекс: источник + ревизия на документ)
  │                      CorporateKnowledgeConnector: Disabled | Mock | ConfluenceMCP (только чтение)
  ├─ AssistantService ── AIProvider (mock | internal_api | disabled) + проверка цитат
  ├─ AuthoringService ── шаблоны · генерация frontmatter · проверки ID/пути · AI-черновик с проверкой цитат
  ├─ ProposalService ─── ProposalStore (SQLite) · ProposalPublisher: Disabled | GitLabMRPublisher
  │      └─ подтверждённый merge → синхронизация базы + FTS → merged_revision → хук публикации
  └─ PublicationService ─ PublicationStore (SQLite: задания, привязки, события)
                          render_storage (Markdown → storage) · ConfluencePublisher: Disabled | ConfluenceRESTPublisher
```

Бизнес-логика зависит только от протоколов (`KnowledgeRepository`, `AIProvider`, `ProposalPublisher`,
`ConfluencePublisher`, `CorporateKnowledgeConnector`). Конкретные адаптеры выбирает `app/container.py` по
конфигурации.

### 4.2. Три независимые машины состояний
- **Статус документа** (`draft` / `approved` / `deprecated` во frontmatter) меняется только через merge в GitLab.
- **Статус предложения** (§3.4) описывает путь изменения до merge.
- **Состояние задания публикации** (§3.5) описывает путь до Confluence.

Они никогда не объединяются в один статус: «готово к ревью» не означает MR, а MR не означает утверждения.

### 4.3. Хранилища
Все хранилища — производное состояние приложения. Каноническая база знаний находится в GitLab.

| Файл в `workspace/` | Что хранит | Восстанавливается? |
|---|---|---|
| поисковый индекс (SQLite FTS5) | Индекс документов | Да, из источника |
| `app_state.sqlite3` | Предложения, черновики, аудит без содержимого | Нет — нужна резервная копия |
| `publications.sqlite3` | Задания, привязки документ → страница, события публикации | Нет — нужна резервная копия |

### 4.4. Стек
Python 3.12, FastAPI, Pydantic v2, httpx, SQLite FTS5; React 19, TypeScript, Vite; pytest, Vitest, Playwright;
Docker Compose. Векторной БД, брокера сообщений и фреймворков оркестрации нет. Публикация выполняется
синхронно в запросе, состояние хранится в SQLite (ADR-035).

Подробнее: `docs/ARCHITECTURE.md`, `docs/DECISIONS.md` (ADR-001…038).

## 5. Режимы запуска и интеграции

Переменная `INTEGRATION_PROFILE` задаёт, куда приложению можно обращаться и куда писать. Небезопасная
комбинация не запускается: процесс завершается с кодом 2.

| Профиль | Цели | Запись |
|---|---|---|
| `offline` (по умолчанию) | Никаких: локальный workspace, демо-AI, встроенные синтетические корпоративные страницы | Предложения остаются локально |
| `integration_mock` | Только объявленные тестовые дубли (`MOCK_SERVICE_HOSTS`: loopback, `*.example`, `*.test`, `*.invalid`, `*.localhost`, `<name>-mock`) | В GitLab и Confluence — только в дубли |
| `live_read_only` | Реальные тестовые системы, только `https` | Нет; публикация — только dry-run |
| `live_write_staging` | Отдельный тестовый проект и пространство `[TEST]`, только `https` | GitLab MR; Confluence — только с `CONFLUENCE_PUBLISH_STAGING_ACK` = ключ пространства и корпоративным CA |

Профили `live_read_only` и `live_write_staging` подготовлены, но **не запускались**.

| Интеграция | Адаптер | Ключевые параметры |
|---|---|---|
| GitLab | `GitLabKnowledgeRepository`, `GitLabMRPublisher` | `KNOWLEDGE_BACKEND=gitlab`, `GITLAB_URL`, `GITLAB_PROJECT_ID`, `GITLAB_KNOWLEDGE_PATH`, `GITLAB_TOKEN_FILE`, `GITLAB_PROPOSALS_ENABLED` |
| Confluence MCP | `ConfluenceMCPConnector` (Streamable HTTP, только чтение) | `CONFLUENCE_CONNECTOR=mcp`, `CONFLUENCE_MCP_URL`, `CONFLUENCE_MCP_TOOL_MAP`, `CONFLUENCE_MCP_RESULT_MAP`, `CONFLUENCE_ALLOWLISTED_SPACES` |

## 6. Безопасность (реализовано)

- **Доступ.** Только loopback и проверка заголовка `Host`. Изменяющие запросы требуют заголовок
  `X-SKH-Client` (защита от CSRF на localhost).
- **Fail closed при старте.** Приложение не запускается, если:
  - `local_demo` слушает нелокальный адрес;
  - включён `AUTH_MODE=sso` или `APP_ENV=production`;
  - адрес не локальный и используется `http`;
  - интеграции включены в профиле `offline`;
  - в `live_read_only` включена запись;
  - в `integration_mock` указан реальный хост;
  - запись в Confluence включена без подтверждения staging и корпоративного CA;
  - токены MCP и публикации совпадают.
- **Авторизация.** Каждый маршрут объявляет действие (`app/authz.py`), тест не даёт добавить маршрут без
  него. Публикация разделена на `prepare_publication` (только чтение) и `publish_confluence` (запись).
- **Контент.** Markdown санитизируется на сервере (nh3) и повторно в браузере (DOMPurify). Строгая CSP,
  шрифты собраны локально. Запрещены path traversal и симлинки за пределы корня базы знаний. Документы и
  предложения проверяются на секреты и персональные данные.
- **Секреты.** Читаются только из файлов (`*_FILE`), корпоративный CA подключается через `*_CA_BUNDLE`.
  Токены не попадают в журналы и ответы API (есть тест на утечку). Проверка TLS не отключается.
- **Сеть.** В Docker у backend нет исходящей сети; произвольные URL от пользователя не запрашиваются;
  интеграции обращаются только к хостам из allowlist.
- **AI.** Источники передаются модели как данные, а не как инструкции; каждая цитата проверяется дословно.
  AI не может утвердить документ.
- **Журналы.** Без тел запросов и query string. Аудит предложений и событий публикации ведётся без
  содержимого.

Подробнее: `docs/SECURITY.md`, `docs/SSO_RBAC_REQUIREMENTS.md`.

## 9. Что и как проверено

| Уровень | Что входит |
|---|---|
| **Проверено локально** | Офлайн-режим, каталог, поиск, ассистент в демо-режиме, создание документов, предложения и diff, конвертация Markdown в storage, запрет небезопасных конфигураций, сетевая изоляция Docker, сохранность данных после перезапуска |
| **Проверено только на тестовых дублях** | Весь цикл GitLab (чтение, ветка, коммит, MR, merge, синхронизация, конфликты, неопределённые результаты); MCP (обнаружение инструментов, пагинация, сбои); вся публикация в Confluence (создание, обновление, конфликты, потерянные ответы, перезапуск) |
| **Не прошло live validation** | Реальные GitLab, Confluence MCP, Confluence DC REST; внутренняя AI-модель; GigaCode |

Что, вероятно, придётся адаптировать на реальном сервере:
- нормализация storage-формата;
- `metadata.properties` при создании страницы;
- доказательство merge при squash- и rebase-стратегиях;
- реальные права учётной записи публикации;
- лимиты запросов.

Подробно — `docs/M4_M5_INTEGRATION_READINESS.md` §9.

## 10. Известные ограничения и отступления от задания

**Отступления (осознанные, записаны в ADR):**
- **Новый документ можно сразу создать со статусом `approved`.** Это касается только ручного документа,
  интерфейс показывает предупреждение. Утверждением считается ревью и merge MR; иначе для публикации нужен
  второй MR только ради смены статуса. AI-черновик утвердить нельзя.
- **Ветка `kb/update/` используется и для новых документов.**
- **Публикация выполняется синхронно с сохранением состояния в базе, без отдельного воркера очереди.**
- **Сохранены прежние имена переменных.** `KNOWLEDGE_BACKEND`, `GITLAB_URL`, `GITLAB_KNOWLEDGE_PATH` вместо
  новых синонимов (ADR-018).
- **«Раздел каталога» — это тип документа (шаблон).**

**Ограничения (не исправлены, задокументированы):**
- Сценарии E2E-29, 30, 32, 34, 35 проверены на уровне API, без браузера.
- Переход по боковому меню не предупреждает о несохранённых изменениях в редакторе.
- `features.confluence_publish` означает «публикация настроена», включая режим только dry-run.
- В списке заданий публикации нет проверки доступа к конкретному документу (сейчас один пользователь).
- Переименование документа в заголовок, уже занятый другой страницей, заранее не проверяется: задание
  завершится `failed`.
- Профиль `offline` не допускает `AI_PROVIDER=internal_api`.

## 11. Что блокирует промышленное использование

Полный перечень с условиями снятия — `docs/PRODUCTION_BLOCKERS.md` (PB-01…18). Главное:
- **Пользователи и права.** Нет SSO и RBAC: один оператор на localhost (PB-01, PB-02). Нет пользовательских
  прав GitLab и Confluence; чтение и запись идут сервисными учётными записями без атрибуции (PB-03, PB-04, PB-18).
- **Проверка интеграций.** Live validation GitLab, MCP и Confluence не проводилась (PB-05, PB-12).
- **Инфраструктура.** Нет согласованных сетевых правил, корпоративного CA для Confluence и учётной записи
  публикации (PB-06, PB-14, PB-16).
- **Данные и аудит.** Нет требований ИБ к аудиту и хранению событий, нет резервного копирования
  `app_state.sqlite3` и `publications.sqlite3` (PB-07, PB-08, PB-15, PB-17).
- **AI.** Нет утверждённого AI-провайдера (PB-09).
- **Эксплуатация.** Нет мониторинга, HA и процедуры поставки (PB-10, PB-11, PB-13).
