# Привязка документ → страница Confluence, версии и метка владельца

Реализация: `backend/app/services/publications.py` (`PublicationStore`, `PublicationService._plan`,
`_inspect`, `acknowledge_manual_edit`), `backend/app/adapters/confluence_rest/publisher.py` (`PROPERTY_KEY`).
Проверено на stateful тестовом дубле Confluence DC (`backend/tests/test_publications.py`). На реальном
Confluence DC **не проверялось**. Архитектура — `docs/CONFLUENCE_PUBLISHING_ARCHITECTURE.md`.

Главный принцип: приложение изменяет только страницу, которая **доказуемо принадлежит** документу —
через durable-привязку **и** метку владельца на самой странице. Ни заголовок, ни frontmatter, ни запрос
пользователя не определяют, какую страницу менять.

## 1. Ключ привязки

`(project_id, document_key)`:

- `project_id` — `GITLAB_PROJECT_ID` (для локального workspace — `local`; публикация из него невозможна);
- `document_key` — стабильный ID документа в нижнем регистре (ID уникален без учёта регистра и не меняется).

Путь файла хранится, но в ключ не входит: перенос файла в GitLab не создаёт новую страницу.

## 2. Что хранится (`publication_mappings` в `publications.sqlite3`)

| Поле | Смысл |
|---|---|
| `project_id`, `document_key` | ключ |
| `document_id`, `document_path` | ID и путь файла в GitLab на момент публикации |
| `page_id`, `space_key`, `parent_id` | страница, пространство и родитель (из конфигурации) |
| `page_title` | заголовок страницы после последней публикации |
| `page_version` | версия страницы в Confluence после последней публикации (или после подтверждения ручной правки) |
| `published_revision` | SHA коммита GitLab, который опубликован |
| `published_signature` | подпись storage, **прочитанного** из Confluence после записи |
| `published_storage` | этот storage целиком — база для diff при ручной правке |
| `rendered_signature` | подпись storage, который приложение отрендерило и отправило |
| `last_published_at`, `updated_at` | время последней записи и последнего изменения привязки |

Состояние, число попыток и санитизированная последняя ошибка (`state`, `attempts`, `error_code`,
`error_message`, `uncertain`, `version_before`, `version_after`) хранятся в задании (`publication_jobs`),
события без содержимого — в `publication_events`. Токены и тексты документов в журналы не пишутся.

## 3. Метка владельца: content property `skh-managed-document`

Значение свойства:

```json
{
  "document_id": "SEM-ARCH-002",
  "project_id": "<GITLAB_PROJECT_ID>",
  "path": "docs/SEM-ARCH-002.md",
  "managed_by": "semantic-knowledge-hub"
}
```

- Записывается при создании страницы — в `metadata.properties` запроса `POST /rest/api/content`. Если после
  создания метка не читается, она записывается отдельным `POST /rest/api/content/:id/property`.
- Страница считается своей, если `document_id` (без учёта регистра) и `project_id` метки совпадают с
  документом и проектом.
- При обновлении страницы метка не переписывается.
- Для людей на странице есть панель-макрос `info` с ID документа; машинным признаком она не является.

## 4. Почему заголовку не доверяют

Страницу с любым заголовком может создать человек. Поэтому:

- **Нет привязки** → поиск страницы с заголовком документа в целевом пространстве:
  - страницы нет → `create`;
  - страница есть **с меткой** этого документа (например, создание прошло, но ответ потерялся) → она
    используется, дубликат не создаётся (предупреждение `managed_page_found`);
  - страница есть **без метки** → конфликт `title_taken`, страница не меняется.
- **Есть привязка** → страница читается по `page_id`; заголовок для выбора страницы не используется.

## 5. Page ID никогда не приходит извне

- Поле `confluence_page_id` во frontmatter документа **игнорируется** (предупреждение
  `frontmatter_page_id_ignored`); тест подтверждает, что указанная там чужая страница не меняется.
- Ни один маршрут API не принимает page ID, пространство или URL; у маршрутов публикации нет тела запроса
  (тест `test_no_route_accepts_a_page_id`).
- Пространство и родитель — только `CONFLUENCE_TARGET_SPACE` и `CONFLUENCE_PARENT_PAGE_ID`.

## 6. Версии

- Обновление отправляет `version.number = remote_version + 1`, где `remote_version` прочитана при повторном
  построении плана непосредственно перед записью.
- `409` от Confluence (кто-то изменил страницу между чтением и записью) → задание `conflict`, ничего не
  перезаписано.
- Если версия страницы изменилась, а содержимое и заголовок совпадают с опубликованными, это не конфликт —
  предупреждение `version_changed`.

## 7. Обнаружение ручной правки

Ручная правка = есть привязка **и** версия страницы отличается от `page_version` **и** (подпись текущего
storage ≠ `published_signature` **или** заголовок ≠ `page_title`).

Результат: действие `conflict`, `diff_kind=manual_edit`, проблема `manual_edit`; diff показывает «опубликовано
приложением → текущее в Confluence». Автоматическая перезапись запрещена: правку нужно перенести в GitLab
(через MR) или явно подтвердить её учёт (раздел 10).

## 8. Правило noop

Если подпись текущего storage страницы равна подписи нового отрендеренного storage и заголовок совпадает,
действие — `noop`: запросов записи нет, новая версия не появляется; при публикации привязка получает текущую
ревизию (`published_revision`), `last_published_at` не меняется. Повторная публикация той же ревизии
идемпотентна (E2E-27).

## 9. Сверка после потерянного ответа

Запись, ответ на которую не получен (таймаут, обрыв, `5xx`, некорректный ответ), никогда не повторяется
вслепую. Confluence проверяется только чтением:

| Действие | Доказательство, что запись применена |
|---|---|
| `create` | в пространстве есть страница с заголовком документа **и** меткой этого документа |
| `update` | версия страницы = `remote_version + 1` **и** подпись storage = подпись отрендеренного |

Применено → привязка сохраняется, задание `published`. Не применено (`create`: страницы с меткой нет;
`update`: версия не изменилась) → `failed`, повтор безопасен. Иначе (в том числе страница не читается или
проверка сама завершилась ошибкой) → `result_unknown`; кнопка «Проверить результат» (`POST …/reconcile`)
повторяет проверку и, если запись не подтвердилась, выполняет свежий dry-run.

## 10. Подтверждение ручной правки — единственный путь перезаписи

`POST /api/publications/jobs/{id}/acknowledge-manual-edit` (право `publish_confluence`):

1. Доступно только для задания в `conflict` с `diff_kind=manual_edit` и известной страницей.
2. Страница перечитывается; базой привязки становятся её текущие версия, заголовок, storage и подпись
   (событие `manual_edit_acknowledged`). В Confluence ничего не записывается.
3. Сразу выполняется dry-run: обычно действие `update`, а diff показывает «текущее в Confluence → новая
   ревизия», то есть **что именно будет заменено**.
4. Перезапись происходит только после отдельного явного «Опубликовать».

Перед подтверждением ручную правку следует перенести в GitLab через MR, если она нужна, — иначе она будет
потеряна при публикации.

## 11. Другие конфликты

| Код | Когда | Как разрешить |
|---|---|---|
| `title_taken` | привязки нет, страница с тем же заголовком без метки | переименовать документ (через MR) или страницу в Confluence |
| `foreign_page` | страница привязки без метки этого документа (метку удалили вручную или привязка повреждена) | выяснить происхождение; страница не меняется |
| `page_moved` | страница привязки перенесена в другое пространство | вернуть страницу в целевое пространство |
| `mapped_page_missing` | страница привязки не найдена (удалена или недоступна) | восстановить страницу (например, из корзины) или, если её не вернуть, «Создать страницу заново» (`POST …/release-missing-page`: приложение проверяет, что страницы сейчас нет, забывает привязку и делает dry-run — план станет `create`) |

## 12. Ограничения и как они обработаны

- **Перенос страницы вручную** (в другое пространство или под другого родителя) — конфликт `page_moved`:
  dry-run сравнивает пространство и прямого родителя (последний элемент `ancestors`). Публикация не
  вернёт страницу обратно автоматически.
- **Страница удалена**: `mapped_page_missing` → восстановить страницу или явно «создать заново»
  (`release-missing-page`, только если страницы действительно нет; событие записывается в журнал).
- **Пересериализация storage в Confluence**: `noop` определяется и без побайтового совпадения — если
  версия страницы не менялась с нашей публикации и новый отрендеренный текст совпадает с
  `rendered_signature`, новая версия не создаётся.
- **Потеря БД привязок**: страница с меткой этого документа находится по заголовку; при совпадении
  содержимого публикация без записи восстанавливает привязку (`managed_page_found` + `noop`).
- **Создание прошло, а метку записать не удалось**: задание `failed` с кодом `marker_write_failed` и ID
  страницы; приложение эту страницу не меняет — её нужно разобрать вручную.
- **Неоднозначная проверка после потерянного ответа** (версия выросла, но содержимое не совпадает) —
  `result_unknown`; «Проверить результат» выполняет dry-run, и неожиданная версия становится конфликтом
  ручной правки для решения человеком. Повторной записи вслепую нет.
- **Переименование документа** в заголовок, уже занятый другой страницей пространства: `update` получит
  `400` от Confluence → `failed`; предварительной проверки заголовка при обновлении нет.
- Нормализация storage реального DC может отличаться от тестового дубля — пункт live validation
  (`docs/M4_M5_INTEGRATION_READINESS.md`, раздел 9).
