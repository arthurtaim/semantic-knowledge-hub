# GigaCode: целевая агентная среда и что остаётся в приложении

Сейчас Claude Code используется только для **разработки** приложения. Приложение от него не зависит:
в рантайме работают `AI_PROVIDER=mock` (детерминированные выдержки, без модели) или явно настроенный
OpenAI-совместимый внутренний эндпоинт. Целевая агентная среда банка — **GigaCode**. Его программные
интерфейсы в банке пока не подтверждены, поэтому интеграции с GigaCode в коде **нет**, и она не
имитируется.

Не путать: GigaChat API (`chat/completions` — языковая модель) и GigaCode (агентная среда:
CLI/IDE, инструменты, MCP) — разные вещи. Первое может стать `AIProvider`, второе — клиентом приложения.

## 1. Целевая архитектура

```text
            Сотрудник
         /             \
  Web UI (React)      GigaCode (IDE/CLI агент)
         \             /          \
     Semantic Knowledge Hub API     MCP-серверы, разрешённые банком
     (FastAPI: поиск, цитаты,       (Confluence MCP — тот же, что у приложения, только чтение;
      шаблоны, черновики,            будущий MCP-сервер самого Hub — опционально)
      валидация, предложения,
      публикация, права, аудит)
        |                  |                          \
   GitLab (источник     AIProvider: mock |           Confluence DC REST
   истины: Markdown,    internal_api | (GigaChat —   (публикация после merge,
   ветки, MR, ревью)    при подтверждении API)       отдельный токен, явное действие человека)
```

**GitLab остаётся источником истины в любом варианте.** Ни агент, ни модель не пишут в основную ветку:
единственный путь изменений — предложение → валидация → ветка `kb/update/…` → MR → ревью людьми → merge.

## 2. Текущие точки входа AI (M4.6)

Все три точки входа идут через протокол `AIProvider` (`backend/app/adapters/ai/base.py`); остальная логика
от провайдера не зависит.

| Маршрут | Метод провайдера | `mock` (проверено локально) | `internal_api` |
|---|---|---|---|
| `POST /api/assistant/ask` | `answer(question, passages, options)` | дословные выдержки, «Недостаточно данных» | реализовано, на реальном эндпоинте не проверялось |
| `POST /api/drafts/suggest` | `suggest_edit(instruction, document_markdown)` | `503 ai_edit_unsupported` | реализовано, не проверялось |
| `POST /api/authoring/ai-draft` | `draft_document(AuthoringRequest) -> AuthoringDraft` | структура шаблона + проверенные выдержки из утверждённых документов (`docs/AI_AUTHORING_CONTRACT.md`) | реализовано (строгий JSON-ответ), не проверялось |

Флаги для UI: `GET /api/session` → `features.ai_mode`, `features.ai_provider`, `features.ai_edit_suggestions`,
`features.ai_authoring`.

## 3. Что может заменить GigaCode

| Функция | Сейчас | С GigaCode |
|---|---|---|
| Генерация текста ответа | `mock` или `internal_api` | `AIProvider` на подтверждённом API модели (GigaChat или внутренний шлюз) |
| Черновик правки по инструкции (`suggest_edit`) | недоступно в `mock` | тот же `AIProvider`; результат — только черновик предложения |
| Черновик нового документа (`draft_document`) | демо: шаблон + дословные выдержки | тот же `AIProvider`, контракт `AuthoringRequest`/`AuthoringDraft` без изменений |
| Интерактивная работа автора (поиск, чтение, черновик в IDE) | Web UI | GigaCode как клиент API Hub (раздел 5) |
| Многошаговые сценарии (найти → сравнить → предложить) | нет | агент GigaCode, вызывающий инструменты Hub; каждое изменение — только через предложение |

## 4. Что остаётся вне AI-провайдера (не переносится в агента)

Меняется только реализация агентных функций. Всё перечисленное ниже остаётся в приложении и работает
одинаково с любым провайдером:

- редактор документа, предпросмотр, генерация frontmatter из формы, шаблоны;
- постоянные черновики (сохранение с `expected_version`, удаление), валидация и проверка уникальности ID/пути;
- жизненный цикл предложений (`create`/`update`), diff, конфликты;
- запись в GitLab только через `GitLabMRPublisher` (ветка `kb/update/…`, коммит, Draft MR); merge — люди;
- `KnowledgeProvider` (локальный workspace / GitLab), синхронизация и индекс FTS;
- MCP-коннектор Confluence с провенансом (ID страницы, версия, ссылка, выдержка) и allowlist пространств;
- отбор источников для AI-черновика (только утверждённые командные документы, область `team`) и проверка
  цитат после ответа провайдера;
- задания публикации, dry-run и Confluence REST publisher (`docs/CONFLUENCE_PUBLISHING_ARCHITECTURE.md`).

Подробнее о защитных механизмах:
- **Права:** кто что читает и меняет (`app/authz.py`, будущий SSO/RBAC). Модель не является слоем авторизации.
- **Поиск и выбор доказательств:** FTS5-индекс, фильтры статусов, исключение черновиков и устаревших документов.
- **Проверка цитат:**
  - цитата возможна только из переданного фрагмента и только с дословной выдержкой не короче 12 символов;
  - маркеры `[Cn]` в тексте источника нейтрализуются;
  - при недостатке данных ответ заменяется фиксированной фразой «Недостаточно данных».
- **Защита от prompt injection:**
  - содержимое документов и ответы MCP — недоверенные данные;
  - они передаются модели отдельным JSON-блоком, фразы-инструкции из документов вырезаются;
  - системные инструкции приложения, запрос пользователя и найденный контент разделены;
  - команды из документации никогда не исполняются; обнаруженные секреты не выдаются.
- **Валидация предложений** (схема, `id`, путь, размер), diff, конфликт ревизий, запись в GitLab только
  через `GitLabMRPublisher` с предусловием `last_commit_id`.
- **Провенанс:** источник, ID, ревизия, ссылка и выдержка для каждой цитаты.

## 5. Как GigaCode получает документы
- **Через API Hub, а не напрямую из GitLab:** `GET /api/search`, `GET /api/documents/{id}`,
  `POST /api/assistant/ask`. Так агент получает только то, что разрешено пользователю, вместе с
  ревизией и ссылками.
- **Контекст для модели в `AIProvider`** формирует `AssistantService` (ответы) или `AuthoringService`
  (черновики документов): только авторизованные фрагменты с ограниченным объёмом (`AI_MAX_CONTEXT_CHARS`),
  с метаданными в JSON.
- Если GigaCode поддерживает только MCP, а не HTTP-инструменты, нужен отдельный тонкий
  **MCP-сервер Hub** поверх того же API: инструменты `search`, `get_document`, `ask`, `list_templates`,
  `check_document`, `create_proposal`. Права и проверки при этом остаются в backend. Это отдельная задача
  после подтверждения транспортов MCP в GigaCode.

## 6. Как GigaCode получает доступ к Confluence MCP
- Предпочтительно — **через Hub** (`sources=["corporate"]`). Тогда работают allowlist пространств,
  фильтрация ссылок, лимиты и проверка цитат.
- Прямое подключение GigaCode к тому же MCP-серверу допустимо, только если MCP применяет права
  **пользователя**. С общим сервисным токеном это недопустимо (PB-04).
- Для записи в Confluence MCP не используется ни приложением, ни агентом: публикация идёт только через
  Confluence REST publisher после merge в GitLab и явного действия человека.

## 7. Как согласуются изменения
1. Агент формирует черновик: изменение — `POST /api/drafts` с базовой ревизией; новый документ —
   `POST /api/authoring/drafts` по шаблону (`origin=ai_suggestion`). Документ не меняется.
2. Ассистент не может поставить `approved` (ошибка валидации для `origin=ai_suggestion`).
3. Человек правит черновик, смотрит diff и отмечает «Готово к ревью».
4. Отправка в GitLab создаёт ветку и MR (`Draft:`). Merge выполняют только ревьюеры GitLab.
5. Предложение получает статус `merged` только после подтверждения GitLab.
6. Публикация в Confluence — отдельное явное действие оператора после dry-run.

## 8. Разрешения инструментов (tool permissions)

Если агент станет клиентом API Hub, его вызовы проходят те же точки авторизации (`require(Action…)`).
Предлагаемое разделение для будущей политики RBAC:

| Действие (`Action`) | Агенту | Почему |
|---|---|---|
| `read_knowledge`, `ask_assistant` | да, от имени пользователя | чтение в пределах прав пользователя |
| `read_corporate` | только при пользовательском ACL Confluence (PB-04) | общий сервисный токен не проверяет права пользователя |
| `create_proposal` (черновики, проверка, AI-черновик) | да | результат — только черновик, документ не меняется |
| `review_proposal` («Готово к ревью», отклонение) | нет, только человек | решение о передаче на ревью |
| `submit_proposal` (ветка, коммит, MR) | нет без явного подтверждения пользователя | запись в GitLab |
| `sync_knowledge` | нет | администрирование |
| `prepare_publication` | допустимо (только чтение Confluence) | dry-run ничего не пишет |
| `publish_confluence` | нет, только человек | запись в Confluence и единственный путь перезаписи ручной правки |

Сейчас агентской идентичности нет, а `LocalDemoPolicy` разрешает единственному оператору **все** действия.
Поэтому подключать агента к API до SSO/RBAC (PB-01/02) можно только в однопользовательском тестовом контуре
и только на синтетических данных.

## 9. Где подключается адаптер (как реализовано)
- **Ответы и черновики модели:** новый модуль, реализующий протокол `AIProvider`
  (`backend/app/adapters/ai/base.py`: `mode`, `supports_edit_suggestions`, `supports_authoring`, `answer`,
  `suggest_edit`, `draft_document`, `status`). Регистрация в `build_ai()` (`backend/app/container.py`)
  под новым значением `AI_PROVIDER` с allowlist хоста и CA, как у `internal_api`. Сейчас любой
  `AI_PROVIDER`, кроме `mock`/`disabled`, — это интеграция: в профиле `offline` такой запуск отклоняется
  (`docs/M4_M5_INTEGRATION_READINESS.md`, раздел 0).
- **Агент как клиент:** изменения в приложении не нужны. Используется тот же HTTP API и те же проверки
  (`X-SKH-Client`, права через `require(Action…)`).
- **Приёмка:** `tests/test_curated_qa.py`, `tests/test_assistant.py` и `tests/test_authoring.py` с
  подменённым транспортом нового провайдера, затем включение за флагом и сравнение с текущим провайдером.

## 10. Что проверить на корпоративной установке GigaCode (до разработки адаптера)
1. Режим поставки: CLI, IDE-плагин, on-prem сервер; есть ли программный агентный API. Публичный REST Agent
   API GigaCode **не предполагается**, пока не подтверждён установкой банка.
2. Поддерживаемые транспорты MCP (stdio / Streamable HTTP), конфигурация MCP-серверов, ограничения на
   инструменты, подтверждение вызовов пользователем (tool approval).
3. Файлы инструкций проекта (аналог `CLAUDE.md`/`AGENTS.md`) и способ автоматизированного вызова агента.
4. Где выполняется модель (on-prem / облако банка), куда уходят данные, хранение промптов и ответов (data residency).
5. Аутентификация: SSO, MFA, сервисные учётные записи, передача идентичности пользователя в инструменты, scopes.
6. Формат вызова инструментов и ответов, лимиты контекста, таймауты, повторы.
7. Журналирование вызовов инструментов (аудит) и требования ИБ к нему.
8. Совместимость с GigaChat API, если он используется как `AIProvider`: эндпоинт, формат, лимиты, CA.

## 11. Ограничения до SSO и live validation
- Один оператор, без пользовательских ACL GitLab и Confluence (PB-01…PB-04): агент видел бы всё, что видит
  сервисная учётная запись.
- `internal_api` (ответы, правки, черновики) на реальной модели не проверялся (PB-09).
- GitLab, MCP и Confluence REST проверены только на тестовых дублях (PB-05, PB-12).

## 12. Антипаттерны
- Модель или агент как единственный слой авторизации.
- Прямая запись агента в GitLab или Confluence в обход предложений, MR и публикатора.
- Использование MCP-коннектора Confluence (или его токена) для записи.
- Хранение промптов и переписки с корпоративными данными в GitHub.
- Предположение, что GigaChat `chat/completions` даёт инструменты GigaCode.
- «Временный» прямой доступ агента к основной ветке.
