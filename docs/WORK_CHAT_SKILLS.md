# Навыки работы с задачами в чате (M7)

Три встроенных навыка ассистента работают с проектами и задачами модуля «Работа» (M6) прямо из чата — через **те же
сервисы, права и экраны проверки**, что и раздел «Работа». Чат ничего не записывает в задачи: новые задачи и изменения
существующих — это **предложения**, которые человек проверяет и подтверждает отдельной кнопкой.

| Навык | Что делает | Запись |
|---|---|---|
| `analyze_project` «Проанализировать проект» | сроки, просрочки, ожидания предшественников, задачи без дат, вехи — по фактам `skh_work` | нет |
| `draft_task_plan` «Составить план задач» | предложение НОВЫХ задач по документам (WAP, M6 «AI план») | только после «Создать задачи» в проекте |
| `propose_task_changes` «Предложить изменения задач» | change-set СУЩЕСТВУЮЩИХ задач (WCP): статус, приоритет, срок, название, описание | только после «Применить изменения» |

Ключевое правило: **слова в чате («да», «принимаю», «сделай», «применяй») ничего не применяют**. Пути записи из
`/api/assistant/ask` нет, инструмента записи в цикле модели нет.

## 1. Поток запроса

```
POST /api/assistant/ask(/stream) {skill_id, question, context_document_ids[], work_context{project_key, task_keys[],
                                   proposal_id, client_request_id}}
  route   глобальные Action навыка (view_tasks | propose_work [+ edit_task]) → 403 до всего остального
          WorkPrincipal из ОДНОГО построителя с api/work.py (work_principal: идентичность сервера, маркер шлюза,
          снимок документов читателя) — никакого X-User-ID, роли или версии от клиента
  plan()  модуль задач и права (work_denied: 503 модуль отключён, 403 только просмотр / нет прав) →
          провайдер (503 skill_unavailable: mock, нет возможности) →
          WorkChatSkills.resolve: проект и задачи в области видимости читателя (404 неизвестный = скрытый,
          409 архивный проект для предложения, 404 задача другого проекта), ссылка на предложение — своё, того же
          навыка и проекта (422 / 404) — ВСЁ до вызова модели
  run()   analyze_project → WorkInspector (get_project_schedule + get_task выбранных задач) → факты [F…]
                            → цикл инструментов M5.7 с этими вызовами как раунд 0 (модель пересказывает факты)
                            → без модели с инструментами: сводка, составленная СЕРВЕРОМ (помечена)
          draft_task_plan → WorkAiService.propose | .revise → WAP suggested → карточка → /projects/KEY?proposal=WAP-…
          propose_task_changes → WorkChangeService.propose | .revise → WCP suggested → карточка → /projects/KEY?changes=WCP-…
```

## 2. Контракты (аддитивные)

- `AskRequest.work_context` (`extra="forbid"`): `project_key` (`^[A-Z][A-Z0-9]{1,9}$`, приводится к верхнему
  регистру), `task_keys` ≤ 20, `proposal_id` (`^(WAP|WCP)-[0-9a-f]{16}$`), `client_request_id`. Принимается только с
  навыком Work (иначе 422). Это ССЫЛКИ, не права: сервер перепроверяет каждую при каждом сообщении.
- `AskResponse.work_proposal` (`WorkProposalRef`): `kind` (`task_plan` | `task_changes`), `id`, `project_key`, `state`
  на момент ответа, `app_path` (строит сервер), `task_count`, `dependency_count`, `change_count`, `revised_from`,
  `requires_confirmation`. Отдельно от `proposal` (документные AI-предложения M5.6.3): карточка никогда не читается из
  `/api/ai/proposals`.
- `SkillInfo.requires.project`, `SkillInfo.work` — каталог навыков; `available=false` с причиной («Модуль задач
  отключён», «Нет прав…», режим только просмотра, «Нет языковой модели (режим mock)…»).
- История чата: `StoredTurnRequest.work` = ключ проекта, ключи задач, id предложения, ключ отправки (без заголовков и
  данных задач). Ответ хранится целиком (с `work_proposal`); при открытии диалога карточка заново читает состояние.
- Новые маршруты (`api/work.py`):

| Маршрут | Action | Что делает |
|---|---|---|
| `POST /api/work-ai/proposals/{id}/revise` | `propose_work` | НОВЫЙ WAP из этого + уточнение; этот не меняется |
| `POST /api/work-ai/change-proposals` | `propose_work` (+ `edit_task` на проекте) | WCP; задачи не меняются |
| `GET /api/work-ai/change-proposals/{id}` | `propose_work` | текущее состояние: `ready` / `stale` + причины / `applied` / `rejected` |
| `POST …/{id}/preview` | `propose_work` | выбранные операции, перечитанные из текущего состояния; ничего не пишет |
| `POST …/{id}/apply` | `apply_work_proposal` + `edit_task` | одна транзакция; идемпотентно по `client_request_id` |
| `POST …/{id}/revise` | `propose_work` | НОВЫЙ WCP |
| `POST …/{id}/reject` | `propose_work` | закрыть без изменений; повтор — 409 |

## 3. Права (одна точка правды)

| Операция | Глобальный Action | Проектный шлюз `WorkAccessGate` |
|---|---|---|
| Анализ | `view_tasks` | просмотр проекта |
| WAP из чата / уточнение | `propose_work` | `propose_work` на проекте, проект не в архиве |
| WCP из чата / уточнение | `propose_work` + `edit_task` | `propose_work` и `edit_task` на проекте, проект не в архиве |
| Применить WAP | `apply_work_proposal` | прежний шлюз M6 |
| Применить WCP | `apply_work_proposal` + `edit_task` | те же действия на проекте |

Режим только просмотра (открытая ссылка, `X-SKH-Exposure: public`) — 403 до модели; анализ доступен. В командном режиме
(`membership`) проект, где пользователь не участник, невидим (404), viewer может анализировать, но не предлагать.
Предложения личные: чужой id — 404, как несуществующий.

## 4. Change-set (WCP): движок изменения существующих задач

- **Поля v1**: `title`, `description`, `status`, `priority`, `due_date` (срок, НЕ план: Гант не двигается; `null` —
  снять срок). Исполнитель, даты плана, закрепление, зависимости, иерархия, архив — не меняются предложением: такие
  пункты модели отбрасываются с подсказкой, где это сделать в интерфейсе задач; «передвинуть по Ганту» никогда не
  выдаётся за сделанное.
- **Какие задачи видит модель**: названные (явно в `task_keys` или ключом в тексте запроса — только этого проекта),
  иначе активные задачи проекта, не больше 60 (больше → 422 «укажите задачи»). Модель видит ключ, очищенные название и
  краткое описание, статус, приоритет, срок — без id, версий, исполнителей.
- **Протокол** (`adapters/ai/work_change_protocol.py`, без привязки к вендору): ответ `{"goal", "changes": [{"task_key",
  "field", "new_value", "reason"}], "unsupported", "assumptions"}`. Неверные ТИПЫ → `502 ai_invalid_response`, ничего
  не сохранено. Смысл проверяет сервер (`validate_changes`): неизвестная задача, неподдерживаемое поле, недопустимое
  значение (те же правила, что у правки задачи), повтор, «то же значение» — отбрасываются как замечания; не осталось ни
  одной операции → 422, ничего не сохранено. `before` и версию задачи читает СЕРВЕР; модель их не задаёт.
- **Хранение** — таблица `work_task_change_proposals` (схема v4): операции с `before`/`after`, версии задач, источники,
  замечания, допущения, `revised_from`; аудит `change_proposal_created`.
- **Устаревание** вычисляется при чтении: `plan_changed` (любая правка проекта повышает ревизию плана), `task_changed`,
  `task_archived`, `task_unavailable`, `source_changed` / `source_unavailable`, `expired` (24 ч). Устаревший WCP
  применить нельзя.
- **Применение** (`WorkService.apply_task_change_set`): одна транзакция `BEGIN IMMEDIATE` — владелец → шлюз
  (`apply_work_proposal` + `edit_task`) → идемпотентный повтор → проект открыт, статус `suggested` → проверка ревизии
  плана, каждой версии задачи, срока, источников и значений → каждая задача обновляется ОДИН раз (одно повышение версии,
  сколько бы полей ни менялось), событие `task_updated` на задачу (`proposal_id`, до/после; описание — только «изменено»),
  ОДНО повышение ревизии плана, `change_proposal_applied`, статус `applied` с результатом. Любая ошибка — откат всего
  (задачи, аудит, ревизия, статус). Пустой выбор → `422 nothing_to_apply` без повышения ревизии. Повтор с тем же
  `client_request_id` возвращает первый результат; тот же ключ с другим телом — 409.

## 5. Многоходовость

- Проект — контекст, который клиент присылает снова (чип «Проект»), а сервер каждый раз проверяет заново.
- «Уточнить» на карточке → тот же навык, проект и `work_context.proposal_id`. Сервер до модели проверяет владельца,
  проект, статус (применённое/отклонённое → 409), ревизию плана, срок, ревизии источников (изменились → 409) и создаёт
  **новое** предложение с `revised_from`; исходное не меняется и остаётся доступным. WAP уточняется по проверенному
  плану исходного предложения (`WorkPlanRequest.previous_plan` + `refinement`, промпт без уточнения — байт-в-байт
  прежний); WCP — по его операциям как данным.
- Без выбранного предложения «разбей первую задачу» — это новый запрос: сервер не угадывает, о каком предложении речь.
- Идемпотентность отправки: каждое сообщение несёт `client_request_id`; повтор той же отправки (или повторная отправка
  прерванного хода из истории) возвращает уже сохранённое предложение — второе не создаётся, модель не вызывается.

## 6. Анализ проекта

- Факты — только `WorkInspector` (тот же, что инструмент `work_inspect`): `get_project_schedule` выбранного проекта и
  `get_task` выбранных задач (до трёх). Определения сервера: просрочка (прошёл срок), отставание (прошёл последний день
  плана), ожидание предшественников FS, без дат, нарушенные зависимости, вехи. Критический путь не рассчитывается — так
  и говорится.
- С моделью, умеющей инструменты: эти вызовы записываются в цикл M5.7 как раунд 0 (`SeededCall`), модель может
  дочитать другие данные только для чтения (без `drafts_propose`), ответ проверяется как обычно (ссылки [F…]).
  Поиск по базе знаний, переформулировка и проверка полноты не запускаются; след поиска не пишется.
- Без модели (mock): сервер сам перечисляет факты со ссылками [F…] и пометкой «составлено сервером без языковой
  модели»; длинные списки — «показаны 10 из N».
- Данные задач недоступны → `503 work_unavailable`, без выдуманного ответа.

## 7. Провайдеры

`claude_cli` и внутренний OpenAI-совместимый endpoint реализуют `plan_work` (+ уточнение) и `plan_work_changes` одним и
тем же JSON-протоколом; mock и disabled — нет (навыки плана и изменений недоступны, анализ — серверной сводкой).
Тестовый двойник — `tests/support/scripted_model.py` (правила по ключевым словам только в нём). Живой модели в
проверке не было; результаты двойника — не доказательство качества реальной модели.

## 8. Интерфейс

- Композер: при навыке Work — строка «Проект» (видимые проекты, **без автоподстановки**, даже если проект один),
  «Задачи» (ключи, необязательно; ключ другого проекта — подсказка и запрет отправки) и чип «Уточняю WAP-…».
- Ответ: карточка «План задач для KEY» / «Изменения задач KEY» — счётчики, ТЕКУЩЕЕ состояние (перечитывается),
  «Проверить план» / «Проверить изменения» (ссылка), «Уточнить» (только для готового). Кнопок записи в чате нет.
- Проект: `?proposal=WAP-…` — прежняя проверка WAP (+ строка «Уточнение предложения …»); `?changes=WCP-…` — новая панель
  «Предложение AI: изменения задач»: было → станет, текущее значение, если оно другое, объяснение модели (не
  проверено), замечания сервера, флажки по операциям, «Проверить выбор», «Применить изменения (N)», «Отклонить».
  Двойной клик пишет один раз (кнопка блокируется, ключ один на панель); 409 → «Предложение устарело — подготовьте
  заново», выбор сохраняется.
- Панель ассистента документа показывает ту же карточку со ссылкой в проект.

## 9. Схема v4, резервная копия и откат

- Миграция v4 `work_task_change_proposals`: новая таблица + колонка `work_ai_proposals.revised_from` (аддитивно, без
  перезаписи строк). Перед миграцией существующей базы — автоматическая копия `work.sqlite3.pre-v4-<UTC>.bak`. Повторный
  старт миграцию не повторяет. Проверено на заполненной базе v3 дважды (`test_wcp22_…`): все строки и id сохранены.
- **Откат на версию без M7**: предыдущее приложение (схема v3) откажется стартовать на базе v4 («база новее
  приложения»). Порядок: остановить backend → `python -m app.tools.work_db restore --from work.sqlite3.pre-v4-….bak
  --yes` → запустить предыдущую версию. Предложения изменений, созданные после миграции, при этом теряются (задачи —
  нет, если их не применяли; применённые изменения тоже откатываются к копии).

## 11. Чего нет (сознательно)

Изменение исполнителя, дат плана, зависимостей и иерархии через предложение; критический путь; правка значений
операции прямо в панели изменений (значение правится в карточке задачи); «запоминание» предложения моделью между
сообщениями (контекст присылает клиент, проверяет сервер); живая проверка на целевой модели.
