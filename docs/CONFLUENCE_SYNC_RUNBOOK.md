# Runbook: публикация в Confluence Data Center

Для оператора публикации (роль «публикатор») и дежурного инженера. Описывает подготовку и dry-run,
чтение предпросмотра, публикацию, разбор конфликтов и ошибок, восстановление, резервное копирование и
ротацию токена.

Статус: процедуры проверены только на stateful тестовом дубле Confluence DC (pytest, `make mock-e2e`).
На реальном Confluence DC **не проверялись**. Запись в реальный Confluence допускается только в профиле
`live_write_staging` и только после отдельного письменного разрешения (`docs/STAGING_TEST_RUNBOOK.md`, раздел 7).
Устройство — `docs/CONFLUENCE_PUBLISHING_ARCHITECTURE.md`, привязки и версии — `docs/CONFLUENCE_MAPPING.md`.

## 1. Перед началом

1. Узнать режим публикатора: `GET /api/documents/<ID>/publication` → `publisher.mode` и `publisher.target_kind`.

   | `mode` | Что можно |
   |---|---|
   | `disabled` | ничего; `CONFLUENCE_REST_URL` не задан |
   | `dry_run_only` | задания и предпросмотр; запись выключена |
   | `write` | предпросмотр и явная публикация |

   `target_kind=mock` — локальный тестовый дубль; `real` — реальный сервер (это **не** live validation).
2. Права: `prepare_publication` (задания, dry-run, сверка) и `publish_confluence` (публикация, подтверждение
   ручной правки). Сейчас действует только `local_demo` — один оператор на loopback.
3. Учётные данные публикации — **только** отдельный токен `CONFLUENCE_REST_TOKEN_FILE`. Токен MCP для
   публикации не использовать никогда (совпадение токенов блокирует запуск).

В UI: блок «Публикация в Confluence» на странице документа (ревизия GitLab, состояние, опубликованная
ревизия, ссылка на страницу, кнопки «Подготовить публикацию» и «Открыть предпросмотр») и страница задания
`/publications/<id задания>` (действие, цель, доказательство merge, проблемы и предупреждения, diff,
storage, кнопки «Проверить заново (dry-run)», «Опубликовать в Confluence», «Проверить результат» /
«Повторить», «Подтвердить ручную правку»). Кнопка «Опубликовать в Confluence» скрыта, если запись выключена.
Страница «Интеграции» показывает цель (`target`), доступ (`access`), режим публикатора и время проверки.

Те же операции доступны через API. Изменяющие запросы требуют заголовок `X-SKH-Client` и loopback-адрес:

```bash
BASE=http://127.0.0.1:5174        # make mock-up (integration_mock); для другого стека — его адрес UI
DOC=SEM-ARCH-002
curl -s "$BASE/api/documents/$DOC/publication"                                     # состояние документа
curl -s -X POST -H 'X-SKH-Client: operator' "$BASE/api/documents/$DOC/publication/prepare"   # задание + dry-run
curl -s "$BASE/api/publications/jobs?document_id=$DOC"                            # история заданий
JOB=<id задания>
curl -s "$BASE/api/publications/jobs/$JOB"                                        # предпросмотр и история
curl -s -X POST -H 'X-SKH-Client: operator' "$BASE/api/publications/jobs/$JOB/dry-run"
curl -s -X POST -H 'X-SKH-Client: operator' "$BASE/api/publications/jobs/$JOB/publish"
curl -s -X POST -H 'X-SKH-Client: operator' "$BASE/api/publications/jobs/$JOB/reconcile"
curl -s -X POST -H 'X-SKH-Client: operator' "$BASE/api/publications/jobs/$JOB/acknowledge-manual-edit"
```

## 2. Подготовка и dry-run

- После подтверждённого merge и успешной синхронизации задание для новой ревизии создаётся автоматически и
  сразу выполняет dry-run. Публикация автоматически не выполняется.
- Вручную: «Подготовить публикацию» на странице документа (`POST /api/documents/<ID>/publication/prepare`) —
  создаёт задание для **текущей** ревизии (или переиспользует активное задание той же ревизии), заменяет
  активное задание старой ревизии (`superseded`) и выполняет dry-run.
- Повторный dry-run: «Проверить заново (dry-run)» (`POST /api/publications/jobs/<JOB>/dry-run`; из `pending`,
  `dry_run_ready`, `failed`, `conflict`).
- Dry-run выполняет только запросы чтения к GitLab и Confluence.

| Ответ | Значение | Действие |
|---|---|---|
| `409 publication_in_progress` | есть задание в `publishing` или `result_unknown` (`details.job_id`) | сначала «Проверить результат» (раздел 8) |
| `503 publication_disabled` | публикация не настроена | — |
| `502`/`503` с кодом `confluence_*` | Confluence недоступен, отклонил токен или права | задание остаётся `pending`, ничего не записано; устранить причину и повторить |
| `503` с кодом GitLab | не удалось проверить ревизию или merge | повторить после восстановления GitLab |

## 3. Как читать предпросмотр (`plan` задания)

Проверьте по порядку:

1. **Ревизия и merge:** `plan.revision` — SHA коммита GitLab; `plan.merge_request` — номер, ссылка и время
   merge. Нет `merge_request` → публиковать нечего (`not_merged`).
2. **Цель:** `target.space_key` и `target.parent_id` совпадают с согласованными; `target.page_id` — для
   обновления; `target.title` — заголовок страницы.
3. **Действие:** `create` (новая страница), `update` (та же страница, версия `remote_version + 1`), `noop`
   (изменений нет, версия не появится), `conflict` (публикация невозможна).
4. **Diff:** `diff_kind=new_page` — вся страница новая; `page_update` — текущая страница → новая ревизия;
   `manual_edit` — что изменили вручную после последней публикации.
5. **Проблемы** (`problems`) — блокируют. **Предупреждения** (`warnings`) — допускают публикацию, но их нужно
   понять:

   | Код | Что значит |
   |---|---|
   | `image_not_published` | вместо изображения будет текстовая отметка |
   | `diagram_as_code` | диаграмма будет показана исходным кодом |
   | `internal_link_as_text`, `link_as_text` | ссылка станет текстом |
   | `raw_html_as_text` | HTML будет показан как текст |
   | `list_start_ignored` | нумерация списка начнётся с 1 |
   | `frontmatter_page_id_ignored` | `confluence_page_id` в документе проигнорирован |
   | `managed_page_found` | найдена страница этого документа с меткой без привязки (например, после потерянного ответа) — она будет использована |
   | `version_changed` | версия страницы изменилась без изменения содержимого |

6. **Storage** (`plan.storage`) — точный текст, который будет записан.

Публиковать можно, только если `can_publish=true`: действие `create`/`update`/`noop`, проблем нет, запись разрешена.

## 4. Публикация

«Опубликовать в Confluence» (`POST /api/publications/jobs/<JOB>/publish`). Перед записью план строится заново; если состояние Confluence или
документа изменилось — `409 plan_changed` (запись не выполнялась): перечитайте задание и снова проверьте
предпросмотр. Другие отказы до записи: `503 publish_disabled`, `409 invalid_transition` (задание не в
`dry_run_ready`), `409 publication_in_progress`, `502`/`503` с кодом `confluence_*` или GitLab, если повторное
чтение перед записью не удалось (задание остаётся `dry_run_ready`).

Ответ `200` содержит задание в итоговом состоянии (раздел 5). После `published` проверьте: `page_id`,
`version_after`, состояние документа `published`, `mapping.url` ведёт на страницу в целевом пространстве,
на странице есть панель «Страница опубликована из базы знаний команды…».

## 5. Состояния задания и действия оператора

| Состояние | Что значит | Что делать |
|---|---|---|
| `pending` | задание создано, предпросмотра нет (или dry-run прервался) | dry-run |
| `validating` | идёт dry-run | подождать |
| `dry_run_ready` | предпросмотр готов | прочитать (раздел 3), опубликовать или оставить |
| `publishing` | идёт запись | подождать; после перезапуска станет `result_unknown` |
| `published` | страница создана/обновлена или изменений не было | — |
| `conflict` | ничего не записано: ручная правка, чужая страница, заголовок занят, страница пропала или перенесена | раздел 6 |
| `failed` | ничего не записано (или проверка показала, что запись не применилась) | раздел 7 |
| `result_unknown` | запись могла произойти | «Проверить результат» — раздел 8 |
| `superseded` | есть задание для более новой ревизии | работать с новым заданием |

Состояние документа: `not_published`, `published`, `outdated` (опубликована старая ревизия — подготовьте
публикацию), `disabled`, либо состояние последнего задания.

## 6. Конфликты

Код — в `error_code` задания и в `plan.problems`.

**`manual_edit` — страницу изменили в Confluence вручную.**
1. Откройте `plan.diff` («опубликовано приложением → текущее в Confluence»).
2. Если правка нужна — перенесите её в документ через предложение и MR в GitLab. После merge появится новое
   задание; оно тоже будет в `conflict`, пока не подтверждён учёт правки.
3. Подтвердите учёт: «Подтвердить ручную правку» (`POST …/acknowledge-manual-edit`). В Confluence ничего не пишется; базой становится текущая
   страница, сразу выполняется dry-run.
4. Проверьте новый diff — это ровно то, что будет **заменено** на странице. Если правка не перенесена в
   GitLab, она пропадёт.
5. Опубликуйте явно. Это единственный путь перезаписи страницы.

**`title_taken` — привязки нет, а страница с таким заголовком создана не приложением.** Страница не
меняется. Переименуйте документ (через MR) или договоритесь с владельцем страницы о переименовании; затем
повторный dry-run.

**`foreign_page` — у страницы привязки нет метки этого документа.** Метку удалили вручную или привязка
повреждена. Страница не меняется. Выясните происхождение страницы; не восстанавливайте метку вручную без
решения владельца пространства.

**`mapped_page_missing` — страница привязки не найдена.** Удалена, перенесена в недоступное место или
у учётной записи пропали права. Восстановите страницу (например, из корзины пространства) или права, затем
повторный dry-run. Если страницу не восстановить — «Создать страницу заново»
(`POST /api/publications/jobs/{id}/release-missing-page`): приложение убеждается, что страницы сейчас нет,
забывает привязку (событие `missing_page_released`) и показывает новый предпросмотр с действием `create`.

**`page_moved` — страница перенесена в другое пространство или под другого родителя.** Верните её в целевое пространство, затем
повторный dry-run. Перенос под другого родителя в том же пространстве сейчас **не** обнаруживается, и
обновление вернёт страницу под настроенного родителя (`docs/CONFLUENCE_MAPPING.md`, раздел 12).

**`confluence_version_conflict` (во время записи)** — страницу изменили между проверкой и записью. Повторный
dry-run покажет, что изменилось.

## 7. Ошибки (`failed`)

| Код | Причина | Действие |
|---|---|---|
| `not_merged` | GitLab не подтверждает merge этой ревизии через MR | публикуются только смёрженные изменения; провести изменение через MR |
| `status_not_publishable` | статус документа не в `CONFLUENCE_PUBLISH_STATUSES` | изменить статус через MR или конфигурацию (по решению владельца продукта) |
| `revision_superseded` | документ в GitLab изменился после подготовки | `prepare` заново |
| `space_not_found`, `parent_not_found` | пространство/родитель не найдены или нет прав | проверить `CONFLUENCE_TARGET_SPACE`, `CONFLUENCE_PARENT_PAGE_ID`, права учётной записи |
| `unsafe_link` | в документе ссылка `javascript:`/`data:`/`file:`/`vbscript:` | исправить документ через MR |
| `confluence_auth_failed` (401) | токен отклонён | раздел 11 |
| `confluence_forbidden` (403) | нет прав на операцию | выдать права учётной записи публикации |
| `confluence_bad_request` (400) | запрос отклонён (например, заголовок занят при переименовании) | разобрать причину |
| `confluence_unavailable`, `confluence_timeout`, `confluence_unreachable` с текстом «страница не изменена; публикацию можно повторить» | запись не дошла, проверка это подтвердила | повторить |

Повтор: «Повторить» (`POST …/reconcile`; для `failed` и `conflict` — это свежий dry-run) → проверить предпросмотр → публикация.
Ошибка публикации не влияет на GitLab: merge и предложение остаются как есть.

## 8. `result_unknown` → «Проверить результат»

Запись могла примениться, но ответ не получен (или процесс прервался). Повторная публикация и новый `prepare`
заблокированы до проверки.

«Проверить результат» (`POST /api/publications/jobs/<JOB>/reconcile`) проверяет Confluence только чтением:
- запись подтверждена → `published`, привязка сохранена (событие `write_confirmed_on_check`);
- запись не применилась → `failed`, затем сразу свежий dry-run (обычно `dry_run_ready`);
- проверить не удалось → `502 confluence_write_uncertain`, задание остаётся `result_unknown`; повторите
  позже. Не создавайте и не правьте страницу вручную, пока результат не выяснен.

## 9. Восстановление после перезапуска

При старте backend (`PublicationService.recover`, в журнале — `recovered publication jobs`):
- `validating` → `pending`: повторите dry-run;
- `publishing` → `result_unknown` с кодом `interrupted`: выполните «Проверить результат».

Задания и привязки хранятся в `publications.sqlite3` и переживают перезапуск (E2E-32).

## 10. Резервное копирование `publications.sqlite3`

Файл содержит привязки документ → страница, задания и журнал публикации (включая опубликованный storage —
это копии текстов документов). Без него приложение не знает, какие страницы его: следующая публикация будет
искать страницы по заголовку и метке, возможны конфликты.

- Где: `PUBLICATION_STATE_PATH`; в Docker — том `workspace`, `/data/workspace/publications.sqlite3`.
  Рядом — `app_state.sqlite3` (предложения), его копировать вместе.
- Как (рекомендуемая процедура, в приложении не автоматизирована): консистентная копия средствами SQLite,
  например внутри контейнера
  ```bash
  docker compose exec backend python -c "import sqlite3; s=sqlite3.connect('/data/workspace/publications.sqlite3'); d=sqlite3.connect('/data/workspace/publications.backup.sqlite3'); s.backup(d); d.close()"
  docker compose cp backend:/data/workspace/publications.backup.sqlite3 <каталог-бэкапов-вне-репозитория>/
  ```
  (для профиля `integration_mock` — через `docker compose -p skh-mock -f docker-compose.yml -f docker-compose.mock.yml`).
- Копии хранить вне репозитория (`*.sqlite3` в `.gitignore`), с правами как у секретов; срок хранения —
  по решению ИБ (PB-15, PB-17).
- Восстановление: остановить backend, заменить файл, запустить. Для затронутых документов выполнить dry-run.
  Если привязка старее страницы, появится `manual_edit` — сверить историю страницы в Confluence и только
  затем подтвердить учёт правки.
- Смена `GITLAB_PROJECT_ID` «отвязывает» все страницы: ключ привязки и метка содержат ID проекта.

## 11. Ротация токена публикации

1. Получить новый PAT для учётной записи публикации (не токен MCP, не персональный).
2. Записать его в файл секрета (`SKH_SECRETS_DIR/confluence_rest_token`), права как у остальных секретов.
3. Перезапустить backend (токен читается при старте); убедиться, что запуск не отклонён.
4. Проверить: `make readiness` (или статус «Confluence Data Center (REST, публикация)» на странице
   «Интеграции») — «Подключено», `access` соответствует режиму.
5. Отозвать старый токен в Confluence.

Признак просроченного или отозванного токена — `confluence_auth_failed`. Dry-run отвечает `503` (задание
остаётся `pending`); «Опубликовать» тоже отвечает `503` ещё на этапе повторного чтения перед записью (задание
остаётся `dry_run_ready`). Если чтение разрешено, а запись — нет, публикация завершается `failed`
(`confluence_forbidden`). Ничего не записывается. Токены не передаются в чат,
отчёты и Git.

## 12. Запрещено

- Использовать токен MCP для публикации или выдавать учётной записи публикации права вне `[TEST]`-пространства.
- Указывать page ID вручную (в документе, запросе или БД) вместо штатной привязки.
- Править опубликованные страницы вручную вместо MR в GitLab (правка станет конфликтом).
- Включать `CONFLUENCE_PUBLISH_ENABLED=true` для реального хоста без письменного разрешения и профиля `live_write_staging`.
- Удалять или менять привязки без резервной копии.

## 13. Диагностика

- Журналы: `skh.publications` (создание заданий, итог публикации, предупреждения), `skh.confluence.rest`
  (метод, путь без параметров, HTTP-код). Тел запросов, текстов страниц и токенов в журналах нет.
- История задания: `history` в `GET /api/publications/jobs/<JOB>`.
- Статус интеграции: `GET /api/integrations/status` → `confluence_publisher` (`state`, `target`, `access`,
  `capabilities`, `checked_at`).
- Read-only проверка доступности: `make readiness` (`make mock-readiness` для `integration_mock`).
