# 00 — Главная задача и порядок реализации

## Цель

Продолжить **существующий** Semantic Knowledge Hub. Реализовать локально полный путь: создание документа вручную или через demo AI → постоянный черновик → валидация → отдельная ветка GitLab → commit → MR → подтверждённый merge → GitLab knowledge sync → очередь публикации → dry-run → создание/обновление Confluence Data Center страницы через **stateful mock**.

Все операции должны быть протестированы. Реальные GitLab, Confluence MCP и Confluence REST **не подключать**, реальную запись **не включать**. Отсутствие доступа к корпоративным сервисам не должно блокировать разработку адаптеров, проверки контрактов, dry-run и mock E2E.

## Прежде чем писать код

1. Прочитай `CLAUDE.md`, `AGENTS.md`, `README.md` и релевантные `docs/` существующего проекта.
2. Проверь фактические Git branch/HEAD/status, существующие сервисы, модели, конфигурации и тесты. Не принимай сведения из задания как доказательство текущего состояния.
3. Выполни начальный `make check`, `make preflight`, при возможности `make e2e`, зафиксируй baseline.
4. Определи реализацию каждой задачи без дублирования нынешнего кода. Существующие архитектурные контракты и требования безопасности имеют приоритет; расхождения документируй.

## Этапы — строго по порядку

1. **M4.6 Authoring:** `02_DOCUMENT_AUTHORING.md` + `07_UI_UX.md`: шаблоны, создание, черновики, preview, AI demo.
2. **GitLab workflow:** `03_GITLAB_WORKFLOW.md`: добавь `create` к `update`, полноценную цепочку до синхронизации.
3. **M4 readiness:** `04_CONFLUENCE_MCP.md` + `06_MOCKS_AND_ENVIRONMENTS.md`: проверяемый read-only MCP и GitLab mock.
4. **M5 Publisher:** `05_CONFLUENCE_PUBLISHING.md`: отдельный Confluence DC REST publisher, состояния, dry-run, mapping, version conflicts.
5. **Local integration:** `06_MOCKS_AND_ENVIRONMENTS.md` + `07_UI_UX.md`: Docker профили и интерфейс статусов публикации.
6. **Security/test/hand-off:** `08_SECURITY.md`, `09_TESTS_AND_ACCEPTANCE.md`, `10_STAGING_HANDOFF.md`, `11_GIGACODE_MIGRATION.md`, `12_DELIVERABLES.md`.

После каждого этапа запускай релевантные тесты и исправляй критические ошибки до перехода к следующему.

## Неподвижные архитектурные правила

- GitHub — **код приложения**; GitLab — **источник истины командной базы знаний**; Confluence DC — **корпоративный read-only источник через MCP** плюс **публикация утверждённых страниц через REST API**; GigaCode — будущая агентная среда.
- Изменения в GitLab — только через ветку/MR; документ становится утверждённым лишь после подтверждённого merge и синхронизации.
- Публикация независима от GitLab MR: ошибка публикации не отменяет merge.
- Не создавать собственную большую LLM-оркестрацию. Не придумывать GigaCode API.
- Сохранить офлайн-режим, его сетевую изоляцию и тесты.

## Границы работы

Не используй банковские данные, корпоративные endpoint/токены, внешние AI API. Не отключай TLS. Не выполняй `git push`; не меняй `main`. Включение write в **локальном mock** допустимо только в тестовом профиле, без возможности адресовать корпоративный хост.

## Что сдавать

Запущенный локальный стек, тесты полного сценария, код адаптеров, интерфейс, dry-run и все выходные документы из `12_DELIVERABLES.md`; всё с явным различием **реально локально проверено / mock-проверено / не прошло live validation**.
