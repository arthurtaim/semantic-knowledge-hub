## 2. Только mock (не дефекты retrieval)

`KE-ADR-005` и `KE-SRC-013`: весь нужный материал в контексте (`context_ok` true до и после), extractive mock цитирует
другие предложения. В исторических живых прогонах оба кейса проходили. `mock.py` не менялся.

`KE-ST-006` стал PASS как побочный эффект. Пробы RQ-CAN-01 (стал FAIL), RQ-MS-03 и RQ-MD-01 тоже чисто генерационные:
контекст полный, mock процитировал другое. Генерационные флипы в обе стороны ожидаемы при любой смене набора термов
и контекста. Ни один не исправлялся правилом под кейс.

**Требует отдельной live-LLM-проверки** (в этой задаче запрещена, LIVE_LLM_NOT_TESTED). Что проверить:
- KE-ADR-005, KE-SRC-013, RQ-CAN-01, RQ-MS-01/03, RQ-MD-01: при полном контексте настоящая модель должна их проходить;
- что новые контексты (больше секций лучшего документа, меньше шума) не ухудшают ответы модели;
- вопросы, называющие документ по id: теперь контекст — почти только этот документ.

Опция: `SKH_LIVE_EVAL=1 make knowledge-eval-live` на синтетическом стенде, по явному разрешению.

| Изменение | Риск | Чем ограничен |
|---|---|---|
| Служебные слова не термы | вопрос только из служебных слов → «нет значимых слов» вместо поиска | так же было со стоп-словами; акронимы капслоком сохраняются (тест) |

## 4. Ограничения проверки

- Все измерения — на синтетическом корпусе из 83 документов и 24 mock-страниц. На реальной базе GitLab/Confluence
  статистика (df, доля специфических слов) другая.
- Латентность — внутрипроцессный замер на Apple M5, не Hetzner.
- `make check` на итоговом коде зелёный (exit 0). В одном из промежуточных прогонов frontend-тест
  `workBoardWindow.test.tsx`, не затронутый изменениями, упал по тайм-ауту 5 с под нагрузкой и прошёл при повторе.
  Это чувствительность к нагрузке, существовавшая до задачи (`04_TEST_RESULTS.md` §2).
- E2E — против изолированного офлайн-стенда и test doubles GitLab/Confluence, не против реальных систем.
- Holdout использован для итоговой оценки дважды: слепой run 1 и контрольный run 2 после правки по E2E, совпавший
  по каждому кейсу. Для KE-SRC-004 и KX-RAG-04 диагностика после заморозки прочитана, поэтому следующее изменение,
  нацеленное на них, требует **нового** holdout.
- Live LLM не проверялся (LIVE_LLM_NOT_TESTED). Реальные GitLab, Confluence и Hetzner не затрагивались.
