# 01 — Матрица корневых причин

## 1. Реальный путь вопроса

`question → analyze (text.analyze_query + dictionary.expand) → rank_documents (exact id / title / FTS5 AND→OR) →
passages (секции ≤ 4 документов, ≤ 6 фрагментов) → AssistantService._prepare (бюджет контекста, local sufficiency,
опционально mock Confluence) → provider → серверная проверка цитат`.

| Компонент | Файл | Лимиты и фильтры (до → после) | Где используется |
|---|---|---|---|
| Анализ запроса | `domain/text.py` | `MAX_QUERY_TERMS` **12 → 16**. Отсев только `STOPWORDS` → весь `FUNCTION_WORDS`. Стемминг суффиксами + **альтернатива для беглой гласной** | все пути: каталог, `/api/search`, ассистент, `knowledge_search`, M6 `work_ai`, metadata, skills |
| Словарь | `domain/dictionary.py`, `dictionary.yaml` | содержимое не менялось. Морфологическая альтернатива слова теперь **сохраняется** при синонимическом расширении (раньше перезаписывалась бы) | все пути |
| Ранжирование документов | `services/retrieval.py::rank_documents` | без изменений: FTS 200 кандидатов, веса колонок, статус как фильтр | все пути |
| Отбор фрагментов | `retrieval.py::passages` | 4 документа, 6 фрагментов, 1500 символов на фрагмент, бюджет 12 000 символов (не менялись). Кандидаты: **60 лучших секций всего корпуса → все подходящие секции 4 документов контекста**. Упаковка: **по 2 BM25-лучших на документ → BM25-первая + прирост покрытия** | ассистент (`/api/assistant/ask`, stream) и M5.7 `knowledge_search` (тот же метод, `max_documents = max_passages = limit`) |
| Достаточность | `services/assistant.py::local_insufficiency` | **v1 → v2** (`02_DESIGN_AND_CHANGES.md`) | только режим `local_then_external` |
| Внешний источник | `services/external.py` | без изменений: ≤ 10 кандидатов, ≤ 3 загрузки, 5 с на страницу, 12 с общий дедлайн, кэш 100 страниц / 24 ч | `local_then_external`, `external` |
| Проверка цитат | `assistant.py::_validated_response` | без изменений | все ответы |

**Согласованность путей.** `/api/search` и каталог используют `rank_documents`. Ассистент и M5.7 `knowledge_search`
используют `passages`, которая сама вызывает `rank_documents` с теми же фильтрами статуса. Новая логика лежит внутри
`passages` и `analyze`, поэтому эти пути не расходятся: порядок документов в `/api/search` и состав документов
контекста считаются одной функцией. Предварительный контекст M5.7 (обычный ask с инструментами) строится тем же
`_prepare`. Инструмент работает со снимком читателя (`snapshot.get`), так что невидимый документ не попадает ни в
кандидаты, ни в вывод (тест `test_a_document_outside_the_readers_snapshot_never_appears`).

## 2. Шесть retrieval-дефектов

Обозначения стадий: **R** — retrieval (документа нет среди 4 документов контекста); **P** — passage packing (документ
есть, нужной секции или факта нет в контексте); **X** — external (внешний источник не опрошен или опрошен зря); **G** —
generation (всё в контексте, mock процитировал другое). Трассы: `evidence/before_traces.json` и
`evidence/after_holdout_traces.json`, второй файл снят после заморозки.

## 4. Разделение retrieved / included / cited / stated

Для каждого кейса трасса отдельно фиксирует:

- `expected_rank` — retrieved;
- `context.expected_docs_in_context` и `facts_in_context` — included_in_context;
- `answer.cited` и `facts_cited` — cited;
- `facts_stated` — stated_in_answer.

Пример `KE-INTA-012` после изменений: факты retrieved, included, cited и stated есть все, а провал только в
документе-источнике (INT-002 не retrieved в топ-4). Это сознательно не названо «исправлено», хотя ответ по существу
верен. У `KE-SRC-012` провал смешанный: два факта не включены (P), а SRC-004 включён, но mock его не цитирует (G).
