# 07 — Поле `known`: обрезка вместо отказа и короткий промпт без него

Изменение разрешено владельцем 26.11.2026 после прогона на Claude: 2–3 из 40 верных решений отвергались, потому что
пункт `known` был длиннее 160 символов. Коммит `ef1c429`. Deploy и merge не выполнялись.

## 1. Что изменено

## 3. Оценка: убрать `known` из запроса к целевой слабой модели

**Можно, с сохранением обратной совместимости.** Это уже доступно: `EXTERNAL_GATE_REQUEST_KNOWN=false`.

Аргументы за:
- сервер `known` не использует: не как доказательство, не для решения, не для поиска, не для показа пользователю;
  поле только разбирается;
- меньше выходных токенов: на Claude вызов ворот быстрее на 17 % по p50 (2,4 → 2,0 с) и на 31 % по p95 (3,5 → 2,4 с);
  у слабой модели с медленной генерацией выигрыш будет заметнее;
- на одно поле с лимитами меньше — меньше поводов нарушить формат; для слабой модели это главный источник ошибок;
- на Claude качество решения не изменилось: те же 40 решений «идти / не идти».

Риски и неизвестное:
- у слабой модели перечисление `known` может работать как короткое рассуждение перед решением, и без него точность
  может снизиться — на Claude этого не видно, на целевой модели не измерено;
- `known` мог бы пригодиться позже (показать пользователю, что подтверждено локально), но сейчас не используется.

Обратная совместимость:
- разбор принимает ответы с `known` и без него;
- ответ с `known` при `REQUEST_KNOWN=false` тоже принимается (с той же обрезкой);
- формат ответа API не меняется (`evidence_gate` не содержит `known`).

**Рекомендация.** Прогнать sign-off на целевой модели в обеих конфигурациях (`--set external_gate_request_known=false`
во второй команде из `04_WEAK_MODEL.md`) и выбрать по:
- доле `invalid`;
- точности решения при данном контексте;
- p95 вызова ворот.

До этого значение по умолчанию оставлено `true`: прежний промпт, контракт из `02_MODEL_CONTRACT.md`.
