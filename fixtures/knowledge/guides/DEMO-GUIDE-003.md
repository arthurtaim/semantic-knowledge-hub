# Как проверить ограничения интеграции

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Когда использовать

Руководство пригодится, если пачка интеграции ARIS → Catalog не загрузилась, оказалась в карантине или вы
хотите заранее убедиться, что выгрузка пройдёт проверку. Ограничения интеграции задаёт DEMO-INT-003, а общий
порог полноты — регламент качества DEMO-GOV-003. Ниже порядок проверки, в котором удобно искать причину.

## Пошагово

1. **Обязательные поля.** В каждой записи должны быть заполнены `aris_object_guid`, `aris_object_name` и
   `aris_owner_role`. Запись без любого из них не проходит проверку.
2. **Глубина иерархии.** Путь модели `aris_model_path` может содержать не более **7** уровней
   (`ARIS_MAX_DEPTH = 7`). Запись с более глубоким путём не проходит проверку.
3. **Статус в источнике.** Записи с `aris_status = obsolete` отклоняются всегда — это правило маппинга,
   а не ошибка выгрузки.
4. **Порог пачки.** Посчитайте долю записей, прошедших шаги 1–3. Пачка принимается, только если прошло
   **≥ 95 %** записей (порог по умолчанию из DEMO-GOV-003). Иначе вся пачка целиком уходит в карантин
   `q_aris_rejected`.
5. **Порог датасета.** Для датасета Process Overview (DEMO-SEM-009) действует более строгое правило: полнота
   полей `process_id`, `process_name`, `owner_role` должна быть не ниже **98 %**. Проверяйте его отдельно от
   порога пачки.
6. **Код ошибки.** Ошибки проверки регистрируются с кодом `E-VAL-002` (validation failed) по классификации
   DEMO-INT-011. Повторная отправка той же пачки без исправления данных даст тот же результат, поэтому сначала
   исправьте записи в источнике.

## Пример

Инкрементальная пачка ARIS → Catalog содержит 500 записей.

- 12 записей без `aris_owner_role`, 4 записи с путём глубиной 8 уровней, 9 записей с `aris_status = obsolete`.
- Не прошли 25 записей, прошли 475: это **95 %** — порог пачки выполнен, пачка принята.
- Если бы не прошли 30 записей (прошли 470, то есть 94 %), вся пачка ушла бы в `q_aris_rejected`.

Теперь датасет. После загрузки полнота `owner_role` в Process Overview составила 97 %. Пачка при этом
корректно принята по порогу 95 %, но датасет не выполняет своё правило 98 % — это сигнал для стюарда
данных и владельца интеграции.

## Частые ошибки

- **Считают 95 % и 98 % противоречием.** Это не конфликт, а разная область применения: 95 % — общий порог для
  пачки или датасета по умолчанию (DEMO-GOV-003), 98 % — более строгое правило только для трёх полей
  Process Overview.
- **Ищут отдельные записи в карантине.** В `q_aris_rejected` уходит вся пачка, а не только записи с ошибками.
- **Считают `obsolete` сбоем.** Отклонение устаревших объектов — ожидаемое поведение.
- **Путают уровни и символы.** Ограничение 7 — это число уровней иерархии модели, а не длина строки пути.
- **Проверяют по черновику.** Правила берутся из утверждённого DEMO-INT-003; предложения в черновиках
  не меняют действующие ограничения.

## Связанные документы

- **DEMO-INT-003** — валидационные ограничения ARIS: обязательные поля, `ARIS_MAX_DEPTH = 7`, отклонение
  `obsolete`, карантин `q_aris_rejected` (шаги 1–4).
- **DEMO-GOV-003** — регламент полноты метаданных с порогом 95 % по умолчанию и правилом 98 % для Process
  Overview (шаги 4–5).
- **DEMO-SEM-009** — датасет Process Overview, на который распространяется строгий порог 98 % (шаг 5).
- **DEMO-INT-011** — классификация интеграционных ошибок и retry, откуда взят код `E-VAL-002` (шаг 6).
