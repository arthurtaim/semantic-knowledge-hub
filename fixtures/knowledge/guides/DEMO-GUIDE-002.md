# Как восстановить lineage датасета

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Когда использовать

Руководство нужно, когда требуется ответить на вопрос «откуда взялось это значение в датасете»: при разборе
расхождения, при ревью изменения атрибутов или перед тем, как опираться на поле в отчёте. Восстановить
происхождение данных (data lineage, линейдж) — значит пройти цепочку от атрибута датасета через маппинг и поток
интеграции до поля в системе-источнике. Опорная схема цепочки — [[DEMO-INT-014]].

## Пошагово

Цепочка для датасета Process Overview (DEMO-SEM-009):

**ARIS (DEMO-SRC-002) → [[DEMO-INT-001]] (поток) → [[DEMO-INT-002]] (маппинг полей) → BusinessProcess
(DEMO-SEM-002) → Process Overview (DEMO-SEM-009)**

Идти удобнее в обратную сторону — от датасета к источнику.

1. **Откройте запись датасета и прочитайте `lineage_ref`.** Это поле Process Overview указывает, по какой
   цепочке получена запись. Рядом лежат `source_system` (например, `SYS-ARIS`) и `source_changed_at` — момент
   изменения объекта в источнике.
2. **Перейдите к логической сущности.** Process Overview выведен (`derived_from`) из логической модели
   BusinessProcess (DEMO-SEM-002). Убедитесь, что нужный атрибут — например, `owner_role` — есть в сущности.
3. **Найдите правило маппинга.** В DEMO-INT-002 найдите строку, где атрибут сущности является целевым полем.
   Для `owner_role` источник — `aris_owner_role`; для `process_id` — `aris_object_guid` через таблицу
   соответствия `MAP_ARIS_PROCESS`; для `process_name` — `aris_object_name` после нормализации.
4. **Проверьте поток.** DEMO-INT-001 описывает, как данные забираются из ARIS и попадают в каталог:
   инкрементальная загрузка каждые 6 ч пакетами по 500 записей. По `source_changed_at` можно понять, в какой
   загрузке пришло значение.
5. **Дойдите до источника.** В профиле ARIS (DEMO-SRC-002) найдите исходное поле и его смысл.
6. **Сверьте со схемой.** DEMO-INT-014 содержит ту же цепочку целиком; если ваш путь отличается от схемы,
   это повод открыть вопрос владельцу интеграции, а не «достраивать» связь самостоятельно.

В графе знаний тот же путь виден как рёбра: DEMO-INT-001 `consumes` DEMO-SRC-002, DEMO-INT-002 `depends_on`
DEMO-INT-001 и `maps_to` DEMO-SEM-002, DEMO-SEM-009 `derived_from` DEMO-SEM-002.

## Пример

Вопрос: откуда в записи `PRC-000417` «Согласование заявки (демо)» значение `lifecycle_state = active`?

1. В записи Process Overview: `source_system = SYS-ARIS`, `lineage_ref` указывает на цепочку ARIS → Catalog.
2. В BusinessProcess атрибут `lifecycle_state` — состояние жизненного цикла процесса.
3. В DEMO-INT-002: `aris_status` → `lifecycle_state`, причём `released` → `active`, `in_work` → `draft`, а
   записи с `obsolete` отклоняются.
4. Значит, в ARIS у объекта был статус `released`. Поток DEMO-INT-001 доставил его в ближайшую загрузку после
   `source_changed_at`.

Итог: `active` — результат правила преобразования, а не значение, которое хранится в ARIS буквально.

## Частые ошибки

- **Останавливаются на датасете.** `lineage_ref` — это указатель на цепочку, а не доказательство; его нужно
  пройти до источника.
- **Ищут поле источника по имени датасета.** В ARIS нет поля `owner_role`; есть `aris_owner_role`, а связь
  задаёт маппинг DEMO-INT-002.
- **Забывают про нормализацию.** `process_name` не равен `aris_object_name` побуквенно: название
  нормализуется по справочникам.
- **Опираются на устаревший поток.** Старая ночная полная выгрузка ARIS (DEMO-INT-018) устарела; актуальная
  цепочка идёт через DEMO-INT-001.
- **Путают lineage и зависимость.** Рёбра `depends_on` между регламентами — это не происхождение данных;
  для lineage важны `consumes`, `maps_to` и `derived_from`.

## Связанные документы

- **DEMO-INT-014** — схема lineage из источника в датасет; эталон, с которым сверяется найденный путь (шаг 6).
- **DEMO-SEM-009** — датасет Process Overview с полем `lineage_ref`, с которого начинается восстановление.
- **DEMO-SRC-002** — профиль ARIS, конечная точка цепочки (шаг 5).
- **DEMO-INT-001** — поток ARIS → Catalog, через который проходят данные (шаг 4).
- **DEMO-INT-002** — маппинг полей ARIS → Catalog, где находится правило для каждого атрибута (шаг 3).
- **DEMO-SEM-002** — логическая модель BusinessProcess, промежуточное звено между маппингом и датасетом (шаг 2).
- **DEMO-INT-018** — устаревшая ночная выгрузка ARIS; упомянута в «Частых ошибках» как путь, по которому
  lineage восстанавливать нельзя.
