# Решение о версионируемых шаблонах

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

Запись архитектурного решения (ADR, Architecture Decision Record) о том, что происходит с документами, когда
меняется шаблон, по которому они написаны.

## Контекст

Новые документы базы знаний создаются из машиночитаемых шаблонов (реестр `backend/app/document_templates/`);
человекочитаемые описания шаблонов — это документы [[DEMO-PROC-006]]…[[DEMO-PROC-009]]. Шаблоны развиваются.
Пример: шаблон Integration Specification v1 содержит восемь разделов — Назначение, Источник и получатель,
Передаваемые данные, Маппинг, Бизнес-правила, Ограничения, Ошибки, Требования. Версия v2 добавляет ещё четыре:
Data Quality Rules, Data Lineage, Update Frequency, Validation Constraints (DEMO-PROC-006).

Если изменить шаблон «на месте», все черновики, начатые по v1, внезапно становятся «неполными»: валидатор
требует разделы, о которых автор не знал, ревьюер видит в diff изменения, не связанные с содержанием, а уже
согласованная структура ломается посреди ревью.

## Решение

1. **У каждого шаблона есть целочисленная версия** (`template_version`, целое число ≥ 1). Изменение набора
   обязательных разделов или их смысла выпускается как новая версия; прежняя версия остаётся в реестре только
   для чтения.
2. **Новая версия применяется только к новым документам** — созданным после её выпуска.
3. **Старые черновики сохраняют свою версию шаблона.** Во frontmatter черновика записаны `template` и
   `template_version`; черновик проверяется по той версии, с которой был создан, и не получает
   предупреждений о разделах, появившихся позже.
4. **Миграция на новую версию — только явное действие автора**, оформленное как обычная правка с ревью.
   Ни синхронизация, ни ассистент не переносят документ на новую версию шаблона автоматически.
5. Утверждённые документы не перепроверяются по новой версии задним числом; владелец может мигрировать документ
   при очередной существенной ревизии.
6. Когда выпускать новую версию и как её объявлять, определяет политика [[DEMO-PROC-010]].

## Рассмотренные альтернативы

- **Один изменяемый шаблон без версий.** Отклонено: изменения действуют задним числом и ломают начатую работу.
- **Копия шаблона внутри каждого документа без номера версии.** Отклонено: невозможно понять, какие правила
  проверки применимы к документу, и нельзя собрать статистику по версиям.
- **Семантическое версионирование шаблонов (MAJOR.MINOR.PATCH).** Отклонено как избыточное: у шаблона меняется
  только структура, и целого номера достаточно. Версии самих документов по-прежнему MAJOR.MINOR.

## Последствия

- Пример: черновик спецификации интеграции создан по Integration Specification с `template_version: 1`. После
  выпуска v2 он по-прежнему проверяется по восьми разделам v1, и отсутствие раздела Data Lineage не считается
  ошибкой. Новая интеграция, созданная после выпуска v2, сразу получает двенадцать разделов.
- Реестр хранит несколько версий одного шаблона; валидатору нужна пара «шаблон + версия».
- Отчёт по базе может показать распределение документов по версиям шаблонов и черновики, оставшиеся на старых
  версиях.
- Старую версию шаблона можно вывести из употребления только после того, как закрыты все черновики, которые на
  неё ссылаются.
- Шаблон Dataset Specification v1 (Overview, Source Systems, Business Entities, Attributes, Mapping Rules, Data
  Quality, Refresh Policy, Access Restrictions, Related Docs — DEMO-PROC-007) подчиняется тем же правилам.

## Статус решения

Принято (accepted), версия 1.0. Решение касается шаблонов документов базы знаний; шаблоны сообщений
интеграций и схемы данных регулируются отдельно (совместимость схем — в интеграционных регламентах).
