# Data Quality Monitor: контроль качества

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

`SYS-DQM` — условный монитор качества данных (data quality, DQ). Он измеряет метаданные после каждой загрузки и публикует результаты проверок. Пороги и определения DQM не придумывает: они берутся из стандартов качества — полнота (DEMO-GOV-003), согласованность (DEMO-GOV-004), актуальность (DEMO-GOV-005). DQM только измеряет и сигнализирует стюардам; данные он не исправляет и записи не удаляет.

## Границы (Scope)

В границах: проверки активов Data Catalog, датасетов Process Overview, Dependency Graph и Source Coverage, счётчики интеграционных ошибок. Вне границ: исправление записей, карантин и согласование порогов. Решение о карантине `q_aris_rejected` принимает поток ARIS по своим валидационным ограничениям; DQM получает от него метрику `aris_batch_pass_rate` и число записей в карантине. Исторические снимки Archive Store не проверяются.

## Сущности и идентификаторы

- **Проверка** — `check_id` из стандартов: `DQ-COMP-001`, `DQ-CONS-001`, `DQ-CONS-002`, `DQ-FRESH-001`, `DQ-REF-001`; собственная проверка объёма — `DQ-VOL-001`.
- **Результат** — строка таблицы `dq_check_results`: `check_id`, `target_id`, `metric`, `value`, `threshold`, `result` (`pass`, `warn`, `fail`), `measured_at`.
- **ADR — Average Daily Rows** (среднее число строк в сутки) — метрика объёма. Внимание: в остальной базе ADR означает Architecture Decision Record (запись архитектурного решения). В DQM и его отчётах ADR — всегда метрика объёма.

## Выгружаемые метаданные (Outputs)

| Проверка | Что измеряет | Порог |
|---|---|---|
| `DQ-COMP-001` (полнота) | `completeness_score` — доля заполненных значений обязательных атрибутов в пакете или датасете | не ниже 95 %; для Process Overview — не ниже 98 % по `process_id`, `process_name`, `owner_role` |
| `DQ-CONS-001` (согласованность) | код отсутствует в действующем справочнике, включая коды систем `SYS-*` | 100 % записей без нарушений |
| `DQ-CONS-002` (согласованность) | у одного `process_id` разные названия в разных системах или датасетах | не менее 99 % записей без нарушений |
| `DQ-FRESH-001` (актуальность) | возраст изменения от `source_changed_at` до появления в каталоге | не более 24 ч для каталога; не более 12 ч для Process Overview |
| `DQ-REF-001` (ссылочная целостность) | висячие ссылки после загрузки ARIS и после изменения `MAP_ARIS_PROCESS` | отчёт для стюарда |
| `DQ-VOL-001` (объём) | строки за сутки против ADR | отклонение не более 30 % |

Разница между 95 % и 98 % — разница области применения, а не противоречие: общий порог действует для всех пакетов и датасетов, строгий — только для трёх полей датасета Process Overview.

ADR считается для каждого потока как среднее число загруженных строк за последние 7 полных суток. Типичные значения: ARIS → Catalog — около 1 200 строк в сутки (четыре инкремента), ERP → Semantic Layer — около 7 300 строк (ночной full refresh каталога колонок).

Дополнительно DQM собирает счётчики сообщений в `dlq.metadata.v1` по кодам ошибок `E-MAP-001`, `E-VAL-002`, `E-SRC-003` и показывает их рядом с полнотой и актуальностью. Проверки запускаются после каждой загрузки; сводный отчёт с трендом полноты за 30 дней формируется ежедневно в 07:00 (условное время).

## Ограничения

- DQM не меняет статусы документов и данных: результат `fail` — сигнал стюарду и задача владельцу, а не автоматическое действие.
- Новый порог применяется только после выхода утверждённой версии стандарта качества.
- Метрика ADR не применяется к CDC-потоку CRM → MDM: число событий там зависит от активности пользователей, и отклонение от среднего не говорит о качестве.
- Пустой пакет по полноте не оценивается и фиксируется как «нет данных».
- SLA на реакцию по результатам проверок не определён.

## Владельцы и роли

- **Owner** (владелец): роль `src-owner-dqm` — набор проверок и их расписание.
- **Steward** (стюард): роль `src-steward-dqm` — разбор `fail` и `warn` вместе со стюардами источников.
- **Reviewer** (ревьюер): представитель команды управления данными при изменении порогов.

## Пример

Пакет ARIS из 500 записей: заполнено 1 470 из 1 500 значений обязательных атрибутов — `completeness_score` 98,0 %, `DQ-COMP-001` = `pass` (порог 95 %). В датасете Process Overview `owner_role` заполнен в 979 строках из 1 000 — 97,9 %, это `fail`, потому что для этого поля действует порог 98 %. Объём ARIS за сутки — 610 строк при ADR 1 200: отклонение 49 %, `DQ-VOL-001` = `warn`; в счётчиках DLQ две загрузки с кодом `E-SRC-003` (источник недоступен).
