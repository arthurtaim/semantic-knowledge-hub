# MDM: мастер-данные

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

`SYS-MDM` — условная система управления мастер-данными (Master Data Management). Она ведёт эталонные копии всех справочников учебной модели: собственные справочники семантического слоя и справочники, первичный источник которых — CRM. Семантический слой получает их копию только для чтения и по ним нормализует названия. Для мастер-записей (golden record) MDM — первоисточник; для исходных карточек CRM — нет.

## Границы (Scope)

В границах: мастер-записи справочников и их связи с исходными ключами. Справочники, которые ведутся прямо в MDM: `DICT_OWNER_ROLE`, `DICT_SYSTEM_CODE`, `DICT_LIFECYCLE_STATE`, `DICT_DEPENDENCY_TYPE`, `DICT_NAME_SYNONYM`. Справочники из CRM: каналы, сегменты и типы обращений. Вне границ: клиентские данные, процессы, изделия, финансовые данные. Всего около 7 000 элементов справочников, из них около 900 пришли из CRM. Внешний справочник External Registry — только кандидат на подключение: его профиль — черновик.

## Сущности и идентификаторы

- **Мастер-запись** — `mdm_golden_id`, формат `MDM-` + 8 цифр (например, `MDM-00031942`). Идентификатор присваивает MDM по своим правилам; поток CRM → MDM его не вычисляет.
- **Элемент справочника** — пара `dict_code` + `item_code`; `item_code` уникален внутри справочника и не переиспользуется.
- **Название** — `item_name`, нормализованное.
- **Исходные ключи** — `mdm_source_keys`: пары `система:идентификатор`, например `SYS-CRM:crm-card-demo-42`. У справочников, которые ведутся прямо в MDM, исходного ключа нет.
- **Состояние** — `active` или `retired`.
- **Ответственный стюард** — `mdm_steward_role`.

## Выгружаемые метаданные (Outputs)

- **Справочники для семантического слоя**: элемент с полями `dict_code`, `item_code`, `item_name`, `is_active`, `valid_from` — копия только для чтения.
- **Применение событий CRM** (поток CRM → MDM, задержка до 15 минут): `create` и `update` создают или обновляют мастер-запись, `delete` переводит её в `retired`.
- **Поиск дублей**: если две карточки CRM одного типа похожи по названию, MDM считает `mdm_match_score` от 0 до 100. При 90 и выше карточки автоматически привязываются к одной мастер-записи; от 70 до 89 — создаётся задача стюарду в очереди `mdm_review_queue`; ниже 70 — записи остаются разными.
- **Уведомления**: изменения мастер-записей MDM публикует в Event Hub (`source_system = SYS-MDM`), чтобы потребители узнали о новой ревизии справочника.

## Ограничения

- `mdm_golden_id` и `item_code` не переиспользуются; выведенный элемент (`retired`) хранится для истории.
- Решение стюарда по спорной паре (70–89) автоматика не отменяет.
- MDM не правит карточки в CRM, а только фиксирует их соответствие мастер-записи.
- Аббревиатура MDM в этой базе значит Master Data Management. В текстах ARIS встречается «MDM-модель» в значении модели метаданных — это другое понятие, к `SYS-MDM` отношения не имеет.
- SLA для обработки событий не определён.

## Владельцы и роли

- **Owner** (владелец): роль `src-owner-mdm` — правила сопоставления и пороги `mdm_match_score`.
- **Steward** (стюард): роль `src-steward-mdm` — решения по спорным парам, ведение справочников.
- **Reviewer** (ревьюер): представитель семантической команды при изменении справочников нормализации.

## Пример

Из CRM пришли события по двум каналам: `crm-card-demo-42` «Мобильное приложение (демо)» и `crm-card-demo-57` «Приложение для смартфона (демо)». MDM оценил сходство: `mdm_match_score = 76`. Значение в диапазоне 70–89, поэтому создана задача стюарду. Стюард подтвердил, что это один канал, и `mdm_source_keys` мастер-записи `MDM-00031942` теперь содержит оба ключа: `SYS-CRM:crm-card-demo-42` и `SYS-CRM:crm-card-demo-57`. Изменение ушло в Event Hub. При оценке 93 привязка прошла бы без участия стюарда.
