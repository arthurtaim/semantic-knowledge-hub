# CATIA: условная модель метаданных изделий

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Условная система `SYS-CATIA` в учебном сценарии хранит конструкторские данные изделий. Семантический слой берёт из неё только метаданные структуры изделия: какие детали существуют, в какие сборки они входят, какая ревизия актуальна и к какому классу материала относится деталь. Из этих метаданных строятся бизнес-объекты BusinessObject в каталоге и граф зависимостей (датасет Dependency Graph).

## Границы (Scope)

В границах: детали и сборки, связь «входит в сборку», буква ревизии, класс материала. Вне границ: 3D-геометрия, чертежи, допуски, расчёты, файлы моделей, история согласований внутри CATIA. В источнике около 40 000 изделий, из них примерно 3 200 сборок верхнего и промежуточного уровней; суточная дельта обычно — от нескольких десятков до нескольких сотен изделий.

## Сущности и идентификаторы

- **Изделие (деталь)** — `catia_part_number`, номер вида `CP-` + 6 цифр (в учебных примерах `CP-100010`, `CP-104233`). Номер уникален в источнике и не переиспользуется.
- **Сборка** — тоже изделие, на которое ссылаются другие. Ссылка на родительскую сборку хранится в поле `assembly_ref`; у корневой сборки оно пустое.
- **Ревизия** — `revision_letter`: заглавные латинские буквы `A`, `B`, … `Z`, после `Z` идёт `AA`. Новая ревизия не меняет `catia_part_number`.
- **Класс материала** — `material_class` из закрытого списка: `MC-STEEL`, `MC-ALU`, `MC-COMPOSITE`, `MC-ASSEMBLY` (для сборок), `MC-OTHER`.

## Выгружаемые метаданные (Outputs)

Выгрузка содержит четыре поля:

| Поле CATIA | Смысл | Куда попадает |
|---|---|---|
| `catia_part_number` | номер изделия | `node_id` в Dependency Graph и идентификатор BusinessObject |
| `assembly_ref` | родительская сборка | `depends_on_node_id` в Dependency Graph |
| `revision_letter` | актуальная ревизия | атрибут `revision` бизнес-объекта |
| `material_class` | класс материала | атрибут `material_class` бизнес-объекта |

Каждая связь «изделие → сборка» получает `dependency_type = assembly` и `source_system = SYS-CATIA`. Точное правило построения `node_id` из номера изделия задаёт маппинг полей (DEMO-INT-005).

Режим — суточная дельта, ежедневно в 02:30 (условное время): в выгрузку попадают изделия, у которых после предыдущего запуска появилась новая ревизия или изменилась ссылка на сборку. Отдельного размера пакета нет — дельта загружается одним запуском. CDC-событий CATIA не публикует. Поток в каталог описан в DEMO-INT-004.

## Ограничения

- `catia_part_number` обязателен; запись без него не принимается.
- `assembly_ref` должна указывать на существующее изделие; ссылка на неизвестную сборку не создаёт связь.
- Циклы в составе сборки недопустимы: изделие не может прямо или косвенно входить само в себя.
- Ревизия не может «откатиться»: запись с ревизией младше уже известной отклоняется.
- `material_class` заполняется только из закрытого списка; иных значений источник не допускает.
- Изменения, сделанные после запуска 02:30, видны в каталоге только на следующий день.
- SLA для выгрузки не определён.

## Владельцы и роли

- **Owner** (владелец): роль `src-owner-catia` — состав полей и закрытый список `material_class`.
- **Steward** (стюард): роль `src-steward-catia` — разбор ссылок на неизвестные сборки, циклов и откатов ревизий.
- **Reviewer** (ревьюер): представитель семантической команды при изменении состава выгрузки.

Роли назначены по правилам DEMO-SRC-012.

## Пример

Фрагмент суточной дельты (вымышленные значения):

```
catia_part_number;assembly_ref;revision_letter;material_class
CP-100010;;B;MC-ASSEMBLY
CP-104233;CP-100010;C;MC-STEEL
```

Изделие `CP-104233` (ревизия `C`, класс `MC-STEEL`) входит в корневую сборку `CP-100010`. Оба изделия становятся бизнес-объектами, а в графе зависимостей появляется одно ребро от `CP-104233` к `CP-100010` с `dependency_type = assembly`. У корневой сборки исходящего ребра нет. Если завтра выйдет ревизия `D` изделия `CP-104233`, номер не изменится — обновится только атрибут ревизии.
