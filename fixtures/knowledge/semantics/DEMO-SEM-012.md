# Правила разрешения неоднозначных сущностей

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

**Статус: на ревью (`in_review`).** Документ не является утверждённым источником (authority нет). До
утверждения действуют только ключи идентичности из логических моделей BusinessProcess и BusinessObject, а
все спорные случаи разбирает стюард данных вручную.

## Назначение

Документ предлагает правила, по которым семантический слой и поиск решают, одна ли это сущность или
разные, когда названия совпадают или похожи. Типичные случаи: одинаковое название у процесса в ARIS и у
сборки в CATIA, два процесса с одним названием в разных ветках модели, синонимы и сокращения, аббревиатуры
с двумя значениями.

## Определение

- **Омоним** — разные сущности с одинаковым ключом названия `name_key`.
- **Синоним** — одна сущность под разными названиями; признаётся только при наличии записи в
  `DICT_NAME_SYNONYM`.
- **Неоднозначный случай** — ситуация, которую правила 1–5 не разрешили; оформляется как запись с
  идентификатором `AMB-` и 4 цифры и попадает в очередь стюарда `q_entity_ambiguous`.

Правила разрешения (по порядку):

1. **Идентичность определяется ключом, а не названием.** Ключ — тип сущности + идентификатор:
   `process_id` для BusinessProcess, `object_id` с префиксом системы (например, `SYS-CATIA:CP-100010`) для
   BusinessObject.
2. **Разные типы или разные источники — разные сущности.** Процесс ARIS и сборка CATIA с одинаковым
   названием никогда не объединяются автоматически; в результатах поиска показываются обе с указанием типа
   и источника.
3. **Омонимы внутри одного источника** сохраняются как разные сущности и различаются контекстом:
   `process_path` для процессов, `object_class` и `parent_object_id` для объектов. Если совпадает и
   контекст, создаётся случай `AMB-*`.
4. **Синонимы** связываются только записью в `DICT_NAME_SYNONYM`; нечёткое сравнение названий не
   применяется.
5. **Аббревиатуры с двумя значениями** (ADR, MDM) толкуются по контексту согласно глоссарию; если контекст
   не позволяет выбрать, ответ называет оба значения.
6. **Конфликт требований** между документами (например, два правила слияния) не решается произвольным
   выбором — применяется порядок работы с конфликтующими требованиями.
7. **Предложение, не утверждено:** автоматически объединять позицию ERP и деталь CATIA, если совпадают
   `name_key` и `material_class`. Вопрос открыт на ревью; до решения такие пары уходят стюарду.

## Атрибуты

Запись неоднозначного случая:

| Атрибут | Тип | Обязательный | Описание | Источник |
|---|---|---|---|---|
| `case_id` | string | да | Идентификатор `AMB-` и 4 цифры | Выдаётся при создании случая |
| `entity_type` | enum | да | `BusinessProcess`, `BusinessObject` или `term` | Правило, создавшее случай |
| `candidate_keys` | list | да | Ключи сущностей-кандидатов, не менее двух | Правила 1–3 |
| `name_key` | string | да | Общий ключ названия | Нормализация по справочникам |
| `resolution` | enum | да | `pending`, `distinct` (разные) или `same` (одна сущность) | Стюард данных |
| `resolved_by_role` | string | нет | Роль, принявшая решение | Стюард данных |
| `resolved_at` | datetime (UTC) | нет | Момент решения | Стюард данных |

## Связи с другими сущностями

- Опирается на `name_key` и `DICT_NAME_SYNONYM` из правил нормализации.
- Применяется к BusinessProcess и BusinessObject; ключи идентичности берутся из их логических моделей.
- Для аббревиатур использует значения из глоссария семантического слоя.

## Ограничения

1. Решение `same` для пары из разных источников возможно только вручную, стюардом данных, и требует записи
   в `DICT_NAME_SYNONYM`; автоматически такое решение не принимается.
2. Решение никогда не меняет Process ID и `object_id`.
3. Случай `AMB-*` без решения не блокирует загрузку: обе сущности сохраняются как разные (`pending`
   трактуется как `distinct`).
4. Пока документ на ревью, правило 7 не применяется.

## Пример

Название «Сборка узла крепления (демо)» встречается дважды, `name_key` = `сборка узла крепления демо`:

| Источник | Тип | Ключ | Контекст |
|---|---|---|---|
| ARIS (`SYS-ARIS`) | BusinessProcess | `PRC-000512` | Процесс сборки в ветке «Демо-модель/Производство» |
| CATIA (`SYS-CATIA`) | BusinessObject | `SYS-CATIA:CP-100010` | Сборка верхнего уровня, класс `assembly`, название задал стюард |

По правилу 2 это разные сущности. На вопрос «кто владелец сборки узла крепления» ответ должен уточнить,
какая сущность имеется в виду, или показать обе с источниками.

Второй случай: в ARIS два процесса «Согласование заявки (демо)» — `PRC-000417` с путём
«Демо-модель/Заявки/Согласование» и `PRC-000588` с путём «Демо-модель/Розница/Согласование». Контекст `process_path` различается, правило 3 оставляет их разными без
случая `AMB-*`.
