# Датасет Process Overview

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Обзор

Process Overview (`DS-001`) — витрина действующих бизнес-процессов для потребителей семантического слоя:
один процесс — одна строка с идентификатором, названием, ролью-владельцем, временем последнего изменения,
оценкой полноты записи и ссылкой на происхождение данных (lineage). Датасет описан по логической модели
Dataset и выдаётся потребителям через Consumer API.

## Источники

- Условная система ARIS (`SYS-ARIS`) — через инкрементальный поток ARIS → Catalog.
- Физическая таблица `sl_process_metadata`: из неё датасет читает текущее состояние процессов, переводя
  физические колонки обратно в логические атрибуты.
- Справочник `DICT_OWNER_ROLE` (MDM) — для получения значения роли по коду `owner_role_code`.

## Бизнес-сущности

BusinessProcess. В датасет попадают только процессы с `lifecycle_state = active`; черновики (`draft`) не
выдаются, поэтому атрибута `lifecycle_state` в датасете нет.

## Атрибуты

| Атрибут | Тип | Обязательный | Описание | Источник |
|---|---|---|---|---|
| `process_id` | string | да | Process ID, `PRC-` и 6 цифр, уникален в датасете | BusinessProcess.`process_id` |
| `process_name` | string | да | Нормализованное название процесса | BusinessProcess.`process_name` |
| `owner_role` | string | да | Роль-владелец в том же виде, что в каталоге (не код справочника) | BusinessProcess.`owner_role`; физически — `owner_role_code` + `DICT_OWNER_ROLE` |
| `source_system` | string | да | Код системы-источника, всегда `SYS-ARIS` | BusinessProcess.`source_system` |
| `source_changed_at` | datetime (UTC) | да | Последнее изменение процесса в ARIS | BusinessProcess.`source_changed_at` |
| `completeness_score` | decimal(4,1) | нет | Показатель полноты сборки в процентах, от 0.0 до 100.0 | Вычисляется при каждой сборке |
| `lineage_ref` | string | да | Ссылка на цепочку происхождения: `LIN-ARIS-` + `process_id` | Вычисляется при сборке |

`completeness_score` считается по формуле стандарта полноты: заполненные обязательные значения / (число
записей × число обязательных атрибутов) × 100, с округлением вниз до одного знака. Значение относится к
сборке целиком и одинаково во всех её строках: потребитель видит полноту, не обращаясь к монитору качества.
Сам атрибут в расчёт полноты не входит.

## Правила качества

1. **Полнота ключевых атрибутов — не ниже 98 %.** Каждый из атрибутов `process_id`, `process_name` и
   `owner_role` должен быть заполнен не менее чем в 98 % строк датасета. Это scope-specific stricter rule — более строгое правило для
   области одного датасета поверх общего порога полноты 95 % из стандарта DEMO-GOV-003. Противоречия нет:
   общий стандарт задаёт минимум для всех пакетов и датасетов, а Process Overview ужесточает его только для
   трёх ключевых атрибутов и только у себя. Для остальных атрибутов действует 95 %.
2. **Актуальность — не старше 12 ч.** Это тоже более строгое правило для области датасета: для метаданных
   каталога в целом допускается 24 ч (DEMO-GOV-005). Поток ARIS → Catalog работает каждые 6 ч, поэтому
   порог 12 ч переживает один пропущенный запуск, но не два.
3. **Уникальность.** `process_id` уникален; дубликат останавливает сборку.
4. **Формат.** `process_id` соответствует контракту Process ID; `lineage_ref` строится только из валидного
   `process_id`.
5. **Последствия нарушения.** Если правило 1, 2 или 3 нарушено, новая сборка не публикуется, потребители
   продолжают получать предыдущую сборку, монитор качества данных (`SYS-DQM`) фиксирует нарушение.

SLA для датасета не определён: 12 ч — порог актуальности, а не соглашение об уровне сервиса.

## Политика обновления (Refresh Policy)

Инкрементальная пересборка после каждого запуска потока ARIS → Catalog: 00:00, 06:00, 12:00 и 18:00
(условное время). Пересборка занимает до 30 мин и затрагивает только строки с изменённым `record_hash` в
физической таблице. Полная пересборка выполняется вручную владельцем датасета после изменения правил.

## Ограничения доступа

- `demo-reader` — чтение датасета и его описания.
- `demo-editor` — предложение изменений описания (через ревью).
- `demo-approver` — утверждение изменений описания.

Персональных данных в датасете нет: `owner_role` содержит роль, а не имя человека. Потребители получают
данные только через Consumer API: синтетический контракт `GET /demo/v1/process-overview?process_id=PRC-000417`
(не реальный адрес), страница 100 записей, не более 60 запросов в минуту на потребителя.
