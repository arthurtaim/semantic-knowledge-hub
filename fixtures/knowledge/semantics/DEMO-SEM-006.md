# Маппинг логической и физической моделей

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Документ фиксирует, как каждый атрибут логической модели BusinessProcess (DEMO-SEM-002) попадает в колонку
физической таблицы `sl_process_metadata` (DEMO-SEM-005), и задаёт общий формат реестра таких соответствий.
Это маппинг «логическая модель → физическая модель». Его не следует путать с интеграционным маппингом
«поле ARIS → поле каталога», где, например, `aris_object_guid` превращается в `process_id`.

## Определение

Соответствия хранятся в реестре `MAP_LOGICAL_PHYSICAL`. Одна строка реестра связывает:

- **логическую сторону** — сущность и атрибут (например, BusinessProcess.`owner_role`);
- **физическую сторону** — систему, таблицу, колонку и физический тип;
- **правило преобразования** и состояние `mapping_state`: `mapped` (правило есть) или `unmapped`
  (колонка описана, но логического атрибута для неё нет).

Строки для собственных таблиц семантического слоя ведёт команда семантического слоя, они получают
идентификаторы `LPM-` и 3 цифры. Один атрибут может давать несколько колонок; колонка без логического
атрибута считается технической и в реестр как `mapped` не попадает.

## Атрибуты

| Логический атрибут | Тип | Обязательный | Физическая колонка и правило | Источник |
|---|---|---|---|---|
| `process_id` | string | да | `LPM-001` → `process_id` без преобразования; формат проверяет `ck_process_id_format` | DEMO-SEM-002 |
| `process_name` | string | да | `LPM-002` → `process_name` без преобразования (значение уже нормализовано) | DEMO-SEM-002 |
| `process_name` | string | да | `LPM-003` → `process_name_key`: нижний регистр, «ё» → «е», пунктуация удаляется, пробелы схлопываются | Правила DEMO-SEM-008 |
| `process_path` | string | нет | `LPM-004` → `process_path` без преобразования и `path_depth` = число сегментов между `/` | DEMO-SEM-002 |
| `owner_role` | string | да | `LPM-005` → `owner_role_code`: поиск кода в `DICT_OWNER_ROLE` по значению роли | Справочник MDM |
| `lifecycle_state` | enum | да | `LPM-006` → `lifecycle_code`: `active` → `A`, `draft` → `D` | DEMO-SEM-002 |
| `source_system` | string | да | `LPM-007` → `source_system_code` без преобразования | DEMO-SEM-002 |
| `source_changed_at` | datetime | да | `LPM-008` → `src_changed_ts`: приведение к UTC, точность до секунды | DEMO-SEM-002 |

Все восемь строк имеют `mapping_state = mapped`. Колонки без логического атрибута (технические):
`source_object_id`, `record_hash`, `load_batch_id`, `loaded_at`. Колонка `path_depth` производная:
логического атрибута «глубина» нет.

## Связи с другими сущностями

- **Обратное чтение.** При сборке датасетов правила применяются в обратную сторону: `owner_role_code` →
  `owner_role` по тому же справочнику, `lifecycle_code` → `lifecycle_state`. Потребитель видит логические
  имена, а не физические.
- **Колонки ERP.** Поток ERP → Semantic Layer (DEMO-INT-007) каждую ночь записывает в этот же реестр строки,
  у которых физическая сторона — таблица и колонка ERP (`SYS-ERP`), а логическая — атрибут BusinessObject.
  Логическую сторону поток назначает только по своей таблице правил `MAP_ERP_ATTRIBUTE`; колонка без
  правила получает `unmapped`. Совпадение имён колонки и атрибута правилом не считается.
- **Поля CATIA.** Для CATIA в реестре четыре строки — по одной на поле снимка (`catia_part_number`,
  `assembly_ref`, `revision_letter`, `material_class`) с логической стороной BusinessObject; все в состоянии
  `mapped`, их ведёт команда семантического слоя по маппингу CATIA → Catalog.
- **Покрытие.** Доля строк `mapped` по каждой системе измеряется датасетом Source Coverage
  (DEMO-SEM-011) — он объявляет связь `derived_from` на этот маппинг.
- Ссылочную целостность реестра (каждое правило ссылается на существующий атрибут и существующую колонку)
  проверяют правила ссылочной целостности группы управления.

## Ограничения

1. У каждого обязательного логического атрибута BusinessProcess есть хотя бы одно правило `LPM-*`.
2. Правило `LPM-005` не подставляет значение по умолчанию: если роль не найдена в `DICT_OWNER_ROLE`,
   запись получает ошибку `E-MAP-001` (mapping not found) и в таблицу не пишется.
3. Правило не может менять смысл атрибута — только представление (код вместо значения роли, UTC вместо
   локального времени, буква вместо слова).
4. Идентификатор правила `LPM-*` не используется повторно; изменение правила — новая версия документа.
5. Техническая колонка не может появиться в датасете без добавления логического атрибута.
6. Строка, ссылающаяся на несуществующий логический атрибут, в реестр не записывается.

## Пример

Типичная ошибка — считать `owner_role` и `owner_role_code` одним полем. Логический атрибут `owner_role`
содержит роль в том виде, в каком её знают ARIS и каталог: `process-owner-requests-demo`. Правило `LPM-005`
ищет это значение в справочнике `DICT_OWNER_ROLE` и записывает в колонку `owner_role_code` код `ROLE-014`.
Если в ARIS роль переименуют, а справочник не обновят, поиск не найдёт код: запись получит `E-MAP-001`, а
старая строка таблицы останется без изменений.

Вторая ошибка — путать `src_changed_ts` и `loaded_at`: для процесса `PRC-000417` изменение в ARIS
произошло в 06:12 UTC (`src_changed_ts`), а строка записана при загрузке около 06:20 UTC (`loaded_at`).

Строка ERP в том же реестре: `SYS-ERP`, `DEMO_MATERIAL.MATERIAL_CLASS` → BusinessObject.`material_class`,
`mapping_state = mapped`; соседняя колонка `DEMO_MATERIAL.LEGACY_FLAG` без правила — `unmapped`.
