# Глоссарий ключевых терминов семантического слоя

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

Глоссарий фиксирует одно значение для каждого термина, который встречается в документах группы
«Семантика» (DEMO-SEM-*) и в смежных документах об источниках, интеграциях и качестве. Термины даны на
русском и английском, синонимы и разговорные формы перечислены, чтобы поиск находил определение по любой
из них. Здесь описана предметная область семантического слоя; термины самого приложения базы знаний
(документ, цитата, предложение изменения) описаны в [[SEM-GLOSS-001]] и не повторяются.

## Термины

### Семантический слой (semantic layer)
Уровень, на котором технические поля источников (ARIS, CATIA, ERP и др.) приводятся к согласованным
бизнес-сущностям — BusinessProcess, BusinessObject, Dataset — с едиными идентификаторами, справочниками и
правилами качества.

### Логическая модель (logical model)
Описание бизнес-сущностей и их атрибутов без привязки к хранилищу: имя атрибута, смысл, обязательность,
допустимые значения. Пример — сущность BusinessProcess (DEMO-SEM-002) с атрибутом `owner_role`. Логическая
модель отвечает на вопрос «что хранится и что это значит».

### Физическая модель (physical model)
Реализация логической модели в конкретной таблице: имена колонок, типы, ключи, индексы и технические
колонки. Пример — таблица `sl_process_metadata` (DEMO-SEM-005) с колонкой `owner_role_code`. Похожие имена
атрибута и колонки выбраны намеренно, но это разные уровни; переход между ними описывает маппинг логической
и физической моделей (DEMO-SEM-006).

### Сущность, атрибут, колонка (entity, attribute, column)
Сущность — бизнес-понятие с собственным идентификатором (процесс, объект, датасет). Атрибут — свойство
сущности в логической модели. Колонка — место хранения значения в физической таблице. Один атрибут может
давать несколько колонок (например, название и ключ сравнения названия).

### Маппинг, сопоставление полей (mapping)
Правило соответствия поля одной системы или одного уровня полю другого. Различают интеграционный маппинг
«источник → каталог» (например, `aris_object_guid` → `process_id` через таблицу соответствия
`MAP_ARIS_PROCESS`) и маппинг «логическая модель → физическая модель». Синонимы: маппинг, сопоставление,
сопоставление полей, mapping.

### Происхождение данных, линейдж (data lineage)
Цепочка шагов, по которой значение попало в датасет: источник → интеграция → логическая сущность → датасет
→ потребитель. В датасете Process Overview ссылка на такую цепочку хранится в атрибуте `lineage_ref`.
Синонимы: линейдж, lineage, data lineage, происхождение данных, «откуда пришли данные».

### Датасет (dataset)
Набор данных для потребителей, собранный из логических сущностей по описанным правилам качества и
обновления. Каждый датасет описывается по логической модели Dataset (DEMO-SEM-004) и получает
идентификатор вида `DS-001`.

### Справочник (reference data, dictionary)
Управляемый список допустимых значений с кодами, например `DICT_OWNER_ROLE` (роли-владельцы) или
`DICT_SYSTEM_CODE` (коды систем `SYS-ARIS`, `SYS-CATIA` и др.). Эталонные копии справочников ведутся в MDM.

### Нормализация названий (name normalization)
Детерминированное приведение названия к единому виду (пробелы, кавычки, раскрытие сокращений) и
вычисление ключа сравнения `name_key`. Нормализация не меняет идентичность сущности.

### Владелец (owner)
Роль, отвечающая за содержание документа или набора данных и утверждающая изменения. В атрибутах
хранится роль, а не имя человека. Синонимы: владелец, owner.

### Стюард данных (data steward)
Роль, отвечающая за качество конкретных данных: разбирает карантин и неоднозначные сущности, регистрирует
новые Process ID. Синонимы: стюард, steward.

### Ревьюер (reviewer)
Роль, проверяющая предложенное изменение до его утверждения владельцем.

### Качество данных (data quality)
Совокупность измеримых свойств данных: полнота, согласованность, актуальность, уникальность, формат.
Проверки выполняет монитор качества данных `SYS-DQM`.

### Полнота (completeness)
Доля заполненных обязательных атрибутов в пакете или датасете. Порог по умолчанию — 95 %; отдельный датасет
может установить более строгий порог для своей области, например 98 % для ключевых атрибутов Process
Overview.

### Актуальность, свежесть (freshness)
Максимально допустимый возраст данных: по умолчанию 24 ч для метаданных каталога, 12 ч для датасета
Process Overview.

### Согласованность (consistency)
Один и тот же факт имеет одно значение во всех местах: один код роли — одно название роли, одна система —
один код `SYS-*`.

### Инкрементальная загрузка и полная перезагрузка (incremental load, full refresh)
Инкрементальная загрузка передаёт только изменённые записи (ARIS — пакетами по 500 записей), полная
перезагрузка заменяет весь набор (ERP — пакетами по 2 000 строк).

### Ревизия и версия (revision vs version)
Версия (`version`) — человекочитаемый номер MAJOR.MINOR в заголовке документа: совместимое изменение
увеличивает MINOR, несовместимое (breaking change) — MAJOR. Ревизия — техническая метка содержимого,
вычисляется автоматически: хеш содержимого в локальном режиме или commit в GitLab. Правила смены версий —
[[DEMO-GOV-009]].

### Authority (авторитетность, источник истины)
Признак того, что документу можно доверять как утверждённому источнику. Authority есть только у документов
в статусе `approved`; черновики (`draft`) и документы на ревью (`in_review`) не авторитетны, устаревшие
(`deprecated`) заменены преемником. Почему именно утверждение управляет authority, объясняет [[DEMO-ADR-002]].

### Неоднозначная сущность, омоним (ambiguous entity, homonym)
Разные сущности с одинаковым или похожим названием, например процесс в ARIS и сборка в CATIA с одним
названием «Сборка узла крепления (демо)». Правила разрешения — DEMO-SEM-012 (документ на ревью).

### Process ID
Устойчивый идентификатор бизнес-процесса: `PRC-` и 6 цифр, например `PRC-000417`. Контракт описан в
DEMO-SEM-007.

## Аббревиатуры

### ADR — два конкурирующих значения
1. **Architecture Decision Record** — запись архитектурного решения (документы типа decision, например
   SEM-DEC-001 о полнотекстовом поиске).
2. **Average Daily Rows** — метрика монитора качества данных (`SYS-DQM`, DEMO-SRC-011): среднее число строк
   в сутки по набору данных.

Как различать: если рядом число строк, «метрика», отчёт монитора качества — это Average Daily Rows; если
рядом «решение», контекст, альтернативы, статус решения или номер документа — Architecture Decision Record.
Если контекст не позволяет выбрать, ответ называет оба значения.

### MDM — два конкурирующих значения
1. **Master Data Management** — управление мастер-данными; система MDM (`SYS-MDM`) хранит эталонные
   справочники.
2. **«MDM-модель» в текстах ARIS** — модель метаданных (metadata model), то есть описание структуры
   процессных моделей; к мастер-данным отношения не имеет.

Как различать: справочники, эталонные записи, CRM, `SYS-MDM` — мастер-данные; «MDM-модель», иерархия модели
ARIS, процессные метаданные — модель метаданных. В документах этой базы MDM используется только в первом
значении, второе пишется полностью: «модель метаданных».

### CDC (Change Data Capture)
Захват изменений: источник публикует события об изменениях в Event Hub, топик `demo.metadata.changes.v1`.
Сравнение CDC и полной перезагрузки — DEMO-INT-010.

### FTS (full-text search)
Полнотекстовый поиск; в локальной демонстрации — SQLite FTS5 (решение SEM-DEC-001).

### DQ (data quality)
Качество данных; DQ-правила — полнота, согласованность, актуальность.

### SLA (Service Level Agreement)
Для демо-потоков SLA не определён: ни один документ базы не задаёт соглашение об уровне сервиса.
Расписания загрузки и пороги актуальности — не SLA. На вопрос об SLA любого демо-потока корректный
ответ — «нет данных».
