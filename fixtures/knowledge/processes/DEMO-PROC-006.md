# Шаблон: Integration Specification

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Документ **описывает** шаблон Integration Specification (спецификация интеграции) — структуру, по которой
пишутся документы о потоках метаданных между системами. Сам документ шаблоном не является и для создания
документов не используется: машиночитаемый шаблон хранится в реестре шаблонов приложения (каталог
`backend/app/document_templates/`, идентификатор шаблона `integration`). Если описание и реестр расходятся,
верна структура в реестре, а это описание исправляется.

Версия этого документа-описания (2.1) и версия шаблона (v2) — разные номера: первая следует правилам версий
документов, вторая — целое число из реестра шаблонов.

## Область применения

Шаблон применяется ко всем новым документам типа `integration` (обычно владелец — `demo-integration-team`):
обзорам потоков, маппингам полей и описаниям ограничений. Разделы шаблона (sections) — заголовки второго
уровня `##`; приложение создаёт их с пометкой «Требует уточнения».

**Текущая версия для новых документов — v2.** Черновики, созданные по v1, сохраняют v1 до явной миграции
автором.

## Правила

1. **Разделы v1** (восемь): Назначение, Источник и получатель, Передаваемые данные, Маппинг, Бизнес-правила,
   Ограничения, Ошибки, Требования. В реестре раздел о данных называется «Передаваемые данные и метаданные».
2. **Разделы v2.** Версия v2 шаблона Integration Specification добавляет к восьми разделам v1 четыре раздела:
   Data Quality Rules, Data Lineage, Update Frequency и Validation Constraints. Итого в v2 двенадцать разделов.
3. **Data Quality Rules** — применимые правила качества и пороги. По умолчанию действует порог полноты 95 %
   обязательных атрибутов на пакет; более строгий порог для конкретного датасета указывается явно, с
   оговоркой, что это правило области применения, а не противоречие.
4. **Data Lineage** — цепочка «источник → интеграция → датасет» со ссылками на документы каждого звена
   (линейдж, происхождение данных).
5. **Update Frequency** — расписание и способ обновления: инкремент, полная перезагрузка (full refresh) или
   события CDC; время указывается как условное.
6. **Validation Constraints** — проверяемые ограничения на входные записи: обязательные поля, допустимые
   статусы, предельная глубина иерархии, действие при нарушении (отклонение записи или карантин пакета).
7. **Метаданные.** Документ по шаблону хранит во frontmatter `template: integration` и номер версии шаблона
   (`template_version: 2` для новых документов). Эти поля пишет приложение, автор их вручную не меняет.
8. **Маппинг** оформляется таблицей «поле источника → поле получателя → правило преобразования»; поля без
   соответствия перечисляются явно.
9. Все разделы v2 обязательны: несоответствующий раздел не удаляется, а заполняется строкой «Не применимо» с
   причиной.

## Исключения

- **Черновики v1.** Черновики и документы, созданные по v1, остаются валидными на v1: отсутствие разделов Data
  Quality Rules, Data Lineage, Update Frequency и Validation Constraints в них не считается ошибкой. Переход на
  v2 — явное действие автора по политике изменения версий шаблонов (DEMO-PROC-010), потому что v2 добавляет
  обязательные разделы.
- **Утверждённые документы v1** не перепроверяются по v2 задним числом; владелец может перевести документ на v2
  при очередной существенной правке.

## Контроль и проверка

- При создании и сохранении черновика приложение сверяет заголовки `##` с версией шаблона, записанной в
  `template_version`.
- Перед ревью ни один раздел не должен содержать пометку «Требует уточнения» (контрольная точка процесса
  создания новой интеграции).
- Ревьюер проверяет, что в Data Quality Rules и Validation Constraints названы конкретные значения, а не
  общие формулировки.
- Ассистент, готовящий черновик, получает структуру шаблона из реестра вместе с идентификатором и версией;
  соответствие структуры проверяет приложение, а не ассистент.

## Пример

Скелет нового документа по v2 — двенадцать заголовков `##` в таком порядке: Назначение · Источник и получатель ·
Передаваемые данные · Маппинг · Бизнес-правила · Ограничения · Ошибки · Требования · Data Quality Rules · Data
Lineage · Update Frequency · Validation Constraints. Черновик по v1 содержит только первые восемь.

Заполнение новых разделов для условного потока ARIS → Catalog:

- **Update Frequency** — инкремент каждые 6 ч (00:00, 06:00, 12:00, 18:00, условное время), пакеты по 500
  записей.
- **Validation Constraints** — обязательные `aris_object_guid`, `aris_object_name`, `aris_owner_role`; глубина
  иерархии модели не более 7 уровней (`ARIS_MAX_DEPTH = 7`); записи с `aris_status = obsolete` отклоняются.
- **Data Quality Rules** — пакет принимается, только если проверки проходят не менее 95 % записей; иначе весь
  пакет уходит в карантин `q_aris_rejected`.
- **Data Lineage** — ARIS `SYS-ARIS` → поток ARIS → Catalog → Data Catalog `SYS-CAT` → датасет Process
  Overview.
