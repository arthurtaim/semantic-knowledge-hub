# Шаблон: Dataset Specification

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Документ **описывает** шаблон Dataset Specification (спецификация датасета) — структуру, по которой пишутся
документы о датасетах семантического слоя. Сам документ шаблоном не является: машиночитаемый шаблон хранится в
реестре шаблонов приложения (каталог `backend/app/document_templates/`), и именно оттуда приложение берёт
разделы при создании нового документа. При расхождении верна структура в реестре.

Шаблон — документная форма логической модели Dataset (DEMO-SEM-004): каждый документ, созданный по шаблону,
описывает ровно один экземпляр сущности Dataset, а разделы шаблона соответствуют аспектам этой модели —
источникам, сущностям, атрибутам, качеству, обновлению и доступу.

## Область применения

Шаблон применяется к новым документам типа `dataset` (владелец обычно `demo-semantic-team`). **Текущая версия
шаблона — v1.** Документ хранит во frontmatter идентификатор шаблона и `template_version: 1`; эти поля пишет
приложение, а в логической модели им соответствует атрибут `spec_template_version`. Изменения атрибутов уже
утверждённого датасета вносятся в разделы этого же шаблона по процессу изменения атрибутов датасета.

## Правила

1. **Разделы v1** (девять, в этом порядке): Overview, Source Systems, Business Entities, Attributes, Mapping
   Rules, Data Quality, Refresh Policy, Access Restrictions, Related Docs. Заголовки всех девяти разделов
   присутствуют в каждом документе; Mapping Rules и Related Docs могут содержать «Не применимо» с причиной,
   потому что соответствующие атрибуты модели (`mapping_rules`, `related_docs`) необязательны.
2. **Overview (Обзор)** — идентификатор датасета `dataset_id` (`DS-` и 3 цифры), имя, назначение, потребители,
   команда-владелец и одна фраза о зерне данных (что такое одна строка).
3. **Source Systems (Источники)** — системы по кодам (`SYS-ARIS`, `SYS-CAT` и т. д.) и документы интеграций,
   через которые приходят данные.
4. **Business Entities (Бизнес-сущности)** — сущности логической модели, из которых выведен датасет; связь
   `derived_from` в метаданных обязательна.
5. **Attributes (Атрибуты)** — таблица с колонками: имя, тип, обязательность, описание, источник. Атрибуты
   называются по **логическим** атрибутам, а не по физическим колонкам. Каждый обязательный атрибут
   учитывается в проверке полноты.
6. **Mapping Rules (Правила маппинга)** — как поля источников превращаются в атрибуты датасета; для ломающих
   изменений здесь же описывается соответствие старых и новых имён.
7. **Data Quality (Правила качества)** — пороги полноты, согласованности и актуальности. По умолчанию порог
   полноты 95 %. Датасет может только ужесточить порог для своей области и указывает это явно; ослабление
   общего порога требует отдельного решения по правилам управления.
8. **Refresh Policy (Политика обновления)** — расписание обновления и максимально допустимый возраст данных
   (по умолчанию для метаданных каталога — не более 24 ч).
9. **Access Restrictions (Ограничения доступа)** — какие демо-роли (`demo-reader`, `demo-editor`,
   `demo-approver`) читают и правят описание датасета.
10. **Related Docs (Связанные документы)** — потребители датасета и документы, от которых он зависит, с
    объяснением каждой связи.

## Исключения

- В документах базы знаний разделы могут называться по-русски (Обзор, Источники, Бизнес-сущности, Атрибуты,
  Правила маппинга, Правила качества, Политика обновления, Ограничения доступа, Связанные документы) — это те
  же разделы шаблона.
- Если у датасета нет собственных правил доступа, раздел Access Restrictions не удаляется, а ссылается на общие
  правила демо-среды.
- Черновики, созданные по v1, остаются на v1 и после выхода следующей версии шаблона; переход — явное действие
  автора по политике изменения версий шаблонов.

## Контроль и проверка

- Приложение сверяет заголовки разделов с версией шаблона из `template_version` при создании и сохранении
  черновика.
- Ревьюер проверяет, что таблица Attributes заполнена полностью и каждый обязательный атрибут присутствует в
  правилах Data Quality.
- Ревьюер проверяет, что в Refresh Policy указаны и расписание, и предельный возраст данных.
- Изменение логической модели Dataset (например, новая обязательная характеристика датасета) — повод
  пересмотреть шаблон и выпустить его новую версию по DEMO-PROC-010.

## Пример

Фрагмент документа по шаблону для условного датасета Process Overview (`DS-001`):

| Атрибут | Тип | Обязательность | Описание | Источник |
|---|---|---|---|---|
| `process_id` | string | да | Process ID, `PRC-` и 6 цифр | BusinessProcess.`process_id` |
| `process_name` | string | да | нормализованное название процесса | BusinessProcess.`process_name` |
| `owner_role` | string | да | название роли-владельца (не код) | BusinessProcess.`owner_role` |
| `completeness_score` | decimal(4,1) | да | процент заполненных атрибутов записи | вычисляется при сборке |

- **Source Systems:** `SYS-ARIS` через поток ARIS → Catalog.
- **Data Quality:** для `process_id`, `process_name`, `owner_role` порог полноты 98 % — строже общего порога
  95 %; это правило области применения, а не противоречие.
- **Refresh Policy:** инкремент после каждого запуска ARIS → Catalog (каждые 6 ч); данные не старше 12 ч.

## Связанные документы

- **DEMO-SEM-004** — `describes`: логическая модель Dataset; шаблон является её документной формой — каждый
  раздел соответствует атрибуту модели (`source_systems`, `attributes`, `quality_rules`, `refresh_policy` и
  др.), а каждый документ по шаблону описывает один экземпляр Dataset.
- **DEMO-PROC-010** — ссылка: политика изменения версий шаблонов; определяет, когда выпускается новая версия
  этого шаблона и что происходит с черновиками v1.
