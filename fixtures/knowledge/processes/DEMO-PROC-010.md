# Политика изменения версий шаблонов

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Политика определяет, как меняются шаблоны документов базы знаний (Integration Specification, Dataset
Specification, Source System Profile, ADR и другие) и что при этом происходит с уже созданными документами и
черновиками. Цель — чтобы изменение шаблона никогда не меняло задним числом начатую или утверждённую работу.
Политика реализует архитектурное решение о версионируемых шаблонах DEMO-ADR-005.

## Область применения

Политика относится к машиночитаемым шаблонам в реестре шаблонов приложения (`backend/app/document_templates/`)
и к их описаниям в базе знаний. Она не регулирует версии самих документов: номер `version` документа
(MAJOR.MINOR) ведётся по правилам управления ревизиями документов DEMO-GOV-009. Версия шаблона — отдельное
целое число (`template_version`: 1, 2, …), которое приложение записывает в метаданные документа при его
создании.

## Правила

1. **Любое изменение шаблона — новая версия.** Изменение набора разделов, их порядка или смысла, а также правка
   подсказок выпускается как новая версия с номером на единицу больше. Прежняя версия остаётся в реестре только
   для чтения.
2. **Новая версия — только для новых документов.** Текущая (активная) версия шаблона применяется к документам,
   созданным после её выпуска.
3. **Старые черновики сохраняют свою версию шаблона.** Черновик проверяется по той версии, с которой создан, и
   никогда не переписывается молча. Например, черновики Integration Specification, созданные по v1,
   остаются на v1 после выпуска v2.
4. **Совместимое изменение** — правка подсказок и пояснений внутри разделов без изменения набора разделов.
   Документы на прежней версии остаются валидными; автор может перейти на новую версию по желанию.
5. **Несовместимое изменение** — появление нового обязательного раздела, переименование или удаление
   раздела. Для перехода документа на такую версию нужна **явная миграция**: автор сам выбирает действие
   «перевести на версию N».
6. **Как устроена миграция.** Приложение показывает, каких разделов не хватает и какие переименованы,
   добавляет недостающие разделы с пометкой «Требует уточнения» и не трогает существующий текст. Результат —
   обычная правка с diff и ревью; ни синхронизация, ни ассистент не выполняют миграцию сами.
7. **Версия документа при миграции.** Добавление разделов без изменения смысла существующего текста —
   совместимое изменение документа, поэтому его `version` повышается по MINOR (правила DEMO-GOV-009).
8. **Удаление шаблона никогда не ломает существующие документы.** Удалённый шаблон снимается с выбора для новых
   документов, но его версии остаются в реестре в архиве только для чтения. Документы, созданные по нему,
   открываются, отображаются и редактируются по сохранённой версии.
9. **Вывод версии из употребления.** Версию шаблона выводят из употребления только после того, как все
   черновики на ней закрыты или мигрированы.
10. **Ревью шаблонов.** Каждое изменение шаблона проходит ревью владельца описаний шаблонов
    (`demo-process-office`); описание шаблона в базе знаний обновляется в той же правке, что и реестр.

## Исключения

- **Утверждённые документы** не перепроверяются по новой версии шаблона задним числом и не мигрируются
  принудительно. Владелец может перевести документ при очередной существенной правке.
- **Массовая миграция** не проводится одной операцией: по каждому документу оформляется отдельное предложение
  изменения с ревью.
- **Уточнение описания шаблона** (документы DEMO-PROC-006…DEMO-PROC-009) без изменения шаблона в реестре не
  создаёт новую версию шаблона: меняется только `version` самого документа-описания.

## Контроль и проверка

- Приложение хранит у каждого документа пару «шаблон + версия» (`template`, `template_version`) и проверяет
  разделы по этой паре, а не по текущей версии шаблона.
- Ревьюер миграции проверяет, что существующий текст не изменён, а новые разделы заполнены.
- Ассистент, готовящий черновик, получает структуру текущей версии шаблона из реестра; соответствие
  результата структуре проверяет приложение.
- Отчёт по базе показывает документы и черновики, оставшиеся на старых версиях шаблонов.

## Пример

Шаблон Integration Specification переходит с v1 на v2: добавлены обязательные разделы Data Quality Rules, Data
Lineage, Update Frequency и Validation Constraints. Это несовместимое изменение (правило 5).

- Черновик спецификации, созданный по v1 (`template_version: 1`), проверяется по восьми разделам v1;
  отсутствие раздела Data Lineage ошибкой не считается.
- Новая интеграция, созданная после выпуска v2, сразу получает двенадцать разделов.
- Автор черновика v1 решает мигрировать его: приложение добавляет четыре раздела с пометкой «Требует
  уточнения», автор их заполняет, правка проходит ревью, версия документа повышается по MINOR.
