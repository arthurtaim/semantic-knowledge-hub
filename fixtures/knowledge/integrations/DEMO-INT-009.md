# Source → Dataset: распространение версий (демо)

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

У каждого источника учебной модели есть версия контракта выгрузки (например, `aris_export` для ARIS), а у каждого
датасета — своя версия в формате MAJOR.MINOR. Поток распространяет изменения версий: когда меняется контракт
источника, он определяет затронутые датасеты и поднимает их версии по единому правилу. Так потребитель по одной
версии датасета понимает, совместимо ли изменение с его запросами, не читая контракты всех источников.

## Источник и получатель

- Источник — события `version_changed` в Event Hub (`SYS-EVH`, профиль DEMO-SRC-008), топик
  `demo.metadata.changes.v1`. Их публикует источник при смене версии контракта выгрузки; данные пакетных
  источников (ARIS, CATIA, ERP) по-прежнему идут по расписанию, через Event Hub проходит только уведомление.
- Получатели — реестр версий датасетов (`DS-001` Process Overview, `DS-002` Dependency Graph, `DS-003` Source
  Coverage) и потребители, которые получают ответное событие `dataset_version_changed` в тот же топик.

## Входные данные (Inputs)

Событие `version_changed`:

- `event_id` — идентификатор события;
- `source_system` — код системы (`SYS-ARIS`, `SYS-CATIA`, `SYS-ERP` …);
- `contract_name` — имя контракта выгрузки, например `aris_export`;
- `old_version`, `new_version` — версии контракта MAJOR.MINOR;
- `change_kind` — `minor` или `major`.

## Выходные данные (Outputs)

- Новая версия затронутого датасета — применённая или ожидающая ревью.
- Событие `dataset_version_changed`: `event_id`, датасет, старая и новая версия.
- Черновик изменения для владельца датасета, если изменение несовместимое.

## Правила преобразования (Transformation Rules)

1. Версия — MAJOR.MINOR по правилам управления ревизиями (DEMO-GOV-009): совместимое изменение повышает MINOR,
   несовместимое (breaking change) — MAJOR.
2. Затронутые датасеты определяются по цепочке происхождения: контракт источника → поток интеграции и его маппинг
   → датасет. Например, `aris_export` → поток ARIS → Catalog → Process Overview.
3. `change_kind = minor` повышает MINOR затронутого датасета на 1 и применяется автоматически.
4. `change_kind = major` повышает MAJOR датасета на 1 и сбрасывает MINOR в 0, но **автоматически не
   применяется**: создаётся черновик изменения, его утверждает владелец датасета. Пока черновик не утверждён,
   датасет сохраняет прежнюю версию, а загрузка по новому контракту не начинается.
5. Версии не уменьшаются: событие с `new_version` не выше текущей зарегистрированной игнорируется с причиной
   `stale_version`.
6. Что считать несовместимым, определяет документ о совместимости схем: переименование или удаление поля —
   breaking change (и только после окна устаревания), новое необязательное поле — совместимое изменение.

## Ограничения (Constraints)

- Версия датасета — не то же самое, что версия документа и ревизия содержимого (хеш локально или коммит в
  GitLab): поток работает только с версиями контрактов и датасетов.
- Поток не меняет схему датасета сам — он фиксирует версию и уведомляет потребителей.
- Одно событие источника может поднять версии нескольких датасетов; каждое повышение — отдельное событие
  `dataset_version_changed`.
- Глубина хранения событий в топике не определена: при простое поток не перечитывает старые события, а реестр
  версий сверяется с владельцами источников вручную.
- Несовместимое изменение никогда не становится действующим без ревью.

## Ошибки и обработка (Error Cases)

| Код | Ситуация | Обработка |
|---|---|---|
| `E-VAL-002` | нет `change_kind` или `new_version` не в формате MAJOR.MINOR | сразу `dlq.metadata.v1`, без повторов; версии не меняются |
| `E-MAP-001` | неизвестный `contract_name` — нет цепочки к датасетам | повторы по общей политике, затем `dlq.metadata.v1`; ни один датасет не затрагивается |
| `E-SRC-003` | Event Hub недоступен | до 5 повторных попыток, затем `dlq.metadata.v1` |

## Версия и статус

Версия 1.2, статус approved, дата проверки 2026-10-29. В 1.2 (MINOR) добавлено правило `stale_version`; в 1.1 —

## Пример

1. В выгрузку ARIS добавлено новое необязательное поле. Событие: `contract_name: aris_export`,
   `old_version: "1.4"`, `new_version: "1.5"`, `change_kind: minor`. Process Overview автоматически переходит
   с 2.3 на 2.4, в топик уходит `dataset_version_changed`.
2. В выгрузке ARIS после окна устаревания переименовано поле `aris_owner_role`. Событие с `change_kind: major`,
   `new_version: "2.0"`.

```yaml
event: version_changed
source_system: SYS-ARIS
contract_name: aris_export
old_version: "1.5"
new_version: "2.0"
change_kind: major
result:
  dataset: DS-001             # Process Overview
  current_version: "2.4"
  proposed_version: "3.0"
  state: awaiting_review      # загрузка по контракту 2.0 ждёт утверждения
```
