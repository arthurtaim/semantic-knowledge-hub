# CDC и full refresh: сравнение

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Документ сравнивает два способа доставки метаданных из источников в каталог и семантический слой учебной
модели: захват изменений (CDC, Change Data Capture) и полную перезагрузку (full refresh). Между ними
находится инкрементальная загрузка по водяному знаку: она тоже передаёт только изменения, но читает их из
источника по расписанию, а не из потока событий. Документ помогает выбирать способ для новой интеграции и
объясняет, почему действующие демо-потоки устроены по-разному. Расписания конкретных потоков здесь не
утверждаются — они закреплены в DEMO-INT-013.

## Источник и получатель

Сравнение опирается на три действующих потока учебной модели:

| Поток | Способ | Источник → получатель | Единица обработки |
|---|---|---|---|
| CRM → MDM (DEMO-INT-006) | CDC: непрерывное чтение событий Event Hub | `SYS-CRM` → `SYS-MDM` | одно событие |
| ARIS → Catalog (DEMO-INT-001) | инкрементально по водяному знаку `aris_watermark`, по расписанию | `SYS-ARIS` → `SYS-CAT` | пакет из 500 записей |
| ERP → Semantic Layer (DEMO-INT-007) | full refresh | `SYS-ERP` → семантический слой | пакет из 2 000 строк |

Транспортом для CDC служит Event Hub (`SYS-EVH`, DEMO-SRC-008).

## Входные данные (Inputs)

- **CDC**: события об изменении объекта в топике Event Hub `demo.metadata.changes.v1`. Каждое событие
  содержит `event_id`, `event_type` (`create`, `update`, `delete`), `source_system`, `source_object_id`,
  `source_changed_at` и значения изменённых атрибутов.
- **Инкрементальная загрузка**: объекты источника, изменённые после водяного знака предыдущего успешного
  запуска (для ARIS — `aris_last_change` больше `aris_watermark`).
- **Full refresh**: полный снимок справочников и атрибутов источника на момент выгрузки, без признака
  операции. Время снимка служит значением `source_changed_at` для всех его строк.

## Выходные данные (Outputs)

- **CDC**: обновлены только записи изменившихся объектов; удаление объекта приходит отдельным событием
  с `event_type = delete`.
- **Инкрементальная загрузка**: обновлены записи изменившихся объектов; удаление в источнике отдельным
  событием не передаётся и обрабатывается правилами конкретного потока.
- **Full refresh**: набор записей получателя пересобран целиком; объект, которого нет в новом снимке,
  помечается удалённым при сверке с предыдущим снимком.

## Правила преобразования (Transformation Rules)

1. Маппинг полей не зависит от способа доставки: он задаётся документом маппинга потока (для ARIS —
   DEMO-INT-002), а не выбором CDC или full refresh.
2. При CDC и инкрементальной загрузке изменения одного объекта применяются в порядке `source_changed_at`;
   изменение со значением не новее уже применённого отбрасывается как устаревшее.
3. Повторно доставленные события отбрасываются по ключу идемпотентности (DEMO-INT-012).
4. При full refresh новый снимок загружается во временную область пакетами по 2 000 строк и заменяет
   предыдущий только после успешной загрузки последнего пакета.

## Как выбирать способ

CDC выбирают, когда:

- источник умеет публиковать события об изменениях в Event Hub;
- за период меняется малая доля объектов по сравнению с общим объёмом;
- получателю нужна задержка в минутах (например, CRM → MDM: задержка до 15 мин).

Инкрементальную загрузку по водяному знаку выбирают, когда источник не публикует события, но надёжно
хранит время последнего изменения объекта, а задержки в несколько часов достаточно (ARIS → Catalog).

Полную перезагрузку (full refresh) выбирают, когда:

- источник не публикует события или не фиксирует удаления;
- объём справочников невелик и полная выгрузка укладывается в ночное окно (ERP: ночью в 01:00);
- нужна периодическая сверка, устраняющая накопленные расхождения.

Общая стратегия «snapshot или события» принята архитектурным решением DEMO-ADR-004; этот документ —
практическое сравнение для авторов интеграций.

## Ограничения (Constraints)

- CDC не восстанавливает изменения, которые не попали в топик. При подозрении на потерю событий владелец
  интеграции заказывает разовую полную выгрузку как исключение.
- Глубина хранения событий в топике `demo.metadata.changes.v1` в демо-модели не определена.
- Инкрементальная загрузка теряет изменение, если источник не обновил время изменения объекта.
- Full refresh нагружает источник пропорционально полному объёму, а не числу изменений; поэтому поток ARIS
  переведён на инкрементальную загрузку.
- Размер пакета ARIS (500 записей) и ERP (2 000 строк) меняется только новой версией документа
  соответствующего потока.

## Ошибки и обработка (Error Cases)

- Недоступность источника или Event Hub — код `E-SRC-003`, далее действует общая политика повторных попыток.
- Ошибка маппинга `E-MAP-001` и ошибка валидации `E-VAL-002` обрабатываются одинаково для обоих способов.
- Сбой full refresh посреди загрузки: предыдущий снимок остаётся действующим, частично загруженный
  отбрасывается целиком.

## Пример

Одно и то же утро в трёх потоках (условное время):

- Карточка канала в CRM изменена в 10:02. Событие попадает в топик `demo.metadata.changes.v1` и через
  несколько минут применяется в MDM — в пределах 15 мин.
- Объект ARIS, соответствующий процессу `PRC-000417`, изменён в 09:12. Ближайший запуск ARIS → Catalog в
  12:00 выбирает его по водяному знаку вместе с другими изменениями, пакетами до 500 записей.
- Справочник ERP изменён в 14:00. Изменение попадёт в семантический слой только после полной
  перезагрузки в 01:00 следующих суток.
