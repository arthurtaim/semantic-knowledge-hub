# Совместимость схем и breaking changes

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Документ определяет, какие изменения схем считаются совместимыми, а какие — несовместимыми (breaking
changes), и как каждое изменение отражается в версии. Правила действуют для событий в Event Hub, полей
датасетов, которые выдаются потребителям, и контракта Consumer API. Цель — чтобы потребитель заранее знал,
когда его интеграция может сломаться, и успевал перейти на новую версию.

## Источник и получатель

- **Источник изменения**: владелец интеграции, датасета или контракта, который меняет схему.
- **Получатель**: все потребители этой схемы, в том числе пользователи Consumer API.

## Входные данные (Inputs)

Описание изменения схемы: какие поля добавлены, удалены, переименованы или изменили тип; затронутые
ресурсы, топики и датасеты.

## Выходные данные (Outputs)

Класс изменения (совместимое или breaking), новая версия схемы в формате MAJOR.MINOR и, для breaking
changes, план окна устаревания.

## Правила преобразования (Transformation Rules)

| Изменение | Класс | Версия |
|---|---|---|
| добавление необязательного поля в ответ или событие (additive) | совместимое | MINOR |
| добавление нового ресурса, топика или датасета | совместимое | MINOR |
| добавление значения в перечисление (enum) | совместимое, если потребители игнорируют неизвестные значения | MINOR |
| пометка поля как устаревшего (deprecated) | совместимое | MINOR |
| удаление поля | breaking | MAJOR |
| переименование поля (равносильно удалению и добавлению) | breaking | MAJOR |
| изменение типа или формата поля | breaking | MAJOR |
| новый обязательный параметр запроса | breaking | MAJOR |

1. Версия схемы ведётся в формате MAJOR.MINOR по тем же принципам, что и версии документов: совместимое
   изменение увеличивает MINOR, несовместимое — MAJOR.
2. Окно устаревания (deprecation window) — 2 релиза. Поле помечается устаревшим в релизе N и может быть
   удалено не раньше релиза N+2, причём удаление всегда выпускается как MAJOR.
3. Релизом считается любая опубликованная версия схемы, MINOR или MAJOR.
4. При MAJOR-изменении меняется номер в адресе или имени: путь `/demo/v1/` становится `/demo/v2/`,
   топик `demo.metadata.changes.v1` — `demo.metadata.changes.v2`. Во время окна устаревания старая и
   новая версии работают параллельно.

## Ограничения (Constraints)

- Breaking change без окна устаревания в учебной модели не допускается.
- Правила относятся к схемам данных; лимиты Consumer API (размер страницы 100 записей, 60 запросов в
  минуту) меняются отдельной версией контракта и тоже классифицируются: ужесточение лимита — MAJOR,
  ослабление — MINOR.
- Изменение версии схемы распространяется от источника к датасетам по правилам распространения версий
  (DEMO-INT-009).

## Ошибки и обработка (Error Cases)

- Если на ревью обнаружено breaking change, оформленное как MINOR, изменение возвращается автору для
  исправления версии и плана окна устаревания.
- Если потребитель продолжает читать поле после его удаления, это ошибка потребителя: окно устаревания
  считается достаточным предупреждением.

## Версия и статус

Версия 1.1, статус approved. Версия 1.1 (MINOR) добавила правило о лимитах Consumer API.

## Пример

Нужно переименовать поле `owner_role` в ответе Consumer API в `owner_role_code`:

1. Релиз 1.5 (MINOR): добавлено поле `owner_role_code`, поле `owner_role` помечено устаревшим.
2. Релиз 1.6 (MINOR): оба поля продолжают выдаваться; потребители переходят на новое имя.
3. Релиз 2.0 (MAJOR): поле `owner_role` удалено, контракт доступен по пути `/demo/v2/`; путь `/demo/v1/`
   работает до конца своего окна устаревания.

Удалить поле уже в релизе 1.6 нельзя: с момента пометки прошёл только один релиз из двух.
