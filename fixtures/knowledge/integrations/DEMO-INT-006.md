# CRM → MDM: синхронизация справочников (демо)

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Поток поддерживает в MDM (Master Data Management, `SYS-MDM`) актуальные мастер-записи справочных карточек
условной CRM (`SYS-CRM`): каналов взаимодействия, сегментов и типов обращений. Через MDM эти карточки становятся
общими справочниками, по которым нормализуются названия в датасетах. Синхронизация идёт почти в реальном времени
через механизм CDC (Change Data Capture): каждое изменение карточки в CRM публикуется событием в Event Hub
(`SYS-EVH`), а поток применяет его в MDM. Ожидаемая задержка от изменения в CRM до записи в MDM — **до 15 минут**.

## Источник и получатель

| Роль | Система | Код | Комментарий |
|---|---|---|---|
| Источник | CRM (условная модель) | `SYS-CRM` | справочные карточки, профиль [[DEMO-SRC-004]] |
| Транспорт | Event Hub | `SYS-EVH` | топик `demo.metadata.changes.v1`, профиль [[DEMO-SRC-008]] |
| Получатель | MDM | `SYS-MDM` | мастер-записи и общие справочники, профиль [[DEMO-SRC-006]] |

Клиентские карточки и любые персональные данные в поток не входят: синхронизируются только справочники.

## Входные данные (Inputs)

CDC-событие из топика `demo.metadata.changes.v1` с полями:

- `event_id` — уникальный идентификатор события;
- `event_type` — `create`, `update` или `delete`;
- `source_system` — всегда `SYS-CRM` для этого потока;
- `source_object_id` — идентификатор карточки `crm_card_id` (вида `crm-card-demo-42`);
- `source_changed_at` — момент изменения карточки (`crm_updated_at`);
- `card_type` — `channel`, `segment` или `request_type`;
- `card_name`, `card_state` — название «как есть» и состояние (`active` или `inactive`).

События других систем в том же топике поток пропускает по полю `source_system`.

## Выходные данные (Outputs)

Мастер-запись справочника в MDM: тип справочника, нормализованное название, состояние, исходный ключ
`SYS-CRM:<crm_card_id>` в списке `mdm_source_keys` и время последнего применённого изменения. Мастер-идентификатор
вида `MDM-00031942` присваивает MDM; поток его не вычисляет.

## Правила преобразования (Transformation Rules)

1. `card_name` нормализуется по правилам справочников и нормализации названий (DEMO-SEM-008); в CRM название
   хранится без нормализации.
2. `create` и `update` создают или обновляют запись; `delete` выводит её (`retired`) — физического удаления в
   MDM нет.
3. Похожие карточки одного типа MDM сводит сам по `mdm_match_score`: 90 и выше — автоматическая привязка к одной
   мастер-записи, от 70 до 89 — задача стюарду в очереди `mdm_review_queue`, ниже 70 — записи остаются разными.
   Поток пороги не меняет.
4. Ключ идемпотентности — `source_system + source_object_id + source_changed_at`; дубликат в пределах 72 ч
   отбрасывается (Event Hub доставляет «не менее одного раза»).
5. Порядок гарантирован только в пределах одной карточки: событие старше уже применённого игнорируется с
   причиной `stale_event`.
6. `card_type` переводится в тип справочника MDM по фиксированной таблице; других типов поток не принимает.

## Ограничения (Constraints)

- Задержка до 15 минут — ожидаемая величина для синхронизации почти в реальном времени. SLA для потока не
  определён, поэтому эта цифра не является обязательством об уровне сервиса.
- Превышение 15 минут фиксируется в мониторинге как нарушение актуальности потока, но события не теряются.
- Поток не пишет в CRM: направление строго CRM → MDM.
- Полного снимка у CRM нет, а глубина хранения событий в топике не определена. При подозрении на потерю событий
  нужна разовая полная выгрузка по отдельной заявке, а не перечитывание старых событий.

## Ошибки и обработка (Error Cases)

| Код | Ситуация | Обработка |
|---|---|---|
| `E-SRC-003` | Event Hub или MDM недоступны | до 5 повторных попыток с экспоненциальной задержкой (30 с → 60 с → 2 мин → 4 мин → 8 мин), затем `dlq.metadata.v1` |
| `E-MAP-001` | неизвестный `card_type` | повторы по общей политике (таблица может пополниться), затем `dlq.metadata.v1`; тип не угадывается |
| `E-VAL-002` | пустой `card_name` или `source_object_id` | сразу `dlq.metadata.v1`, без повторов; мастер-запись не меняется |

Сообщения из `dlq.metadata.v1` разбирает владелец потока вместе со стюардом Event Hub; после устранения причины
их можно повторно отправить в топик — идемпотентность не даст применить изменение дважды.

## Версия и статус

Версия 1.4, статус approved, дата проверки 2026-08-27. В 1.4 (MINOR) добавлена причина `stale_event` для
событий, пришедших не по порядку. Формат события не менялся.

## Пример

```json
{
  "event_id": "evt-demo-5521",
  "event_type": "update",
  "source_system": "SYS-CRM",
  "source_object_id": "crm-card-demo-42",
  "source_changed_at": "2026-08-20T10:04:00Z",
  "card_type": "channel",
  "card_name": "  Мобильное приложение (демо) ",
  "card_state": "active"
}
```

Событие прочитано в 10:09, мастер-запись канала «Мобильное приложение (демо)» обновлена в 10:11 — задержка
7 минут, в пределах 15 минут. Карточка `crm-card-demo-57` «Приложение для смартфона (демо)» получила с ней
`mdm_match_score = 76`, поэтому решение о слиянии ушло стюарду в `mdm_review_queue`. Повторная доставка того же
события отброшена по ключу идемпотентности.
