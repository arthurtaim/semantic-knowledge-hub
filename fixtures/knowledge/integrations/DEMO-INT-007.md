# ERP → Semantic Layer: атрибуты (демо)

> Синтетический демо-документ: описывает вымышленную учебную модель, не системы банка.

## Назначение

Поток каждую ночь заново загружает в семантический слой описания физических атрибутов условной ERP (`SYS-ERP`):
таблицы справочников и транзакций, их колонки и типы. Каждая колонка становится строкой реестра маппинга
логической и физической моделей `MAP_LOGICAL_PHYSICAL` (DEMO-SEM-006): физическая сторона — таблица и колонка ERP,
логическая — атрибут бизнес-объекта BusinessObject, если для колонки есть правило. Режим — полная перезагрузка
(full refresh) **в 01:00** (условное время), пакетами по **2 000 строк**.

## Источник и получатель

| Роль | Система | Код | Комментарий |
|---|---|---|---|
| Источник | ERP (условная модель) | `SYS-ERP` | каталог колонок, профиль DEMO-SRC-005 |
| Получатель | Semantic Layer | — | реестр `MAP_LOGICAL_PHYSICAL` (DEMO-SEM-006) |
| Владелец потока | `demo-integration-team` | — | сопровождение и разбор ошибок |

## Входные данные (Inputs)

Каталог колонок ERP, одна строка на колонку, вместе с заявленным источником числом строк:

- `erp_table` — имя таблицы;
- `erp_column` — имя колонки;
- `erp_data_type` — физический тип (`VARCHAR`, `CHAR`, `NUMBER`, `DATE`);
- `erp_description` — описание колонки;
- `erp_changed_at` — время последнего изменения описания.

Строки данных транзакционных таблиц в поток не входят — передаются только описания колонок. Позиции
справочников (`erp_ref_*`) приходят в том же ночном перегрузе и описаны логической моделью BusinessObject; этот
документ описывает только каталог колонок.

## Выходные данные (Outputs)

Строки реестра `MAP_LOGICAL_PHYSICAL`: физическая сторона (`SYS-ERP`, таблица, колонка, логический тип) и
логическая сторона (атрибут BusinessObject) с состоянием `mapped`; если правила для колонки нет — состояние
`unmapped`. По доле строк `mapped` датасет Source Coverage считает покрытие ERP. Отчёт запуска: число строк,
пакетов, строк `mapped` и `unmapped`, отклонённых строк.

## Правила преобразования (Transformation Rules)

1. Каждую ночь в 01:00 строится новый снимок: все колонки ERP читаются заново и загружаются во временную область
   пакетами по 2 000 строк; последний пакет может быть меньше.
2. После всех пакетов число строк сверяется с количеством, заявленным источником. Только при совпадении новый
   снимок атомарно заменяет строки ERP в реестре.
3. Логическая сторона назначается только по таблице правил `MAP_ERP_ATTRIBUTE` (`erp_table` + `erp_column` →
   атрибут BusinessObject). Совпадение имён колонки и атрибута правилом не считается: без строки в
   `MAP_ERP_ATTRIBUTE` колонка остаётся `unmapped`.
4. Физические типы переводятся в логические: `VARCHAR` и `CHAR` → `string`, `NUMBER` → `decimal`, `DATE` → `date`.
5. Колонка, удалённая в ERP, исчезает из реестра только после успешной замены снимка — частичных удалений нет.

## Ограничения (Constraints)

- Инкрементального режима нет: ERP не публикует CDC-событий, а удаление видно только по полному снимку.
- Загрузка должна завершиться до запуска CATIA → Catalog в 02:30; измерение Source Coverage в 04:00 видит уже
  новый снимок.
- Если загрузка не завершилась, в реестре остаётся снимок прошлой ночи; смешанного состояния «половина новой,
  половина старой» не бывает.
- Поток не изменяет логическую модель BusinessObject и не пишет в ERP.

## Ошибки и обработка (Error Cases)

| Код | Ситуация | Обработка |
|---|---|---|
| `E-SRC-003` | ERP недоступна | до 5 повторных попыток, затем `dlq.metadata.v1`; остаётся снимок прошлой ночи |
| `E-VAL-002` | пустые `erp_table` или `erp_column`; число строк снимка не совпало | пустые поля — строка отклоняется; несовпадение количества — новый снимок не применяется целиком |
| `E-MAP-001` | правило `MAP_ERP_ATTRIBUTE` указывает на несуществующий атрибут BusinessObject | строка в реестр не пишется, причина в отчёте; атрибут не подбирается по имени |

Состояние `unmapped` — штатный результат, а не ошибка доставки: такая строка не уходит в `dlq.metadata.v1`.

## Версия и статус

Версия 2.1, статус approved, дата проверки 2026-10-20. MAJOR-версия 2 введена при переходе к атомарной замене

## Пример

ERP заявила 7 340 строк каталога колонок. Загрузка идёт четырьмя пакетами — 2 000, 2 000, 2 000 и 1 340 строк;
количество совпало, снимок заменён в 01:37. Правило в `MAP_ERP_ATTRIBUTE` есть у 910 колонок, остальные
получили `unmapped`, поэтому покрытие ERP в Source Coverage — 12,3 %.

```yaml
- erp_table: "DEMO_MATERIAL"
  erp_column: "MATERIAL_CLASS"
  erp_data_type: "VARCHAR"
  erp_description: "Класс материала (демо)"
  # правило MAP_ERP_ATTRIBUTE: DEMO_MATERIAL.MATERIAL_CLASS → BusinessObject.material_class
  mapping_state: mapped
  logical_type: string
- erp_table: "DEMO_MATERIAL"
  erp_column: "LEGACY_FLAG"
  erp_data_type: "CHAR"
  mapping_state: unmapped   # правила нет — колонка уменьшает покрытие
```
